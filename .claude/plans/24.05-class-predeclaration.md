# 24.05 - Predeclare classes without changing runtime effects

## Objective

Allow same-file `extends` and `new` references to later class declarations while preserving deterministic Lua initialization behavior.

## Options Considered

| Option | Type correctness | Runtime correctness | Decision |
|---|---|---|---|
| Checker prepass only | Yes | Parent may not exist at runtime | Reject |
| Reorder complete class statements | Yes | Can reorder top-level effects | Reject |
| Emit class shells, then inheritance and bodies | Yes | Preserves explicit phases | Accept, implemented as runtime shells |

## Delivered

The accepted option is implemented without emitting a shell statement. The
development output contract keeps one generated line per authored line, so the
shell is created inside `class.lua` when `extends` names a class the registry
does not hold yet, and the later declaration fills that same table. No emitted
line moves or appears, and a file that compiled before produces identical Lua.
[ADR-024](../docs/adr/024-two-phase-class-declaration.md) records the
semantics, including what a forward reference does not check.

T-04 executes the Lua. `packages/runtime/tests/support/lua-vm.ts` loads a helper
and a generated chunk into a fengari state, and
`packages/runtime/tests/class-runtime.test.ts` covers child-before-parent,
`super` against a pending parent, initializer order across a forward reference,
a parent that never arrives, a duplicate declaration, and the blocked
metamethods. It found one defect on first run: a filled class read `__pending`
through its parent metatable, so a class extending a shell reported itself as
undefined. Fengari is a Lua 5.3 VM, so it verifies behaviour, not the 5.1
surface; the static Lua 5.1 assertions in `helpers.test.ts` keep that half.

## Scope

- **In:** Class symbol prepass, duplicate and cycle diagnostics, runtime class shells, ordered initialization, source maps, cache fingerprints, and LSP symbols.
- **Out:** Hoisting arbitrary locals or functions and changing top-level execution order outside generated class setup.

- [ ] Child-before-parent classes check and produce valid runtime registration.

- [ ] Existing class output remains compatible when declarations are already ordered.
