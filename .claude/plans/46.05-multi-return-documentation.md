# 46.05 - Record what a multi-return local shows in the editor

> File: `.claude/plans/46.05-multi-return-documentation.md`

## Objective

State what the editor answers for a name declared by a multi-return call, and
close the gap between the language documentation, which describes the rule
correctly, and the tooling documentation, which never mentioned it.

## Context

`docs/en/language/functions.md` already tells the reader that "each target gets
its own type" for a call returning several values. The checker has always honoured
that. The editor did not, so the documentation was describing behaviour a reader
could not see in their own editor — the worst kind of documentation defect,
because the reader concludes the feature is missing rather than the hint.

## Scope

- **In:** The inlay hint and hover sections of the tooling documentation in both
  locales, and the changelog.
- **Out:** The language documentation. The rule it states did not change.
- **Out:** New settings. No switch was added.

## Steps

- [ ] Document that a `local` that destructures a multi-return call gets one hint
      and one hover answer per name, and that a call in non-final position
      contributes only its first value.
- [ ] Note the narrow-to-first rule for `local only = f()`, since it is the case a
      reader is most likely to read as a regression from a tuple label.
- [ ] Add the changelog entry naming both defects by what the user saw: the whole
      tuple on the first name, and nothing on the rest.
- [ ] Record that an editor running an older extension build keeps the old hints
      until the extension is reinstalled and the extension host restarted.
- [ ] Keep both locales in parity.

## Acceptance Criteria

- [ ] `pnpm docs:verify` passes, including the parity check between locales.
- [ ] The tooling documentation and `docs/*/language/functions.md` describe the
      same rule in the same terms.
- [ ] The changelog entry names the extension version that carries the fix.
