# 39.05 - Let a project configure the formatter through .luam.formatter

## Objective

Give a project a way to choose the formatter's whitespace decisions, in a
`.luam.formatter` file, so a team whose house style differs from Luam's default
can adopt the formatter instead of turning it off.

## Scope

- **In:** The `.luam.formatter` file, its field set, its discovery rule, its
  diagnostics, and the wiring into `formatSource`, `formatRange`, the LSP
  provider and `luam format`.
- **In:** An ADR recording why the configuration is a second file rather than a
  manifest domain.
- **Out:** Any option that changes a token. The formatter reprints the token
  stream and verifies the result against the original; an option that rewrote a
  quote, a name or a construct would fail that verification by construction. See
  **The boundary is enforced, not promised** below.
- **Out:** Per-file overrides, directive-based overrides, and ranges excluded
  from formatting. One file, one style, for everything below it.
- **Out:** Presets or inheritance from another package. A project states its own
  style.

## Context

Milestone 32 built the formatter and fixed its style deliberately:

> **The formatter rewrites whitespace, never structure.** It reprints the token
> stream with the comments merged back in [...] Line breaks are the author's;
> indentation, spacing and blank-line runs are the formatter's.

It also settled one contested rule by counting the corpus:

> **`function (` over `function(`.** The corpus was split — 60 to 37 — and no
> rule makes both valid.

That decision was correct for this repository and is not correct for every
project that will use Luam. A 60–37 split is not a consensus; it is a majority,
and the minority is now unable to use the formatter at all. The same holds for
indentation: `INDENT` is a module constant in
`packages/compiler/src/format/format.ts`, hard-coded to four spaces, and a team
that indents with tabs has no path that does not involve not formatting.

This task does not reopen the default. Every option defaults to exactly what the
formatter does today, so a project with no `.luam.formatter` is byte-identical
to one built before this task existed. What changes is that a project may say
otherwise.

### The boundary is enforced, not promised

`formatSource` does not merely intend to preserve meaning. `render` produces a
piece list, `verified` re-renders the output, re-parses it, and compares
`JSON.stringify(pieces.map((piece) => [piece.kind, piece.value]))` against the
original. If a single token's kind or value differs, `formatSource` returns
`null` and the file is left alone.

That is the safety property this task inherits for free, and it is what makes a
configurable formatter safe to build here: an option that tried to change a
string's quotes, drop a semicolon or rename anything would not produce wrong
output, it would produce no output. The option set below is therefore bounded by
what whitespace can express, and the bound is checked by code rather than by
review.

## Design

### Why a second file

`.luam.manifest` is the project contract ([ADR-017](../docs/adr/017-manifest-domain-contract.md)),
and every configuration Luam has lives in it. A formatter configuration does not
fit, for one concrete reason: **the formatter runs on files that have no
project**. A developer opening a single `.luam` file in an editor, outside any
project directory, gets formatting today. Reading the style from a manifest would
mean that file has no style, or has the default while its sibling in a project
has another.

So `.luam.formatter` is discovered by walking up from the file being formatted to
the nearest one, independent of whether a manifest exists. That is also why it is
not simply a `formatter` domain inside the manifest — the two files answer
questions with different scopes.

This is an architectural deviation from "one project file", so T-01 records it as
an ADR rather than as an implementation detail.

### The dialect

`.luam.formatter` is written in the manifest dialect
([ADR-015](../docs/adr/015-luam-manifest-language.md)), parsed and validated by
the same machinery — `manifest-field.ts` for the field table,
`manifest-rules.ts` for validation, `manifest-diagnostics.ts` for reporting, and
the LSP's `manifest-completion.ts` and `manifest-hover.ts` for editor support.

Reusing the dialect is worth more than the file being small. A developer who has
written `.luam.manifest` already knows the syntax, and completion, hover,
defaults and validation all arrive without a second implementation. A JSON or
TOML file would need every one of those written again.

```luam
indent = 'space'
indentWidth = 4
keywordParenSpace = true
maxBlankLines = 1
lineEnding = 'infer'
```

### The field set

Every default is today's behaviour. The right-hand column names the code that
decides it now, so each option is a constant becoming a parameter rather than a
new rule.

| Field | Type | Default | What it controls |
|---|---|---|---|
| `indent` | `'space' \| 'tab'` | `'space'` | The indent character. `INDENT` in `format.ts`. |
| `indentWidth` | number | `4` | Spaces per level. Ignored when `indent` is `'tab'`, which T-02 must decide is an error or a silent ignore. |
| `keywordParenSpace` | boolean | `true` | `function (` versus `function(`. The rule milestone 32 decided 60–37 in `format-spacing.ts`. |
| `maxBlankLines` | number | `1` | Consecutive blank lines kept. `render` currently emits exactly one for `blankBefore`. |
| `lineEnding` | `'infer' \| 'lf' \| 'crlf'` | `'infer'` | `newlineOf` currently infers from the source. |

T-01 fixes this set. Adding a sixth option later is cheap; removing one is a
breaking change for every project that set it, so the list should be short and
each entry should name a decision a real team actually disagrees on. An option
nobody asked for is a permanent maintenance cost and a second code path through
the formatter for every future change.

Anything not in the table is not configurable, and `limitations.md` should say so
rather than leaving readers to discover it one field at a time.

### Threading the options through

`formatSource(source)` and `formatRange(source, startLine, endLine)` gain an
optional trailing options parameter. Omitted, they behave exactly as today, which
keeps every existing call site — including the LSP's `formatting.ts` — compiling
and correct until it is updated deliberately.

Inside, `INDENT` stops being a module constant and `renderLine` takes the spacing
decisions it needs. `verified` is unchanged: it re-renders with the same options
and compares the same signature, so the round-trip guarantee holds for every
configuration rather than only for the default.

### Discovery and caching

- `luam format` reads the nearest `.luam.formatter` from the project directory
  once per run.
- The LSP reads it per document, walking up from the document's own path, and
  re-reads on change — a formatter file edited in the editor must take effect
  without a restart.
- A file with no `.luam.formatter` above it uses the defaults.

Two `.luam.formatter` files on one path do not merge. The nearest one wins
entirely, which is the rule that is explainable in one sentence; merging would
make the effective style a computation nobody can perform by reading.

### Diagnostics

| Code | When |
|---|---|
| `formatter-unknown-field` | A field the table does not define. |
| `formatter-invalid-value` | A value outside the field's type or range. |
| `formatter-parse-error` | The file does not parse as the manifest dialect. |

A `.luam.formatter` that does not parse is an error, and the run stops. Falling
back to the defaults would silently format a project against a style it
explicitly rejected, which is worse than refusing.

## Out of Scope

- Any option that changes a token: quote style, semicolons, name casing,
  parenthesis insertion, line breaking.
- Per-file or directive-based overrides, and ignore ranges.
- Presets, inheritance, or reading another package's configuration.
- Reopening the project's own default style. This repository keeps the milestone
  32 defaults, and [39.04](39.04-conventions-gate.md) keeps enforcing them.

## Record

### T-01 - The shape, and the ADR

- **The field set is the five in the plan's table**, each defaulting to today's
  behaviour, plus a bound on the two numbers: `indentWidth` is 1 to 8 and
  `maxBlankLines` is 0 to 4. Both bounds exist because an unbounded number is a
  way to produce a file nobody wants and no way to catch it. Rejected and
  recorded: anything that touches a token, per the scope; and per-file,
  directive, preset and inheritance mechanisms, which make the effective style a
  computation instead of a fact.
- **`indentWidth` with `indent = 'tab'` is silently ignored**, not an error. It
  is the value that applies if the project switches back to spaces, and erroring
  on a field that is merely inactive would make a legal file illegal for a reason
  that has nothing to do with it. The field's own summary says it is ignored, so
  the behaviour is documented where it is read.
- **`.luam.formatter` is not formatted by `luam format`**, for the same reason
  `.luam.manifest` is not — [39.01](39.01-format-command.md) selects by extension,
  and both files fall outside it by construction rather than by a special case.
- **No proposed option can change a token.** The five fields are indent
  character, indent width, one inter-token space, blank-line count and line
  ending; every one of them is whitespace between pieces the formatter reprints
  verbatim. This is not asserted by review: `verified` re-renders the output with
  the same options, re-parses it, and compares
  `JSON.stringify(pieces.map((p) => [p.kind, p.value]))` against the original. An
  option that changed a token would return `null` and format nothing.
- **[ADR-042](../docs/adr/042-formatter-configuration-file.md)** records the
  second-file decision, with the projectless-file case as the reason and the
  one-project-file convention as the cost.

### T-02 - The formatter is parameterised

- `format-options.ts` holds `FormatOptions`, `DEFAULT_FORMAT_OPTIONS`,
  `indentUnit` and `newlineOf`. `formatSource` and `formatRange` take an optional
  trailing `Partial<FormatOptions>`; omitted, both behave exactly as before, which
  is why every existing call site compiled unchanged.
- `INDENT` stopped being a module constant. `renderLine` takes the options and
  reads `keywordParenSpace` for a `(` that follows a keyword — the milestone 32
  rule, which is what makes `function (` against `function(`. A call's tight
  binding is a separate branch and is unaffected, and `[` was split out of the
  same condition rather than dragged along.
- `Line.blankBefore` became `Line.blankLines`, the real run length, so
  `maxBlankLines` can keep two where a boolean could only keep one. With the
  default of `1` the output is byte-identical to before, which the corpus test
  proves over all 149 files.
- `verified` re-renders with the same options, so the round-trip guarantee holds
  for every configuration and not only the default.

### T-03 - Reading the file

`analyzeManifest` gained a third parameter, a `ManifestSchema` carrying the field
table, the removed-field map, a normalizer and an optional diagnostic retag. The
manifest passes `MANIFEST_SCHEMA` and is unchanged; the formatter file passes
`FORMATTER_SCHEMA`. That is the reuse the plan asked for: the dialect, the
expression evaluator, the type checking, the closed-set checking, the position
map and the editor's completion and hover all arrive without a second
implementation. The wording of the dialect's own errors is untouched and stays
correct, because a `.luam.formatter` **is** a manifest-dialect file.

The three diagnostics are produced by retagging what the pass reports:
`config-unknown-field` becomes `formatter-unknown-field`, a lexer or parser
diagnostic becomes `formatter-parse-error`, and everything else becomes
`formatter-invalid-value`. The range checks on the two numbers are added on top
with the same code. Retagging lives in the schema rather than in
`analyzeFormatterFile`, so the editor path gets the formatter codes too.

**Discovery is filesystem-injected.** `packages/compiler` imports no `node:fs`
anywhere and is bundled for the browser playground, so `formatter-discovery.ts`
takes a four-method `FormatterFileSystem` and each consumer passes its own. The
walk stops at a `node_modules` segment, so a library's `.luam.formatter` is
unreachable even before the fact that library sources are never formatted.

### T-04 and T-05 - The two surfaces, and the file itself

- `luam format` resolves the nearest file from the project directory once per run.
  An invalid one exits `2` and formats nothing, matching the CLI's meaning for an
  invalid configuration.
- The LSP resolves per document, walking up from the document's own path, and
  **does not cache**. Formatting is user-initiated, so the cost is one stat per
  invocation, and "re-reads on change" is true by construction rather than by
  cache invalidation. An invalid file yields no edits, so the editor never
  reformats against a style the project rejected.
- `.luam.formatter` is analysed as a manifest document with the formatter schema,
  so its diagnostics, completion and hover all work. `manifest-completion.ts` and
  `manifest-hover.ts` pick the field table from the document's path through
  `manifest-field-table.ts`.
- The extension associates `.luam.formatter` with the `luam-manifest` language —
  same grammar, same dialect — adds it to the activation events, and watches
  `**/.luam.formatter`.

### T-06 - What the tests pin

- The corpus test in `format-corpus.test.ts` passes unchanged, which is the
  byte-identical-to-before proof across all 149 files.
- `formatter-options.test.ts` covers each field at its non-default value, the
  three diagnostics, the nearest-file rule, the library exclusion, and
  idempotence-plus-meaning under seven configurations including one that sets
  four fields at once.
- On the compiled-Lua property: the emitter is source-preserving, so
  `maxBlankLines` legitimately changes the blank lines in the emitted Lua. The
  test therefore compares each configuration's output against the
  **default-formatted** source's output, modulo leading indentation *and*
  blank-line runs — both of which are whitespace the configuration explicitly
  owns. Token content is identical, which is the property that matters and which
  `verified` enforces independently.
- The CLI and the LSP each assert their output equals `formatSource(source, style)`
  under the same non-default configuration, so the two surfaces meet at one
  function.
