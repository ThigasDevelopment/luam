# 16.03 - Complete, highlight, and explain decorators in the editor

> File: `.claude/plans/16.03-decorator-editor-support.md`
> A generated method the author never typed only pays off if the editor shows it.
> This task is what turns `@Getter` from a code generator into a feature you can
> discover by typing `@`.

## Objective

Make decorators visible in VS Code: highlighted, completed after `@`, and
explained on hover — and make the accessors they generate behave like members the
author wrote.

## Scope

- **In:** Decorator name completion, hover on a decorator, highlighting in the
  grammar, and how synthetic accessors appear in completion, hover,
  go-to-definition, signature help, and the document outline.
- **Out:** Quick fixes ("add @Getter to this field"), a rename that rewrites both
  the field and its accessors, and any code lens. All three are worth having and
  none belongs in the milestone that introduces the syntax.

## Design

Most of this is already paid for. 16.2 registers accessors in the class member
table and feeds them to the symbol index, so `player:getName()` completes,
hovers, and resolves through the paths that already serve hand-written methods.
What is left is the decorator itself, and the one place the synthetic origin
leaks: the outline.

An accessor carries the position of its field. In the document outline that would
put three symbols on one range — the field and its two accessors — so
`declaration-collector` filters `isSynthetic` members out of the outline while
keeping them in the class member table the completion and hover paths read.

## Steps

- [ ] Add a decorator completion context to `lsp/src/features/completion-context.ts`:
      the cursor sits after an `@` at the start of a line inside or immediately
      above a class body. It offers `Getter` and `Setter`, each with the
      documentation string that explains what it generates.
- [ ] Source the completion list from `KNOWN_DECORATORS` in
      `checker/decorators.ts`, so a decorator added later appears in the editor
      without a second edit.
- [ ] Hover on `@Getter` above a field states the exact method it generates for
      *that* field — "Generates `isAdmin(): Flag`". Read it from the class member
      the checker registered, not by re-deriving the name: the registry already
      resolved the field's type, which is the only thing that knows whether the
      answer is `is` or `get`.
- [ ] Filter synthetic methods out of the document outline in
      `lsp/src/symbols/declaration-collector.ts`, and keep them in the member map
      the class type is built from.
- [ ] Confirm go-to-definition on `player:getName()` lands on the `name` field,
      and add the fallback if it does not: the synthetic method's position is the
      field's, so this should hold without new code.
- [ ] Confirm signature help on `player:setName(` shows `value: string`, again
      through the existing path.
- [ ] Add decorator highlighting to `packages/vscode/syntaxes/luam.tmLanguage.json`:
      `@` as `punctuation.definition.decorator.luam` and the name as
      `entity.name.function.decorator.luam`, matched only at the start of a line
      so an `@` elsewhere is not painted as a decorator.
- [ ] Check the block-indentation rules in `language-configuration.json` still
      behave when a decorator line precedes `class Player {`.

## Acceptance Criteria

- [ ] Typing `@` above a field offers `Getter` and `Setter` with descriptions,
      and offers nothing outside a class.
- [ ] Hovering `@Getter` above `admin: boolean` says it generates
      `isAdmin(): boolean`; above `name: string`, `getName(): string`; and above
      `admin: Flag` where `type Flag = boolean`, `isAdmin(): Flag`.
- [ ] `player:` completes `getName` and `setName` for a decorated class, and the
      items are indistinguishable from hand-written methods.
- [ ] Hover on `getName` shows `(self) -> string`.
- [ ] Go-to-definition on `player:getName()` opens the `name` field.
- [ ] The outline of a class with two decorated fields lists the class, the two
      fields, and the hand-written methods — no accessor entries.
- [ ] `@Getter` renders as a decorator in VS Code, and `local a = b @ c` does not.
- [ ] A file being typed — `@Get` with no class body yet — still analyses, still
      completes, and reports at most the parse diagnostic for the incomplete
      declaration.
- [ ] `pnpm typecheck`, `pnpm build`, and `pnpm test` pass.
