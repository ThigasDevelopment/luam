# 51.07 - Settle the helper and vendored library placement

## Objective

Fix where the runtime helpers land and where vendored libraries sit relative to
them and to the authored `scripts` list, without deciding how a library reaches a
resource — which is a separate decision and is explicitly out of this milestone.

## What this task decides

**The helper directory.** ADR-008 places helpers at `lib/<environment>/`; the
sketch this milestone came from places them at `libs/`, flat:

```
<script src = 'libs/class.lua' type = 'shared' cache = 'false'/>
<script src = 'libs/env.lua'/>
```

The per-environment subdirectory exists to keep a shared and a server helper of
one name apart. Helper names are unique across environments today, so flat works
— but that is a fact about the current helper set, not a rule, and whichever is
chosen has to be written down with the rule that keeps it true.

**The position of helpers and libraries.** Both sit at the head of the `SCRIPTS`
section, helpers first, before the first authored entry. An authored entry cannot
be placed before them: a helper loaded after the code that uses it is a resource
that fails at load, and `class.lua` loaded twice resets the class registry.

## What this task does not decide

**How a library reaches the resource.** ADR-038 vendors a library's code into the
consuming resource, which is what ships today and what stays in this milestone.
The project owner is considering the opposite model — a library is its own MTA
resource on the server, and a consumer names it in `<include>` — because a
library carrying a lot of code and a lot of images is copied into, and downloaded
by, every resource that uses it.

That is a distribution decision with consequences this milestone cannot absorb:

- A vendored library's surface is ordinary code the checker sees. A library that
  is a separate resource is reached through `exports`, so its surface crosses a
  resource boundary and only what the export ABI carries survives —
  [ADR-033](../docs/adr/033-resource-export-abi.md) is the machinery for that, and
  it is typed, which is the strongest argument the model has.
- Not every library has a runtime surface at all. A library of classes, types and
  enums is erased at build time, so there is nothing to `<include>` and it must be
  vendored. The discriminator is therefore not size but whether the library has a
  surface that survives the boundary — and size is what makes the question urgent,
  not what answers it.
- Deployment stops being "copy one folder". The library resources must reach the
  server too, which is a job the workspace from milestone 50 is shaped to own and
  currently does not.
- Two resources needing two versions of one library cannot both have it, because
  a server holds one resource of a given name.

Because the model changes what `environment.libraries` *means*, and this milestone
only changes where its output is written, `environment.libraries` keeps its
ADR-038 meaning verbatim here.

## Scope

- **In:** The helper directory record, helper and library position, and per-side
  library emission under the current vendoring model.
- **Out:** The distribution model, transitive resolution, versioning and asset
  sharing — a separate record and its own milestone.

## Steps

- [ ] Write the helper directory decision as an amendment to ADR-008. If it
      flattens, state the rule that keeps two helpers of one name from colliding
      rather than relying on the current set.
- [ ] Move the helpers to the chosen directory, and update the pruning walk, the
      resource map and the bundle layout that name the current one.
- [ ] Emit one `<script>` per vendored library side, in the declaration order of
      `environment.libraries`, after the helpers and before the first authored
      entry.
- [ ] Give a library's side the same `type` and `cache` rules as any other script,
      with no exception.
- [ ] Report an authored `scripts` entry whose path resolves inside the helper or
      library directory, rather than emitting an entry that would load a helper
      twice.

## Acceptance Criteria

- [ ] The helper directory decision exists as an ADR amendment with its collision
      rule.
- [ ] Helpers are emitted at the chosen path and nothing else references the old
      one.
- [ ] Libraries follow the helpers, in declaration order, before every authored
      entry.
- [ ] A client-only library emits one element and no server element.
- [ ] An authored entry that would match a helper or library path is reported and
      writes nothing.
- [ ] `environment.libraries` behaves exactly as it does today in every other
      respect.
