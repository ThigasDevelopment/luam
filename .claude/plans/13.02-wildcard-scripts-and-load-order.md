# 13.02 - Emit wildcard script entries with a declared load order

> File: `.claude/plans/13.02-wildcard-scripts-and-load-order.md`
> This is the task that changes what the manifest *is*. It stops being an
> enumeration of the modules the compiler produced and becomes a description of
> where they live.

## Objective

Collapse each environment's scripts into one wildcard entry, and give the author
a way to pin the files that must load before the rest.

## Scope

- **In:** Wildcard script entries per environment, the deterministic default
  order, the `loadOrder` field in `luam.json`, asset ordering, and the pruning
  fallback that no longer has a manifest to read.
- **Out:** Attribute defaults and section comments (13.3), `min_mta_version`
  (13.5).

## Steps

- [ ] Replace the per-module `ManifestScript` list with a pattern list:
      `src/shared/**/*.lua`, `src/server/**/*.lua`, `src/client/**/*.lua`, each
      emitted only when the project has at least one module on that side.
- [ ] Fix the default order: helpers (`lib/`), then `config.lua`, then the
      pinned entries, then the wildcards in shared, server, client order.
- [ ] Add an optional ordered `loadOrder` array to `luam.json`, validated by the
      CLI config schema like every other field. Each entry is a source path
      relative to the project root; an entry matching no file is a build error,
      so a rename cannot break the order silently.
- [ ] Emit each pinned file as an explicit entry ahead of its environment group.
      The owner's own manifest in `examples/meta.xml` does exactly this for an
      `index`/`main` file, so an explicit entry ahead of a wildcard that also
      matches it is the established pattern.
- [ ] **Verify the double-load question on a real server before locking it in.**
      If MTA runs a file matched by both an explicit entry and a wildcard twice,
      fall back to enumerating that environment explicitly whenever `loadOrder`
      pins a file inside it, and keep the wildcard for the untouched
      environments. Record the answer in
      [ADR-008](../docs/adr/008-generated-manifest-standard.md).
- [ ] Apply the same ordering rule to `<file>` entries. Asset order is
      meaningful — a shader can depend on another — so assets follow `loadOrder`
      first and their current alphabetical order after it, never the reverse.
- [ ] Move pruning off "every entry of the previous `meta.xml`". An entry is now
      a pattern, not a path, so the removable set falls back to the source
      directory walk plus `lib/`, `meta.xml`, and the `.lua` files.

## Acceptance Criteria

- [ ] A project with fifty server modules produces one `<script>` entry for the
      server side, and adding a fifty-first module leaves `meta.xml` byte
      identical.
- [ ] An environment with no modules emits no entry for that side.
- [ ] `"loadOrder": ["src/server/index.luam"]` puts that file ahead of the
      server group, and the emitted path is the compiled `.lua` path.
- [ ] A `loadOrder` entry naming a file that does not exist fails the build with
      a diagnostic that names the entry, and no manifest is written.
- [ ] Deleting a source file still removes its `.lua` from the resource, proving
      pruning survives without the manifest enumeration.
- [ ] The generated resource still loads in MTA: helpers first, framework before
      the handlers that extend it, verified on a scaffolded project.
- [ ] `pnpm typecheck`, `pnpm build`, and `pnpm test` pass.
