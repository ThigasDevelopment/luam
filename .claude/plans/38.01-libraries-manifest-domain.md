# 38.01 - Add the libraries manifest domain and resolve packages from disk

## Objective

Give a project a way to name the Luam libraries it uses, and give the build a way
to find them on disk, without any step that touches the network.

## Scope

- **In:** The `libraries` manifest domain, the `luam` field a library package
  declares, resolution from `node_modules`, and the diagnostics for a name that
  resolves to nothing or to something malformed.
- **In:** The `requires` list a library declares, read but not walked.
- **Out:** Compiling the resolved sources, which is [38.02](38.02-library-compilation.md).
- **Out:** Emitting them, which is [38.04](38.04-library-vendoring.md).
- **Out:** Fetching. `npm install` is the only step that touches the network, and
  it is the developer's, never the build's.
- **Out:** A `luam add` command. ADR-038 rejected it; the package manager already
  owns installation.

## Context

[ADR-038](../docs/adr/038-library-distribution.md) was accepted in milestone 34,
which states in its own acceptance section that it "produces a decision, not an
implementation" and that "the milestone that builds it follows". No milestone
followed. Today:

```text
grep -rln "libraries" packages/*/src
```

returns nothing. `packages/compiler/src/manifest/manifest-contract.ts` reads
`compiler`, `sources`, `assets`, `dependencies`, `engine`, `environment` and
`output`, and stops. A developer consuming third-party Luam code still copies
files, which is the problem milestone 34 set out to solve and only answered on
paper.

This task is the first of the milestone that builds it. It implements the ADR as
written; where the ADR is silent, the decision is recorded here rather than
invented in code.

### What the ADR fixed, and what it left open

Fixed by the ADR, not re-decided here:

- A library is an npm package with a `luam` field naming its per-environment
  sources, in the same shape as the manifest's `sources` domain.
- Presence in `node_modules` is not enough. A package absent from `libraries` is
  not compiled, because a build must be a function of reviewed files rather than
  of install state.
- A name in `libraries` with no package on disk is a configuration error naming
  the package and the install command — never a fetch.
- Transitive dependencies do not exist. A library declares a `requires` list;
  the compiler names what is missing and the developer lists it.
- The library owns its environment; the consumer does not reassign it.

Open, and decided in T-01:

- Where resolution starts, and whether it follows Node resolution or reads
  `node_modules` at the project root only.
- What a scoped name resolves to on disk, given that the emitted path flattens
  `@scope/name` to `scope-name` ([38.04](38.04-library-vendoring.md) owns the
  emitted path; this task owns the lookup).
- Whether a workspace link — a `file:` dependency or a pnpm workspace package —
  is supported, which matters because this repository is a pnpm workspace and
  the first test fixture will be one.

## Design

### The manifest domain

`libraries` is an ordered list of package names:

```luam
libraries = { '@luam/collections', 'mta-async' }
```

Ordered, because [ADR-038](../docs/adr/038-library-distribution.md) makes the
declaration order the emission order in `meta.xml`. A duplicate name is a
configuration error rather than a silent de-duplication, since two entries for
one package say the author expected something the model does not provide.

The field is added to `packages/compiler/src/manifest/manifest-fields.ts` beside
`dependencies`, with its own `rule` and `owner`, and read in
`manifest-contract.ts` beside `readDependencies`. `dependencies` is untouched and
keeps its meaning — MTA resources written as `<include>`. The two are different
questions and stay different fields, which the manifest reference has to say
plainly, because the names are close enough to confuse.

### The library's own declaration

A library package declares, in its `package.json`:

```json
{
    "luam": {
        "sources": { "shared": ["src/**/*.luam"] },
        "requires": []
    }
}
```

`sources` takes the same three sides the project manifest takes, and the same
pattern rule. Patterns are relative to the package root and may not escape it —
a pattern resolving outside the package is a diagnostic, because a library
reaching into the consumer's tree is a supply-chain surface this model does not
open.

`requires` names other packages the library expects the consumer to list. It is
read and reported against; it is never walked.

### Diagnostics

Four, all reported before any file is compiled:

| Code | When |
|---|---|
| `config-library-missing` | A name in `libraries` has no package on disk. Names the package and the install command. |
| `config-library-invalid` | The package exists but its `luam` field is absent or malformed. Names the field. |
| `config-library-duplicate` | The same package is listed twice. |
| `config-library-escape` | A source pattern resolves outside the package root. |

The missing-requirement diagnostic belongs to
[38.03](38.03-library-collisions.md), because it is reported against the
resolved set rather than against one entry.

### The network invariant

Nothing in this task opens a connection. The build reads `node_modules` from
disk; an offline build with a populated `node_modules` produces byte-identical
output; a missing package is a configuration error, not a fetch. T-04 asserts
this rather than assuming it, because the invariant is the one `.claude/CLAUDE.md`
states first and the one a reviewer will check first.

## Steps

### T-01 - Decide resolution

**Agent:** architecture-engineer

- [ ] Decide whether resolution walks Node's algorithm from the project root or
      reads `<projectRoot>/node_modules/<name>` only, and record the rejected
      alternative. Prefer the narrower rule unless a workspace case forces the
      wider one.
- [ ] Decide how a scoped name is looked up, and confirm it is independent of the
      flattening [38.04](38.04-library-vendoring.md) applies to the emitted path.
- [ ] Decide whether a pnpm workspace link and a `file:` dependency resolve, and
      state it. The first fixture in [38.05](38.05-library-tests.md) is a
      workspace package, so this cannot stay unanswered.
- [ ] Confirm the resolved path is recorded in the build fingerprint, so a
      library change invalidates the cache in `packages/compiler/src/project/project-cache.ts`.

### T-02 - Add the manifest domain

**Agent:** architecture-engineer

**Files:** `packages/compiler/src/manifest/manifest-fields.ts`,
`packages/compiler/src/manifest/manifest-contract.ts`,
`packages/compiler/src/manifest/manifest-defaults.ts`

- [ ] Add `libraries` as an ordered string list with an empty default.
- [ ] Read it in the contract beside `dependencies`, preserving order and
      reporting a duplicate rather than de-duplicating.
- [ ] Confirm the manifest completion and hover in the LSP pick the field up from
      the field table without a second registration.

### T-03 - Read the library declaration

**Agent:** architecture-engineer

**Files:** `packages/compiler/src/project`

- [ ] Read `package.json` for each named package and parse its `luam` field into
      the same per-environment shape `sources` produces.
- [ ] Report `config-library-invalid` for an absent or malformed field, naming
      what was expected.
- [ ] Expand the patterns against the package root and report
      `config-library-escape` for anything resolving outside it.
- [ ] Read `requires` into the resolved set without walking it.

### T-04 - Assert the network invariant

**Agent:** architecture-engineer

- [ ] Confirm no code path added here performs I/O beyond reading the filesystem.
- [ ] Confirm a build with a populated `node_modules` and no network succeeds and
      is byte-identical to one with network.
- [ ] Confirm `config-library-missing` names the install command and does not
      attempt one.

## Acceptance Criteria

- [ ] A `libraries` entry naming an installed package resolves to a package root
      and a per-environment source list.
- [ ] A name with no package on disk reports `config-library-missing` naming the
      package and the install command, and the build writes nothing.
- [ ] A package present in `node_modules` but absent from `libraries` is not
      resolved and not compiled.
- [ ] A malformed `luam` field reports `config-library-invalid`.
- [ ] A pattern escaping the package root reports `config-library-escape`.
- [ ] A duplicate entry reports `config-library-duplicate`.
- [ ] `dependencies` behaves exactly as it does today.
- [ ] An offline build with a populated `node_modules` succeeds and matches a
      networked one byte for byte.

## Out of Scope

- Compiling, checking, or emitting the resolved sources.
- Walking `requires`.
- A `luam add` command, a lockfile, or a registry.
- Version conflict resolution. Two versions of one library cannot coexist in a
  flat Lua namespace, which is why the model has no resolver.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Node resolution pulls in a package the manifest never named | High | T-01 prefers the narrow lookup; presence in `node_modules` is explicitly not sufficient |
| A library pattern reaches into the consumer's tree | High | `config-library-escape`, asserted in T-03 |
| A workspace link resolves differently from a registry install | Medium | T-01 decides it before the fixture in 38.05 depends on it |
| A changed library does not invalidate the build cache | Medium | T-01 puts the resolved path into the fingerprint |
| `libraries` and `dependencies` are confused by readers | Low | 38.06 states the distinction on the manifest reference page |
