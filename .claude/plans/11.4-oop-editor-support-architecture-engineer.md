# 11.4 — Editor support for the MTA OOP API

> File: `.claude/plans/11.4-oop-editor-support-architecture-engineer.md`
> Can run in parallel with 11.3. It depends on member resolution, not on the
> gate.

## Objective

Make the OOP API discoverable in the editor: typing `player:` offers the methods
that element actually has, scoped to the file's environment, and hover explains
what the method wraps.

## Scope

- **In:** Member completion after `:` and `.` on an element type, hover for an
  OOP method, the existing diagnostics flowing through unchanged.
- **Out:** Converting between the procedural and OOP forms with a code action,
  renaming across the two forms.

## Steps

- [x] Extend `resolveReceiver` so an element type resolves to a class target,
      reusing the class member path rather than adding a branch.
- [x] Offer inherited members, so `Player` completes what `Element` declares.
- [x] Scope completion by environment, so a server-only method never appears in
      a client file — the same rule the procedural catalog already follows.
- [x] Show in hover the signature, the environment, and the procedural function
      the method wraps.
- [x] When the `oop` flag is off, offer no OOP members at all, so completion
      never suggests a call the build would reject.
- [x] Confirm the LSP reports the 11.2 and 11.3 diagnostics with no change.

## Acceptance Criteria

- [x] `player:` in a server file offers `getName`, offers the members inherited
      from `Element`, and does not offer a client-only method.
- [x] Hover on `getName` names the return type and `getPlayerName`.
- [x] With `oop` off, `player:` offers nothing from the OOP surface.
- [x] Completion latency on a large file stays within the budget recorded in
      [performance.md](../docs/performance.md).
