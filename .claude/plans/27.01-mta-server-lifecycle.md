# 27.01 - Run a local MTA server through the CLI

## Objective
Let the CLI own the lifecycle of an existing local MTA Server installation through an interactive `luam server` command and an opt-in `luam dev --start-server` workflow.

## Scope
- **In:** Windows and Linux executable discovery, foreground process supervision, interactive standard input for `luam server`, startup readiness, graceful shutdown, unexpected-exit handling, and integration with the existing development loop.
- **Out:** Downloading or updating MTA, detached/background processes, remote process management, multiple server instances, process discovery by PID or port, and changes to `luam ensure`.

## Decisions
- Keep the current `luam dev` behavior unless `--start-server` is present.
- Reuse `serverPath` as the MTA installation root.
- Add an optional `development.server.executable` override relative to `serverPath`; otherwise probe platform-specific executable names.
- Start only processes owned by the current CLI invocation and stop only those processes.
- Implement process management behind an injected service so command tests never launch a real MTA process.
- Treat server readiness as a lifecycle state. Do not run the first HTTP refresh/restart until the owned server is ready.
- Keep download and installation concerns out of the process supervisor.

## User Experience

```text
luam server
luam dev --start-server
```

`luam server` loads `.luam.manifest`, resolves the executable from `serverPath`, runs it in the foreground, attaches the terminal, and exits with the server process. `Ctrl+C` first requests a graceful MTA shutdown and falls back to terminating the child after a bounded timeout.

`luam dev --start-server` starts the server before entering the existing build, sync, restart, watch, and log flow. A startup failure prevents build/watch from starting. An unexpected child exit stops the development loop and returns a failure exit code.

## Architecture

```text
command registration
        |
        v
MTA process supervisor ----> executable resolver
        |                           |
        |                           v
        |                    serverPath + platform
        v
owned child process ----> readiness / exit / shutdown
        |
        v
dev command ----> ensure runner ----> transport restart
        |
        v
server.log follower
```

The supervisor owns executable resolution, spawn options, readiness, and shutdown. Commands own policy: `server` selects interactive console mode, while `dev --start-server` coordinates the child with the existing watcher and log follower.

## Acceptance Criteria
- [x] `luam server` starts an existing local MTA installation from `serverPath` and accepts MTA console input.
- [x] Windows and Linux executable names resolve automatically, with a manifest override for nonstandard layouts.
- [x] `luam dev --start-server` waits for readiness before its first transport call and then preserves the current build/sync/watch/log behavior.
- [x] `luam dev` without `--start-server` never starts or stops an MTA process.
- [x] `Ctrl+C` closes the watcher and log follower, requests graceful server shutdown, and cannot leave an owned child running after the fallback timeout.
- [x] A missing executable, spawn error, readiness timeout, or early child exit produces an actionable diagnostic and a nonzero exit code.
- [x] The CLI never stops an MTA process it did not start.
- [x] No shell is involved in executable launch, and configured executable paths cannot escape `serverPath`.
- [x] Unit and command tests pass on Windows and Linux CI without an MTA installation.
- [x] Existing CLI tests remain green.

## Risks
- MTA readiness text may vary by release or platform. Isolate markers and cover known variants with fixtures; report timeout context rather than silently continuing.
- Windows console signal delivery is not equivalent to POSIX signals. Prefer the MTA `shutdown` command and test the forced fallback separately.
- Owned-server console output can duplicate lines read from `server.log` during `dev`. Keep `server` fully interactive; in integrated `dev`, preserve the existing parsed log stream and route only lifecycle/process errors outside it.
- Starting the process before sync means the target resource may not exist at boot. Readiness followed by the existing refresh/restart flow makes the newly synchronized resource visible.
