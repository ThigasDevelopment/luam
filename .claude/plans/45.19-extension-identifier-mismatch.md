# 45.19 - Detect the extension by the identifier it actually publishes

> File: `.claude/plans/45.19-extension-identifier-mismatch.md`

## Objective

Make `luam doctor` and `luam setup` recognise an installed Luam extension, which
they cannot do today because they look for an identifier the extension never
had.

## Reproduction

Confirmed on the current tree, on Visual Studio Code 1.135.0, with the CLI
installed from this repository at 0.19.12:

```
$ luam setup -y
Visual Studio Code: installing the Luam extension.
Visual Studio Code: installed from the release.

$ code --list-extensions | grep luam
luam.luam

$ luam doctor
Visual Studio Code: Luam extension not installed. Run "luam setup".
```

`setup` succeeds, the extension is installed, and `doctor` reports it missing on
the next line.

## Root Cause

`EXTENSION_ID` is `'thigasdevelopment.luam'`
(`packages/cli/src/editor/editor-service.ts:10`). An extension identifier is
`<publisher>.<name>`, and `packages/vscode/package.json` declares
`"publisher": "luam"` with `"name": "luam"`, so the extension installs and
reports as `luam.luam`. Nothing else in the repository uses the constant's
value — it is a single wrong string with three consequences:

- `hasExtension` (`editor-service.ts:97`) compares the listing against the wrong
  id, so it always returns false and `doctor` always says "not installed".
- `setup` never short-circuits on an already-installed extension, so it reinstalls
  every time it runs.
- The marketplace install (`editor-service.ts:100`) is attempted with the wrong id
  and always fails, so every `setup` silently falls through to downloading the
  release VSIX. A network request is made where a marketplace hit should have
  served, and the fallback path is the only one that has ever been exercised.

## Scope

- **In:** The extension identifier, the detection it drives, the marketplace
  install path it drives, and a guard that keeps the two definitions from drifting
  again.
- **Out:** Changing the publisher. `luam.luam` is the identifier the published
  extension already carries and users already have installed; renaming it would
  strand every existing install. The CLI's npm scope, which is unrelated.

## Steps

- [x] Derive the identifier from `packages/vscode/package.json` rather than
      restating it: read `publisher` and `name` at bundle time and inline the
      result, so a single source produces the constant.
- [x] If the value must stay a literal for bundling reasons, add a test that reads
      the extension manifest and asserts the constant equals
      `<publisher>.<name>`, so the drift fails the suite instead of the user's
      terminal.
- [x] Confirm `hasExtension` compares case-insensitively against the corrected id
      — `--list-extensions` casing is not guaranteed — and keep the trim.
- [x] Make `setup` report "already installed" and skip the install when detection
      succeeds, and confirm the marketplace path is now reached before the release
      download.
- [x] Add a test for the three-way outcome `setup` can produce — already
      installed, installed from the marketplace, installed from the release — with
      the editor command stubbed, so no test touches the network or a real editor.
- [x] Check the same constant is not duplicated in the VS Code extension's own
      code or in the release workflow.

## Acceptance Criteria

- [x] `luam doctor` reports the extension as installed when
      `code --list-extensions` lists `luam.luam`.
- [x] `luam setup` on a machine that already has the extension reports it and
      installs nothing.
- [x] `luam setup` on a clean machine reaches the marketplace before the release
      download, proven by a stubbed test asserting the call order.
- [x] A test fails if `EXTENSION_ID` and the extension manifest disagree.
- [x] No test performs a network request or invokes a real editor.

## Outcome

`EXTENSION_ID` stayed a literal — bundling reads it at build time and inlining
from `packages/vscode/package.json` would put a filesystem read in the CLI
bundle — so the second step is what shipped: `tests/extension-identifier.test.ts`
reads the extension manifest and asserts the constant equals
`<publisher>.<name>`, and asserts the constant is lower case so the listing
comparison cannot miss. `setup` already short-circuited on `hasExtension`; it
simply never returned true. Nothing else in the repository restated the value.
