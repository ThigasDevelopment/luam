# 28.01 - Add contextual typing for callback parameters

## Objective

Infer unannotated callback parameters from every callable signature that accepts a function, then use those inferred types for checker diagnostics, hover, and receiver-specific completion.

## Problem

The checker currently evaluates call arguments before applying the callee signature. A function expression therefore builds its parameters from authored annotations only, and every omitted annotation becomes `any`. The LSP then indexes those parameters from the AST and also records them as `any`, so `parameter.` cannot offer the fields, methods, or native extensions of the callback's declared parameter type.

The MTA catalog compounds the issue: the generator maps TypeScript function type nodes to `any`. APIs such as `addCommandHandler` consequently lose the callback signature before the compiler can provide contextual typing. `addCommandHandler` is only a representative case; the behavior must apply to project functions, declaration files, Lua/runtime libraries, generated MTA APIs, methods, constructors, and other callable values.

## Options Considered

| Option | Correctness | Maintenance | Decision |
|---|---|---|---|
| Infer callback parameters only in LSP completion | Checker, hover, and completion can disagree; duplicates call resolution | High | Reject |
| Mutate missing AST annotations from the LSP | Couples editor concerns to parser nodes and makes analysis order observable | High | Reject |
| Contextually check function expressions in the compiler and let the LSP consume the recorded type | One semantic result powers diagnostics and editor features | Medium | Accept |

## Semantic Contract

- Contextual typing applies whenever an expression is checked against an expected function type, not by API name.
- An authored callback parameter annotation wins over contextual inference and remains subject to normal function assignability diagnostics.
- An unannotated callback parameter at index `n` receives parameter `n` from the expected signature. Authored parameters without a matching expected position remain `any`.
- The callback body is checked only after contextual parameter symbols enter its scope.
- The callback's authored return annotation or inferred body return remains authoritative. Existing assignability rules compare that result with the expected callback return type.
- Optional function types unwrap to their function member. A union provides context only when its callable alternatives yield an unambiguous parameter type at that position; otherwise the checker falls back to `any` rather than selecting an arbitrary signature.
- Explicit `any`, unknown callees, missing catalog information, and unsupported overload ambiguity remain permissive and do not invent types.
- Receiver completion remains syntax-sensitive: `value.` offers fields/properties and native extensions, while `value:` offers methods. Union receivers expose only members valid for every alternative under the existing shared-member rule.
- Contextual typing changes compile-time analysis only and does not alter emitted Lua 5.1.

## Scope

- **In:** Nested function descriptors in `mta-types`, contextual argument checking, callback parameter binding, function-expression type recording, LSP symbol indexing, hover/completion parity, direct and grouped function-expression arguments, optional/union callback expectations, and regression tests.
- **Out:** Named function declarations inferred from later call sites, overload syntax, generic type inference, event-name-dependent callback signatures, callback return-type covariance changes, runtime validation, and API-specific completion branches.

## Architecture

```text
callable signature
       |
       v
expected argument type ----> contextual function type
       |                              |
       v                              v
check function body            bind parameter types
       |                              |
       +-------------> record FunctionExpression type
                                      |
                                      v
                              LSP symbol index
                                      |
                                      v
                         hover and member completion
```

The checker owns contextual typing. Call checking must resolve the callable signature before checking its arguments and pass each expected parameter type into expression checking. The recorded type for a `FunctionExpression` must contain the effective parameter types, allowing the existing LSP analysis and symbol index to reuse checker output without recreating call semantics.

## Acceptance Criteria

- [x] Given `function onPlayer(handler: fun(Player, string): void): void`, `onPlayer(function(player, command) ... end)` types `player` as `Player` and `command` as `string` without authored parameter annotations.
- [x] Every callback parameter represented as a function type by the pinned upstream MTA declarations remains a function descriptor in the generated catalog instead of degrading to `any`.
- [x] A generated MTA API callback receives the same contextual typing; `addCommandHandler` is covered as a regression example, not as a special case.
- [x] Completion after an inferred callback parameter offers only members valid for that receiver type and respects `.` versus `:` and the file environment.
- [x] Hover reports the inferred parameter type, and checker diagnostics use that same type inside the callback body.
- [x] Explicit callback parameter and return annotations retain current validation behavior and are never silently replaced by context.
- [x] Ambiguous or unavailable callback signatures degrade to `any` without false member suggestions or API-specific heuristics.
- [x] Generated Lua output is byte-identical for fixtures that differ only by contextual type information.
- [x] Existing compiler, MTA catalog, LSP, navigation, and completion suites remain green.

## Risks

- Checking a function body before the full callback signature is known can leave stale `any` entries. Resolve the expected signature first and check each function expression once.
- Server/client normalization can erase nested function details if descriptor merging is shallow. Cover nested descriptors directly in normalization tests.
- Parser recovery may produce incomplete calls while the user types. Missing or partial signatures must fall back to `any` and still build a valid symbol scope.
- Passing expected types through every expression can broaden the change unnecessarily. Limit propagation initially to call arguments and transparent grouping, then add other contextual positions under separate tests.
