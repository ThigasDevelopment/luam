# 47.05 - Fold Threads onto the promise scheduler

## Objective

Put both libraries on one yield protocol and one pulse timer, so a long slicing
job becomes awaitable and `await` inside a pool job stops being a silent no-op.

## Why both survive

They solve different problems and neither replaces the other.

`Threads` is a cooperative time-slicer: the work is CPU-bound and too long for
one frame, so a frame budget resumes N jobs per pulse. A promise is an async
completion: the work is waiting on something else, and the suspension is driven
by whatever settles it.

Promises alone cannot replace the slicer. Slicing with `await delay(0)` costs one
timer per slice and lands on MTA's 50ms floor — roughly 20 slices a second —
against a shared pulse with a frame budget, which is 150 at `normal` and 500 at
`high`. That is one to two orders of magnitude on the single problem MTA
resources hit most.

But leaving them side by side is a trap. The two drive coroutines with
incompatible resume payloads: `Threads:process` resumes with the `Thread` object,
the promise scheduler resumes with `(ok, ...)`. A coroutine can belong to only
one, so until they merge, `await` inside `threads:add(...)` is broken — and
broken quietly, because the guard added in 47.01 is the only thing that reports
it.

## Scope

- **In:** One scheduler, one pulse timer, one yield protocol. `add` and the
  `Async` iterators handing back a promise. The weak job table. Deprecation
  wording.
- **Out:** Removing anything. `Threads` and `Async` keep every method and every
  scheduling style.

## Steps

- [ ] Register a pool job's coroutine as a promise task and drive it from the
      promise scheduler's pulse. One timer for the runtime, not one per pool.
- [ ] Keep the frame budget and the three styles — `concurrent`, `priority`,
      `sequential`. The budget is the reason `Threads` still exists.
- [ ] Resume pool jobs with the promise protocol, so `await` and `sleep` behave
      identically inside and outside a pool.
- [ ] Return the job's promise as a **second** value: `local id, done = pool:add(fn)`.
      Existing single-assignment code keeps receiving the id, so nothing breaks,
      and `remove`, `pause` and `resume` keep taking the id.
- [ ] Do the same for `Async.map`, `Async.iterate` and `Async.foreach`, so
      `local id, done = runner:map(...)` lets a caller `await done`.
- [ ] Hold jobs weakly (`__mode = 'k'`). Today `self.threads[id]` is a strong
      reference and a paused job nobody resumes leaks for the resource's life.
- [ ] Read every resume result. A failing job rejects its promise instead of
      raising out of the timer callback, which is where the current
      `error('[Threads] Thread ... failed: ...')` lands.
- [ ] Confirm and fix `PRIORITIES.extreme`. It is `{ pulsing = 0, frame = 50 }`,
      and 0 is below MTA's documented 50ms floor, so `setTimer` should be
      returning false and `start()` never succeeding — every later `add()` would
      retry it. Verify on a running server before changing the numbers.
- [ ] Mark `Threads` and `Async` as the manual path in hover text and
      documentation, pointing at `async`/`await` for anything that waits. No
      removal and no diagnostic.

## Acceptance Criteria

- [ ] `await` and `sleep` behave the same inside a pool job as inside an async
      function.
- [ ] `local id = pool:add(fn)` still yields the id, and `pool:remove(id)`,
      `pause` and `resume` still work on it.
- [ ] `local id, done = pool:add(fn)` yields a promise that settles when the job
      finishes, and rejects with the reason when it fails.
- [ ] `await runner:map(...)` resumes after the whole iteration completes.
- [ ] One `setTimer` is live for the runtime regardless of how many pools exist.
- [ ] A paused job that is never resumed and never referenced is collected.
- [ ] A failing job rejects its promise; the timer callback does not raise.
- [ ] The frame budget still bounds work per pulse for each style, and
      `examples/framework/thread-pool.luam` compiles and runs unchanged.
