# 29.3 - Keep erased declarations visible as Lua comments

## Objective

Render a declaration that has no Lua form as a long-bracket comment over its original span in a development build, so a developer reading the generated file sees the contract instead of an unexplained gap.

## Context

Today an erasure is blanked: `sourceEdits` replaces every non-newline character in the span with nothing, which preserves the line count but discards the text. A declaration disappears entirely, leaving a gap with no explanation.

The rule applies to whole declarations only. An inline type annotation stays erased, because the generated signature should read as plain Lua:

```luam
type CustomType = string;

local function example (name: CustomType): void

end
```

```lua
--[[type CustomType = string;]]

local function example (name)

end
```

The semicolon is inside the comment, not after it. That composes with 29.1: once the erasure span absorbs the trailing semicolon, wrapping the span preserves the token in a development build and blanks it in a release build, and neither emits a bare semicolon.

Erasure spans nest. An annotation inside an interface body carries its own span inside the declaration span. The normalization already in `sourceEdits` sorts by start and then by descending end, drops a span contained in the previous one, and returns null on a partial overlap so the caller falls back to canonical emission. Nesting therefore needs no new rule, but it does need a test that locks the behavior.

## Scope

- **In:** Interface, type alias, declare, and event declarations, rendered as comments in development builds. Build directives too, added during execution: `#!client` had been the last compile-only form still blanked, and it now reads `--!client` in every build, since a directive is already a comment in the source and needs no wrapper.
- **Out:** Inline type annotations and return types, which stay erased in both modes. Any change to what these declarations mean: they remain compile-only and produce no runtime construct.

## Steps

### T-01 - Render an erased declaration as a comment

**Agent:** architecture-engineer

- [x] Replace the blanking replacement with a long-bracket comment wrapping the authored text, for declaration erasures only.
- [x] Reuse the bracket-padding logic in `commentReplacement`, widening the opening bracket with equals signs until the body cannot terminate it early.
- [x] Distinguish a declaration erasure from an annotation erasure, since both arrive as spans and only one is wrapped.

### T-02 - Keep the semicolon inside the comment

**Agent:** architecture-engineer

- [x] Build on 29.1: the semicolon that follows a declaration is part of the erasure span.
- [x] In development builds it is preserved inside the comment.
- [x] In release builds it stays blanked, so no bare semicolon is emitted.

### T-03 - Lock the nesting behavior

**Agent:** architecture-engineer

- [x] Test an interface whose body contains annotations, asserting the inner spans are dropped and only the declaration comment is emitted.
- [x] Test a multi-line type alias, asserting the comment spans exactly the lines the declaration spanned.
- [x] Test an erased body containing a line comment and one containing a block comment.
- [x] Test an erased body containing a closing long bracket, asserting the padding widens.
- [x] Confirm a partial overlap still falls back to canonical emission rather than producing broken output.

### T-04 - Verify release output is untouched

**Agent:** architecture-engineer

- [x] Assert that no release build contains a comment carrying source text.
- [x] Confirm the minifier is never asked to strip these comments, because they never reach it.

## Acceptance Criteria

- [x] A development build renders each erased declaration as a comment on its original lines, semicolon included.
- [x] An inline type annotation is erased in both modes, and a generated signature reads as plain Lua.
- [x] A nested erasure emits one comment, not two.
- [x] An erased body containing a closing long bracket produces a valid comment.
- [x] Line counts are identical between source, development output, and release output.
- [x] A release build is byte-identical to the output produced before this task.
- [x] `pnpm typecheck` and `pnpm test` pass.
