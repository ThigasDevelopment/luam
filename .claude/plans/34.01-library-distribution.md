# 34.01 - Design a distribution model for third-party Luam libraries

## Objective

Decide how a developer consumes Luam code someone else wrote, and record the
decision as an ADR. Today the answer is that they copy files.

## Scope

- **In:** An ADR proposing the model: what a shared library is, how a project
  declares it, where it comes from, and how the compiler and the checker see it.
- **Out:** Implementation. This plan produces a decision; the milestone that
  builds it comes after.
- **Out:** Running a registry. Whether Luam operates infrastructure is one of the
  questions the ADR answers, not a premise.

## Context

A Luam project has exactly one way to depend on code it did not write: the
resource export contract from ADR-033, documented in
[exports.md](../../docs/en/language/exports.md). That contract is real and it is
checked — a call into a declared dependency is verified against the provider's
contract when both names are literal. But it describes a *runtime* boundary
between two deployed MTA resources. It is not a way to obtain code.

There is no `luam add`, no manifest field naming an external package, and no
convention for publishing a library. A developer who writes a good pathfinding
module and wants to share it puts it on a forum, and the developer who wants it
copies the files in.

Three constraints bound every option:

- **The network contract.** `.claude/CLAUDE.md` allows the CLI one build-time
  call and `luam setup` one download; the compiler packages make none, and a
  build with no network must still succeed. Any model where fetching a
  dependency is a step inside `build` is out before it is evaluated.
- **MTA has no module system.** There is no `import` between files, and a
  resource is a flat set of scripts the server loads. A library is therefore
  either vendored into the consuming resource or deployed as its own resource and
  reached through exports — and those two have very different type stories.
- **Luam already has a manifest.** `.luam.manifest` is the project contract from
  milestone 23, and it is where a dependency would be declared.

The honest starting point is that npm may be the answer — the CLI already ships
through it — and the ADR should say so and evaluate it rather than inventing
infrastructure.

## Steps

### T-01 - Frame the options

**Agent:** architecture-engineer

- [ ] Write up each candidate: npm packages consumed by the CLI; git URLs
      resolved by a `luam add`; a vendored `libs/` directory with a lockfile; and
      the status quo of exports-only, which is a legitimate answer if the others
      cost more than they return.
- [ ] For each, state where the code lands, when it is fetched, whether the
      checker sees its types, and what happens on a machine with no network.
- [ ] State which of them require Luam to run infrastructure, and treat that as a
      cost rather than a detail.

### T-02 - Answer the type and environment questions

**Agent:** architecture-engineer

- [ ] Decide how a library's types reach the checker — shipped `.d.luam`
      declaration files, compiled-from-source, or both.
- [ ] Decide how a library declares its environment. A library that is `shared`,
      one that is `server`-only, and one that ships both halves are three
      different things, and the environment model resolves per file.
- [ ] Decide what a library may depend on, and whether transitive dependencies
      exist at all. A resolver is a large surface; deciding to have none is a
      valid answer that must be deliberate.
- [ ] Decide how a library's runtime helpers and native libraries interact with
      the consuming resource's `meta.xml` ordering.

### T-03 - Write the ADR

**Agent:** architecture-engineer

- [ ] Record the decision as the next ADR, in Nygard format, with the rejected
      options and why.
- [ ] State explicitly where in the workflow a fetch happens, and confirm it is
      never inside `build`.
- [ ] Sketch the milestone that would implement it, so the decision hands off to
      concrete work.

## Acceptance Criteria

- [ ] An ADR exists recording the model, the rejected alternatives, and the
      reasoning.
- [ ] The ADR states where dependency fetching happens and confirms a build with
      no network still succeeds.
- [ ] The ADR answers, for the chosen model: how types reach the checker, how the
      environment is declared, whether transitive dependencies exist, and how
      `meta.xml` ordering is preserved.
- [ ] The ADR says whether Luam operates any infrastructure, and if so what.
- [ ] The relationship to the export contract in ADR-033 is stated — whether this
      model replaces it, complements it, or is orthogonal to it.
- [ ] No code under `packages/` is modified by this task.
