# 34.01 - Design a distribution model for third-party Luam libraries

## Objective

Decide how a developer consumes Luam code someone else wrote, and record the
decision as an ADR. Today the answer is that they copy files.

## Scope

- **In:** An ADR proposing the model: what a shared library is, how a project
  declares it, where it comes from, and how the compiler and the checker see it.
- **Out:** Implementation. This plan produces a decision; the milestone that
  builds it comes after.
- **Out:** Running a registry. Whether Luam operates infrastructure is one of the
  questions the ADR answers, not a premise.

## Context

A Luam project has exactly one way to depend on code it did not write: the
resource export contract from ADR-033, documented in
[exports.md](../../docs/en/language/exports.md). That contract is real and it is
checked — a call into a declared dependency is verified against the provider's
contract when both names are literal. But it describes a *runtime* boundary
between two deployed MTA resources. It is not a way to obtain code.

There is no `luam add`, no manifest field naming an external package, and no
convention for publishing a library. A developer who writes a good pathfinding
module and wants to share it puts it on a forum, and the developer who wants it
copies the files in.

Three constraints bound every option:

- **The network contract.** `.claude/CLAUDE.md` allows the CLI one build-time
  call and `luam setup` one download; the compiler packages make none, and a
  build with no network must still succeed. Any model where fetching a
  dependency is a step inside `build` is out before it is evaluated.
- **MTA has no module system.** There is no `import` between files, and a
  resource is a flat set of scripts the server loads. A library is therefore
  either vendored into the consuming resource or deployed as its own resource and
  reached through exports — and those two have very different type stories.
- **Luam already has a manifest.** `.luam.manifest` is the project contract from
  milestone 23, and it is where a dependency would be declared.

The honest starting point is that npm may be the answer — the CLI already ships
through it — and the ADR should say so and evaluate it rather than inventing
infrastructure.

## Steps

### T-01 - Frame the options

**Agent:** architecture-engineer

- [x] Write up each candidate: npm packages consumed by the CLI; git URLs
      resolved by a `luam add`; a vendored `libs/` directory with a lockfile; and
      the status quo of exports-only, which is a legitimate answer if the others
      cost more than they return.
- [x] For each, state where the code lands, when it is fetched, whether the
      checker sees its types, and what happens on a machine with no network.
- [x] State which of them require Luam to run infrastructure, and treat that as a
      cost rather than a detail.

### T-02 - Answer the type and environment questions

**Agent:** architecture-engineer

- [x] Decide how a library's types reach the checker — shipped `.d.luam`
      declaration files, compiled-from-source, or both.
- [x] Decide how a library declares its environment. A library that is `shared`,
      one that is `server`-only, and one that ships both halves are three
      different things, and the environment model resolves per file.
- [x] Decide what a library may depend on, and whether transitive dependencies
      exist at all. A resolver is a large surface; deciding to have none is a
      valid answer that must be deliberate.
- [x] Decide how a library's runtime helpers and native libraries interact with
      the consuming resource's `meta.xml` ordering.

### T-03 - Write the ADR

**Agent:** architecture-engineer

- [x] Record the decision as the next ADR, in Nygard format, with the rejected
      options and why.
- [x] State explicitly where in the workflow a fetch happens, and confirm it is
      never inside `build`.
- [x] Sketch the milestone that would implement it, so the decision hands off to
      concrete work.

## Acceptance Criteria

- [x] An ADR exists recording the model, the rejected alternatives, and the
      reasoning.
- [x] The ADR states where dependency fetching happens and confirms a build with

- [x] The ADR answers, for the chosen model: how types reach the checker, how the

- [x] The ADR says whether Luam operates any infrastructure, and if so what.
- [x] The relationship to the export contract in ADR-033 is stated — whether this
      model replaces it, complements it, or is orthogonal to it.
- [x] No code under `packages/` is modified by this task.

## Outcome

The model is [ADR-038](../docs/adr/038-library-distribution.md): a Luam library
is an npm package, the package manager fetches it, and the compiler reads it
from `node_modules` and vendors it into the consuming resource.

What settled it is that every Luam developer already installs the CLI with
`npm install --global`, so npm's registry, version solver, lockfile and
integrity checking cost nothing to adopt, and none of them is the project's to
operate. Luam runs no infrastructure. Git URLs behind a `luam add`, a vendored
`libs/` with a lockfile, a registry the project hosts, and doing nothing are
recorded as rejected, each with its reason.

The four questions T-02 asked are answered in the ADR: types come from compiling
the library's own `.luam` source, with `.d.luam` for its verbatim Lua half; the
library declares its environment per file in its own `package.json` and the
consumer cannot reassign it; there is no transitive resolution, because Lua's
flat global namespace makes one impossible to resolve meaningfully, so a library
declares its requirements and the compiler names what is missing; and library
scripts are enumerated into `meta.xml` in a section after the runtime library,
ordered by the `libraries` array, with helper requirements folded into the set
the reference trigger of 31.01 already computes.

Fetching is `npm install`, a step a person runs. No build command touches the
network, the CLI's two allowed outbound calls are unchanged, and an offline
build with a populated `node_modules` is byte-identical.

The relationship to [ADR-033](../docs/adr/033-resource-export-abi.md) is
orthogonal: exports are a runtime boundary between two deployed resources, this
is a compile-time source boundary that ships the code inside one, and both stay.

No file under `packages/` was modified.
