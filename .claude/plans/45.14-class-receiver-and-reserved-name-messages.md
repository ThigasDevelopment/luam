# 45.14 - Say what a class receiver and a reserved parameter name really are

> File: `.claude/plans/45.14-class-receiver-and-reserved-name-messages.md`

## Objective

Fix two diagnostics that are correct about the defect and wrong about the remedy,
each of which cost more time in the port than the defect itself.

## Reproduction

**A class used as a receiver.** The class declares `connect` as an instance
method and no statics at all:

```luam
class RedisAdapter {
    connect = function (): boolean
        return true
    end
}

RedisAdapter:connect()
# check-static-receiver: Call the static member "connect" as "RedisAdapter.connect(...)".
# A class value has no "self" to pass.
```

`RedisAdapter.connect(...)` is not a call that works: `connect` is not static, and
the form the message prescribes reports `check-unknown-member` on the next run.
The actual remedy is to instantiate — `local adapter = new RedisAdapter()` — or,
where the author wanted a singleton, to give the instance its own global name.
Six occurrences in the port, all of them from the Lua idiom
`Adapter = new "Adapter"` where a class name and its single instance share one
name.

**A reserved word as a parameter name.** `type` is a Lua standard global and a
Luam keyword, and it is an ordinary parameter name in ported code:

```luam
class MarkersService {
    isMarkerType = function (marker: Marker, type: MarkerType): boolean
        return self.markers[marker].type == type
    end
}
# parse-unexpected-token: Expected identifier but found "type".
# ...and seven more, ending with the class member being dropped entirely.
```

The message names the token and not the rule, and the recovery drops the rest of
the member, so one keyword produces eight diagnostics and a `check-unknown-member`
in another file.

## Scope

- **In:** The text and the code of `check-static-receiver` when the named member
  is not static, the recovery and the message for a reserved word in a parameter
  or local position, and the diagnostics reference entries for both.
- **Out:** Making a reserved word legal as a parameter name — the reserved-word
  rule stands, and `docs/en/reference/keywords.md` records it. Any change to the
  static member rules from 24.06.

## Steps

- [x] Split the receiver diagnostic. When the member exists and is static, keep
      today's message. When the member exists and is an **instance** member, report
      a different code whose message says the receiver is the class itself and
      names the two ways out: instantiate with `new`, or read the member from a
      value of that class.
- [x] Name the singleton case explicitly in that message, since a class and its
      instance sharing a global name is the shape that produces it.
- [x] Change the reserved-word message to name the rule and the word:
      the word is reserved, it cannot name a parameter, and a property of the same
      name is still legal — which is why `marker.type` on the next line compiles.
- [x] Recover at the offending token instead of abandoning the member, so one
      reserved word produces one diagnostic and the surrounding class still
      registers its members.
- [x] Add a fixture asserting the cascade is gone: the reproduction reports one
      error, and the `check-unknown-member` it used to produce in another file
      does not appear.
- [x] Record both entries in the diagnostics reference.

## Acceptance Criteria

- [x] `RedisAdapter:connect()` reports a message that does not prescribe
      `RedisAdapter.connect(...)`, and following the message it does print
      compiles.
- [x] A genuinely static member called with `:` keeps today's message and code.
- [x] The `MarkersService` reproduction reports exactly one error.
- [x] The class still registers `isMarkerType`, so no other file reports
      `check-unknown-member`.
- [x] Both codes are documented with the reproduction.

## Outcome

The `MarkersService` reproduction reports **two** diagnostics, both
`parse-reserved-name`: one at the parameter and one at the read of `type` in the
body. The reserved-word rule stands — the plan puts making the word legal out of
scope — so a body that reads the parameter necessarily names the word a second
time. What is gone is the cascade: eight diagnostics became two, the member still
registers, and the `check-unknown-member` in another file no longer appears.
Reading a reserved word as a value used to be `parse-unexpected-token` with no
recovery; it is now `parse-reserved-name`, recovered, so nothing downstream
collapses.

`local export = 1`, `local class = 1`, `local enum = 3`, `local new = 2` and
`local interface = 4` all changed code from `parse-unexpected-token` to
`parse-reserved-name`. They are still errors; the message now names the rule.
