# 37.02 - Take type parameters on functions and methods

## Objective

Let a function declare its own type parameters, so a utility that works over any
element type is written once and stays checked, instead of being written per
type or typed `any`.

## Scope

- **In:** Type parameters on a function declaration, a function expression, a
  class method and an ambient `declare function`.
- **In:** Inference of the arguments at the call site, explicit type arguments at
  the call site, constraints, and erasure from every emitter.
- **Out:** Type parameters on a constructor. A class already declares its own
  parameters ([ADR-032](../docs/adr/032-erased-generic-classes.md)) and a
  constructor binds them; a second, method-level set on the same declaration is
  a separate question.
- **Out:** Variance. Type arguments keep comparing invariantly, as they do for
  classes today.
- **Out:** Higher-kinded parameters, defaulted parameters, and inference from a
  return position.

## Context

Type aliases have taken type parameters since the generic-alias work. Classes
gained them in [ADR-032](../docs/adr/032-erased-generic-classes.md). Functions
never did, and the parser says so:

```luam
function identity<T>(value: T): T
    return value
end
```

```text
parse-unexpected-token: Expected "(" but found "<".
```

`typeParameters` appears in exactly two places in the parser —
`packages/compiler/src/parser/statement.ts` for a type alias, and
`packages/compiler/src/parser/declarations.ts` for a class. A function
declaration goes straight from the name to the parameter list.

The practical cost lands on the code most worth checking. A `map`, a `filter`, a
`find` or a `first` has to be typed `any` in and `any` out, so the checker stops
exactly where a helper is reused most. It also caps
[38](38.01-libraries-manifest-domain.md): a library of utilities without generic
functions ships an untyped surface.

### Most of the machinery is already built

Four of the five pieces exist and are exported:

| Piece | Where | Today's caller |
|---|---|---|
| `parseTypeParameters` | `packages/compiler/src/parser/declarations.ts` | The class declaration path |
| `inferTypeArguments(typeParameters, parameters, args)` | `packages/compiler/src/checker/generic-class.ts` | `new Box(...)` with no explicit arguments |
| `substituteType(type, substitutions)` | `packages/compiler/src/checker/type-substitution.ts` | Member specialization on a class |
| `checkTypeConstraints(context, name, typeArguments, position)` | `packages/compiler/src/checker/generic-class.ts` | A class reference carrying arguments |

`parseTypeParameters` already handles `extends` constraints and already calls
`stream.eraseFrom(checkpoint)`, which is what makes a source-faithful build drop
the annotation. The one piece that does not exist is a place to put the result:
`FunctionType` in `packages/compiler/src/checker/types.ts` carries `parameters`,
`parameterNames`, `variadicType`, `minimumArguments`, `isVariadic` and
`returnType`, and nothing else.

This is the third case of the same feature, not a new one.

## Design

### Syntax

Type parameters sit between the name and the parameter list, matching the class
form:

```luam
function first<T>(list: table<number, T>): T?
    return list[1]
end

function pluck<T, U extends Element>(source: U, read: fun(U): T): T
    return read(source)
end
```

A function expression takes them after the `function` keyword. A method takes
them after the method name, and its parameters are distinct from the class's own
— a method on `Box<T>` may declare `<U>` and both are in scope in its body.

An explicit argument list at the call site uses the same brackets as a class
reference: `first<string>(names)`.

### Where the parameters live

`FunctionType` gains `typeParameters?: string[]` and
`typeConstraints?: (Type | null)[]`, both optional, so every existing
construction site and every existing comparison is untouched. A function type
with no parameters behaves exactly as it does today.

The parser records the names on the declaration node beside the existing
`parameters`, in the same shape `ClassDeclaration` already uses, so
`buildFunctionType` can carry them onto the type.

### Scope inside the body

A type parameter is a name that resolves in type position only, and only inside
the declaration that introduced it. The class path already needs this — a method
on `Box<T>` resolves `T` — so the work is confirming the same scope mechanism
covers a function's own parameters and nests correctly when a generic method sits
inside a generic class. Shadowing is the case to pin: a method declaring `<T>`
inside a class declaring `<T>` must resolve to the method's.

An unbound name in type position stays what it is today — a `named` type with no
registry entry, which is permissive. That is what keeps this change safe, and it
is the same property that kept [32.06](32.06-nominal-assignability.md) at zero
blast radius.

### Inference at the call site

`inferTypeArguments` already takes exactly the three inputs a call has: the
parameter names, the declared parameter types, and the argument types. The call
path in `packages/compiler/src/checker/callable.ts` gains one branch:

1. If the call carries explicit type arguments, use them, after
   `checkTypeConstraints`.
2. Otherwise call `inferTypeArguments` over the declared parameters and the
   argument types.
3. Substitute the resulting bindings into the parameter types before checking
   the arguments, and into the return type before handing it back.

Anything left unbound is `any`, which is what `new Box(...)` already does. This
is single-pass unification: a parameter appearing only in the return type is
`any` rather than an error, and that limitation is inherited from ADR-032 rather
than introduced here. It belongs in `limitations.md`.

### Erasure

Nothing about a generic function reaches the generated Lua. `parseTypeParameters`
already erases its own span, so the canonical emitter drops it for free; T-05
confirms the source-faithful emitter does too, since that pass reprints from the
token stream and an erased span is what it reads.

## Record

### T-01 - Parsing

`parseTypeParameters` and `parseTypeArguments` moved out of
`parser/declarations.ts` into a new `parser/type-parameters.ts`, because
`function-expression.ts` needed them and `declarations.ts` already imports from
it — sharing them the other way would have closed a cycle. `expression.ts`'s
private `parseNewTypeArguments` was the third copy of the same loop and is gone
with them.

Where they are read:

| Form | Where the brackets sit |
|---|---|
| `function identity<T>(...)` | After the name, before the parameter list |
| `local f = function <T>(...)` | After the `function` keyword |
| A class method | Through the function expression it is written as |
| A call | After the callee, before the argument list |

There is no `declare function` form in the language — an ambient function is
`declare name: fun(...)`. Type parameters on a `fun` **type annotation** are a
separate question about the annotation grammar and are not in this task.

**The `<` ambiguity.** `a < b` is a comparison and `a<b>(c)` is a generic call,
and one token of lookahead cannot tell them apart. `parseCallTypeArguments`
speculates: it parses a type argument list and keeps it **only if a `(` follows
immediately**; on a parse failure, or on any other following token, it rewinds.
`TokenStream` gained `speculate()`/`rewind()` for it, rolling back the index, the
erasure spans and the diagnostics together — `parseTypeAnnotation` can report
`parse-duplicate-key` without throwing, and a speculative report must not
survive.

The forms and how they resolve, each pinned by a test:

| Source | Read as |
|---|---|
| `if a < b then` | Comparison. `then` is not `(`. |
| `local c = a < b` | Comparison. End of expression is not `(`. |
| `a < tonumber('2')` | Comparison. `tonumber` parses as a type name, but the `(` follows `tonumber`, not a `>`. |
| `identity<string>('a')` | Generic call. |
| `a < b > (c)` | **Generic call.** Genuinely ambiguous; the generic reading wins. A chained comparison is not valid Lua anyway, so nothing correct is lost. |

### T-02 - The type

`FunctionType` gained `typeParameters?: string[]` and
`typeConstraints?: (Type | null)[]`, both optional. `createFunction` is unchanged
— an exported `applyTypeParameters` attaches them after the fact, so every
existing construction site and every existing comparison behaves exactly as
before.

`isAssignable` was **not** changed. Two function types still compare by their
erased shapes: parameter count, parameter types, return type. Comparing two
generic signatures for equivalence is out of scope, and comparing the erased
shapes is the answer that cannot be wrong in the permissive direction the rest of
the checker already takes.

### T-03 - Scope

A type parameter resolves through the machinery classes already use: an unbound
name in type position is a `named` type with no registry entry, which is
permissive, and `context.noteTypeParameters` records the names so
`reportUnknownTypes` does not warn. That is the whole of bringing them into
scope, and it is why the blast radius is zero.

Shadowing needed one real fix. A generic method inside a generic class is
specialized by `substituteType` with the **class's** bindings, which would have
rewritten the method's own `T`. `substituteType` now drops any substitution
shadowed by a function type's own `typeParameters` before descending, and carries
those parameters onto the substituted type so the call site can still bind them.
A method on `Box<T>` declaring `<T>` resolves to the method's.

### T-04 - The call site

`specializeCall` in the new `checker/generic-call.ts` runs inside
`checkSignature`, which is the single funnel every call already passes through —
a plain call, a method call, a native member, a constructor. It reads the
argument types `checkValueList` already produced, then:

1. Explicit type arguments, if the call carries them, after an arity check.
2. Otherwise `inferTypeArguments` over the declared parameters and the arguments.
3. Constraints, on whichever set resulted.
4. Substitution into the parameter types and the return type, and the specialized
   signature is what the count and assignability checks then see.

`checkTypeConstraints` was class-shaped — it looked up a `ClassInfo` to find the
parameters. The reporting half is now `reportConstraintViolations`, taking the
parameters and constraints directly; `checkTypeConstraints` is a thin caller.
The message gained an owner phrase: `on class "Box"` or `on Function "label"`.
No new diagnostic code was added — `check-generic-arity`,
`check-generic-constraint` and `check-type-mismatch` all keep their existing
meanings.

An unbound parameter is `any`, not an error. A call with type arguments on a
function that declares none is `check-generic-arity`.

**No second depth guard was added.** The class cap exists because a nested
*annotation* can be written arbitrarily deep, and `resolveAnnotation` already
applies it to an explicit type argument here. Substitution itself is one pass
over a type tree with no cycle to enter: the map sends a name to an
already-resolved type, and the shadowing filter removes a parameter before its
own body is walked.

### T-05 - Output

Erasure is free. `parseTypeParameters` and `parseTypeArguments` already call
`stream.eraseFrom`, which is what both emitters read. A generic function emits
byte-for-byte what the same function without its parameters emits, asserted in
both directions.

The **formatter was not a fixed point** and needed two rules in
`format/format-spacing.ts`:

- A type `>` now binds tight to a following `(`, so `identity<T>(` and
  `identity<number>(1)` keep their shape instead of gaining a space. This was
  already wrong for `new Box<number>(1)`; no corpus file had exercised it.
- A type `<` keeps its space after the `function` keyword, so an anonymous
  generic function is `function <T>(` — matching the `function (` the corpus
  already settled on — while `identity<T>` stays tight.

### T-06 - Editor

- **Hover shows the type parameters.** `signatureText` renders them, so a
  declaration reads `identity<T>(value: T): T` and a method reads
  `read<T>(value: T): T`. `typeToString` renders a generic function type as
  `fun<T>(T): T`.
- **Hover on a call shows the specialized type.** It already did: the checker
  records the substituted return type against the call expression.
- **Semantic tokens already classify a type parameter as a type.** In use
  position — `value: T`, `: T` — it is `type` with the `erased` modifier, the
  same as any other name in type position. The declaration bracket itself
  (`<T>` after the name) carries no token, which is exactly what `class Box<T>`
  and `type Nullable<T>` do today: `typeParameters` is a `string[]` with no
  recorded positions, so there is nothing to anchor a token to. Giving the three
  forms declaration-site tokens is one change to the AST shape all three share,
  and it belongs to whichever task decides to make it — not to this one, where
  it would leave functions inconsistent with classes either way.
- **Signature help does not specialize its parameter labels.** It resolves
  through `SignatureSource`, which is built from the symbol index's *rendered
  text* — `declaration.parameters` are strings, not types — and the call frame
  exposes argument **source text**, not argument types. Substituting into
  pre-rendered labels would be string surgery on a signature, and doing it
  properly means giving the signature path the declared `FunctionType` and the
  checked argument types at a partially-typed call. That is its own task. The
  label still names the parameters, so a reader can see what `T` binds from.

- [x] The compiler suite, `examples/` and `docs/snippets` pass unchanged.

## Out of Scope

- Variance, higher-kinded parameters, defaulted parameters.
- Inference from a return position or from a later argument, which single-pass
  unification cannot do. It is a documented limitation, inherited from ADR-032.
- Type parameters on a constructor.
- Structural equivalence of two generic signatures.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| `<` after a function name is ambiguous with a comparison in some call form | High | T-01 records every ambiguous form and resolves it with the checkpoint mechanism `parseTypeParameters` already uses |
| A generic method inside a generic class resolves the wrong parameter | Medium | T-03 pins shadowing explicitly, with a test |
| Substitution loops on a self-referential binding | Medium | T-04 reuses the depth cap ADR-032 established rather than adding a second guard |
| The source-faithful emitter leaves the brackets in | Medium | T-05 asserts byte-identical output in both layouts |
| Widening `FunctionType` churns comparison code | Low | Both fields optional; a function with none behaves exactly as today |
