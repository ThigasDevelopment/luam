# 45.02 - Accept the empty table literal for a map whose value is an element class

> File: `.claude/plans/45.02-empty-literal-element-map.md`

## Objective

Let `{}` initialise every map, so a field that indexes MTA elements can be
declared and then filled, which is how every registry in a real resource starts.

## Reproduction

Confirmed on the current tree:

```luam
local names: table<string, string> = {}      # accepted
local players: Player[] = {}                 # accepted
local byId: table<number, Player> = {}       # check-type-mismatch
local shapes: table<number, ColShape> = {}   # check-type-mismatch
```

The failing message is `Variable "byId" expects "table<number, Player>" but
received "{}"`. The same assignment inside a constructor produces the field form
of the message. `docs/en/language/types.md:293` documents
`local ages: table<string, number> = {}` as working, so the rule is not that maps
reject `{}` — only maps whose **value** type is an element class do.

The ported resource hit this four times: `table<number, ColShape>`,
`table<Vehicle, Vehicle>`, `table<number, Vehicle>` and the same shape inside
`GaragesService`.

## Root Cause

`isAssignable` lets an empty literal record reach an array, a map or `table`
(`packages/compiler/src/checker/types.ts`). The map arm compares the key and the
value types; the empty-literal shortcut is not reached, or is reached and then
overridden, when the value descriptor is an element class rather than a
primitive, a record or an interface. Confirm which of the two before changing
anything — the fix is different for each.

## Scope

- **In:** Assignability of an empty table literal to a map, in a variable
  declaration, a field initialiser, an assignment, an argument and a return.
- **Out:** A non-empty literal, which must keep comparing its shape. Arrays and
  `table`, which already work. Any change to how an element class is modelled.

## Steps

- [x] Write the failing case as a unit test first, with a matrix over the value
      type: primitive, record, interface, project class, element class, union.
      The matrix is the bug report.
- [x] Locate where the empty-literal shortcut stops applying and make it apply
      before the key/value comparison, so the value type is never consulted for an
      empty literal.
- [x] Do the same for the key type, so `table<Ped, number>` and
      `table<ColShape, Data>` are both reachable from `{}`.
- [x] Check the array arm for the same asymmetry: `ColShape[] = {}` must be
      accepted, and a test must say so.
- [x] Confirm the emitted Lua is unchanged — this is an assignability rule and
      touches no output.

## Acceptance Criteria

- [x] Every cell of the matrix accepts `{}`, in all five positions.
- [x] A non-empty literal that does not match the map still reports
      `check-type-mismatch`, with its current message.
- [x] The ported resource's four occurrences compile.
- [x] The emitter and manifest baselines are byte identical.

## Outcome

The value type was never the cause. `isMapAssignable` reached the `record` arm
for `{}` and required `string` to be assignable to the map's **key**, so every
map keyed by anything other than `string` rejected `{}` — the element-class value
types in the ported resource all happened to sit behind a `number` key. The
shortcut now runs first: `isEmptyLiteral(source)` accepts any map, exactly as the
array arm already did.
