# 40.01 - Add inlay hints to the language server

## Objective

Show what the checker inferred, inline, so a developer reading Luam can see the
types the annotations left implicit without hovering over every name.

## Scope

- **In:** Inlay hints for an inferred local type, an inferred function return
  type, an inferred parameter type in a contextually typed callback, and a
  parameter name at a call site.
- **In:** The settings that let a developer choose which of those they want, and
  the default.
- **Out:** Editing from a hint. Clicking a type hint to insert the annotation is
  a code action, and belongs with the quick fixes rather than here.
- **Out:** Hints in the manifest. A manifest field's type is already declared.

## Context

Milestone 32 delivered the two providers it set out to deliver — a formatter and
quick fixes — and excluded this one in writing:

> Inlay hints. The editor gains formatting and actions in this milestone; hints
> are a separate decision.

This is that decision. The case for it is stronger in Luam than in most typed
languages, because Luam erases everything: a type annotation exists only for the
checker, so a reader who wants to know what a local holds has no runtime artifact
and no generated declaration to look at. Hover answers one name at a time.

The server already computes every type a hint would show.
`packages/lsp/src/server/capabilities.ts` registers eleven providers — completion,
signature help, hover, definition, references, rename, document symbols, code
actions, workspace symbols, and formatting in both forms — and
`packages/lsp/src/features/hover.ts` already renders a type for a position through
the same `typeToString` a hint needs. The feature is a new provider over an
existing analysis, not a new analysis.

## Design

### Four hint kinds

| Kind | Shown where | Example |
|---|---|---|
| Local type | A `local` with an initializer and no annotation | `local count` → `: number` |
| Return type | A function with no return annotation | `function total()` → `: number` |
| Callback parameter | A parameter typed by context, per [milestone 26](../docs/roadmap.md) | `function (player)` → `: Player` |
| Parameter name | A call argument that is a literal | `setTimer(fn, 1000, 0)` → `interval:`, `repeats:` |

The third is the one most specific to this project. Contextual callback typing
gives an event handler's parameters types the developer never wrote, and there is
currently no way to see them except by hovering each one. It is the highest-value
kind here and should not be an afterthought in the ordering.

The fourth is the one most likely to be noise. `parameterNames` exists on
`FunctionType` — milestone 32 widened it to `(string | null)[]` for exactly this
kind of use — so the data is there, but a hint on every argument of every call
makes dense code unreadable. Restricting it to literal arguments is the standard
answer and the one T-01 should confirm.

### Defaults

Hints are display, and a wrong default is an annoyance every user has to turn
off. T-01 decides the default per kind; the recommendation is that the three type
kinds are on and parameter names are off, because the first three show what was
inferred and the fourth restates what the reader can already look up.

The settings live where the extension's other settings live and must be readable
by a server that a different editor started, so they belong in the LSP
initialization options rather than in anything VS Code specific.

### What must not be shown

A hint that says `any` is worse than no hint: it takes space to report that the
checker knows nothing. Suppress it, and record that as a rule rather than as an
oversight.

A hint on a line the developer is editing should not shift text under the cursor.
That is the editor's concern, not the server's, but T-03 should confirm the
behaviour in the real extension rather than assume it.

### Cost

Hints are requested per visible range, on every scroll. The server must answer
from the analysis it already holds for the document and must not recompile. If
answering a range means a fresh check, the feature is a performance problem
disguised as a nicety — T-02 confirms the cache is enough before the provider
ships, the same way workspace symbols were required to answer from the existing
index.

## Record

### T-01 - The kinds, the defaults and the limits

- **The four kinds are confirmed, and the implementation order was local type,
  return type, callback parameter, parameter name.** The first three share one
  code path — an offset, a `Type`, and `typeToString` — so they landed together;
  the fourth is the only one that reads names rather than types.
- **The defaults are the three type kinds on and parameter names off**, as
  recommended. `DEFAULT_INLAY_HINT_SETTINGS` in
  `packages/lsp/src/features/inlay-hint-settings.ts` is the single source, and the
  VS Code contributions in `packages/vscode/package.json` repeat it; a test asserts
  the two agree.
- **The settings live in the LSP initialization options**, under an
  `inlayHints` object with one boolean per kind. Every field is optional and a
  non-boolean falls back to the default, so a client that sends `{}`, sends
  nothing, or sends garbage gets the defaults rather than an error. The VS Code
  extension maps `luam.inlayHints.*` onto that object and restarts the server when
  one of them changes, because the server reads the options once on connect.
- **Parameter-name hints are limited to literal arguments** — `nil`, a boolean, a
  number and a string literal. A template literal is not one: it can be long and
  it already reads as a value. A method call (`a:b(x)`) gets no name hints at all,
  because its callee type is the receiver rather than the function.
- **An `any` hint is suppressed**, and so is a type that renders as the empty
  string. The rule lives in one place, `typeLabel`, so no kind can bypass it.

### T-02 - Answering from the existing analysis

- A hint request reads `analysis.types`, `analysis.declarations` and
  `analysis.tokens` from the `DocumentAnalysis` the workspace index already holds.
  Nothing in the provider parses or checks. The test asserts the analysis object is
  **identical by reference** before and after a request, which a recompile could
  not be.
- **Measured**, 100 requests per figure, whole document, every kind on:
  `packages/compiler/tests/fixtures/mta-api/src/shared/world-tools.luam` — the
  largest fixture, 51 lines, 27 hints — takes **0.118 ms** per request; a synthetic
  2000-line document with 1999 hints takes **1.681 ms**. The suite keeps a 50 ms
  ceiling on a 400-line document so a regression that reintroduced a compile would
  fail rather than merely be slow.
- The parenthesis index that locates the end of a parameter list is built once per
  request from the token stream and searched by bisection, so the walk stays linear
  in the size of the document.

### T-03 - What was built

- `inlayHintProvider` is registered in `capabilities.ts`, the server answers
  `textDocument/inlayHint` over `LanguageService.inlayHints`, and
  `LanguageService.useInlayHints` holds the settings the client sent.
- `inlay-hints.ts` walks the program once and emits through `inlay-hint-kinds.ts`;
  a hint outside the requested range is dropped rather than never produced, which
  keeps the walk simple and still answers only for the range.
- The return-type kind covers a function declaration, a function expression and a
  class method. A constructor is excluded: its return type is the class, and saying
  so adds nothing.
- Parameter names come from `FunctionType.parameterNames` for a project function
  and, when the checker has none, from the MTA catalog documentation, so
  `setTimer(tick, 1000, 0)` reads `timeInterval:` and `timesToExecute:` — the
  wiki's own names.
- A manifest yields no hints, and a file with any `lex-` or `parse-` diagnostic
  yields none either, matching the rule formatting follows.
- **The packaged extension is bundled but not yet installed.** `pnpm --filter luam
  bundle` emits a `dist/server/luam-lsp.cjs` carrying `inlayHintProvider` and an
  `extension.cjs` carrying the four `luam.inlayHints.*` switches, so the bundle is
  verified. Packaging the VSIX and reinstalling it into the maintainer's editor is
  the one box left open: it replaces the extension they are working in, so it waits
  for them to ask.
