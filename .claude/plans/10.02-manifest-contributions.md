# 10.02 - Carry manifest contributions through the pipeline and emit `<export>`

> File: `.claude/plans/10.02-manifest-contributions.md`
> Overlaps 9.1, which reorders `manifestScripts`. Land 9.1 first or the manifest
> snapshots are rewritten twice.

## Objective

Turn the exports a module declares into `<export>` entries in the generated
`meta.xml`, through a contribution channel that the next directive reuses
without touching anything between the parser and the manifest.

## Scope

- **In:** The contribution type, `CompiledModule` and the project cache,
  cross-module validation, `<export>` in `generateManifest`, manifest ordering.
- **Out:** The `export` syntax itself (10.1), `setting` and `depends` (10.3).

## Steps

- [x] Define `ManifestContribution` as a discriminated union in
      `project/manifest.ts`, with `export` as its only member for now, and keep
      the union open for the kinds 10.3 adds.
- [x] Add `contributions: ManifestContribution[]` to `CompiledModule` in
      `project/module.ts`, mapped from `CompileResult.exports` in
      `compileModule`.
- [x] Expand a shared-file export into two contributions, `server` and
      `client`, at the point of mapping — the manifest layer receives an
      already-resolved environment.
- [x] Verify the module cache in `project-cache.ts` round-trips contributions:
      a rebuild in which every module is reused must still produce the full
      manifest, since `assembleResource` runs on every build.
- [x] Validate duplicates in `module-graph.ts` beside the existing global check
      and report `project-duplicate-export` when two modules export the same
      name for the same environment. MTA keeps one and drops the other with no
      warning.
- [x] Add `exportElement` to `project/manifest.ts` and place exports after the
      scripts and before the files, sorted by name then environment.
- [x] Escape the function name through the existing `escapeXml`.
- [x] Thread contributions into `assembleResource` in `project/resource.ts`,
      collecting from `project.modules` the way `collectHelpers` already does.
- [x] Confirm `packages/cli/src/build/build-runner.ts` needs no change — it
      consumes `assembly.build.manifest`.
- [x] Record the manifest element order in
      [architecture](../docs/architecture.md).

## Acceptance Criteria

- [x] An exported function in `src/server/main.luam` produces
      `<export function="f" type="server" />` in `build/meta.xml`.
- [x] The same function in `src/client` produces `type="client"`, and in
      `src/shared` produces two entries, one per side.
- [x] Renaming an unrelated source file does not change the export section of
      the manifest.
- [x] Two modules exporting the same name for the same side report
      `project-duplicate-export`, and no manifest is written.
- [x] The same name exported once from a server file and once from a client file
      is accepted, since MTA scopes an export by side.
- [x] A second build with an unchanged project reuses every module and still
      writes a manifest identical to the first.
- [x] `luam build` on a project with no exports produces a manifest byte
      identical to the one it produced before this task.
