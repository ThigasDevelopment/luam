# 39.04 - Enforce the source conventions in the pipeline

## Objective

Close the enforcement gap milestone 36 deferred, so `code-conventions.md` is
checked by a gate rather than by a reviewer's memory.

## Scope

- **In:** A conventions check in the merge gate, composed from the reusable
  workflow units milestone 36 extracted, covering the `.luam` corpus through
  `luam format --check` and the TypeScript sources through whatever T-01
  selects.
- **Out:** Changing any convention. The rules in `code-conventions.md` are the
  input, not the question.
- **Out:** Reformatting the TypeScript workspace as part of this task, if T-01
  selects a tool that would. That is its own change with its own review.

## Context

Milestone 36 deferred this in writing:

> Automated enforcement of the source conventions. The workspace has no linter
> or formatter, so `code-conventions.md` — kebab-case, single quotes, the line
> and file limits — is enforced only by review. Adding one is a new gate rather
> than a reorganization of an existing pipeline, and it belongs to its own task.

This is that task. One half of it stopped being a question when
[39.01](39.01-format-command.md) shipped `luam format --check`: the `.luam` corpus
gains an enforceable, idempotent standard with a command that exits `1` when a
file differs.

The other half — the TypeScript in `packages/` and `tools/` — has no tool at all.
The workspace's devDependencies are `esbuild`, `typescript`, `vitepress` and
`vitest`. Nothing checks kebab-case filenames, single quotes, the 175-character
line limit or the 250-line file limit.

The pipeline this plugs into is already written. Milestone 36 extracted
`unit-typecheck.yml`, `unit-test.yml`, `unit-build.yml` and `unit-docs.yml` as
`workflow_call` units that `ci.yml`, the release path and a fork run all compose,
and `@luam/pipeline` asserts that every required check name resolves to a job
that reports. A new gate job is a new unit plus a ruleset update, and the suite
will fail if the two disagree — which is the property that makes this safe to add.

## Design

### Two halves, one job

One `unit-conventions.yml` reporting as a single check, running both halves. A
contributor sees one red check, not two, and the required-check set in
`.github/rulesets/main.json` grows by one name.

### The `.luam` half

`luam format --check` over the repository's own corpus: `docs/snippets`,
`examples/`, the compiler fixtures. It exits `1` on any file that differs, and
39.01 T-04 already asserts the corpus is a fixed point, so this passes on the day
it lands.

[39.05](39.05-formatter-configuration.md) makes the style a project choice
through a `.luam.formatter` file, which does not weaken this gate: **this
repository sets no such file and keeps the milestone 32 defaults**, so
`--check` here means what it means today. The gate asserts that this
repository's own corpus is formatted, not that every Luam project shares one
style. T-02 should commit to that in writing, because a reader who sees the
formatter become configurable will reasonably ask whether the gate still
decides anything.

### The TypeScript half

T-01 chooses between two shapes, and records the rejection:

1. **A conventions script in `tools/`.** Reads `code-conventions.md`'s
   mechanical rules and asserts them: kebab-case file names, the line limit, the
   file limit, single quotes. No new dependency, no reformatting, no opinions the
   project did not already write down. It checks exactly the rules that exist.
2. **A standard linter and formatter.** More coverage, at the cost of a
   dependency, a configuration file, an opinion set that will disagree with the
   codebase somewhere, and a reformatting commit touching every file.

Option 1 is the recommendation. The conventions are already written and already
mechanical; a tool that enforces them is a script, and one that brings its own
opinions is a negotiation. Option 2 is recorded so the rejection is on the
record, and so a future task that wants broader coverage knows what it is
choosing.

Either way the check must be reproducible locally from `CONTRIBUTING.md`, which
milestone 36 made a requirement of every required check.

### The ruleset

`.github/rulesets/main.json` currently requires five checks. This adds a sixth.
Two constraints from milestone 36 apply unchanged: the check must report on every
pull request, so it cannot be path-filtered; and it must be one a fork run can
satisfy, so it needs no secret and no write token. Both are asserted by
`@luam/pipeline`, and the ruleset file and the live ruleset have to move together
— the live rulesets were applied from those files verbatim.

## Steps

### T-01 - Choose the TypeScript half

**Agent:** github-engineer

- [ ] Choose between the conventions script and a standard linter, and record the
      rejected option with its reasoning.
- [ ] Enumerate which rules in `code-conventions.md` are mechanically checkable
      and which stay a review matter, so the gate's coverage is stated rather
      than assumed.
- [ ] Confirm the choice adds no network dependency to a build.

### T-02 - Write the check

**Agent:** github-engineer

- [ ] Implement the chosen check.
- [ ] Fix every existing violation it finds, in its own commit, separate from the
      commit that turns the gate on.
- [ ] Confirm it runs from a clean checkout with no secret.
- [ ] Record that this repository sets no `.luam.formatter` and keeps the
      milestone 32 defaults, so the gate asserts its own corpus is formatted
      rather than asserting a style on every Luam project. State what would have
      to change if this repository ever added one.

### T-03 - Add the workflow unit

**Agent:** github-engineer

**Files:** `.github/workflows/unit-conventions.yml`, `.github/workflows/ci.yml`

- [ ] Add the unit as a `workflow_call` job, following the shape of the four
      existing units.
- [ ] Declare its permissions explicitly and pin every third-party action to a
      commit SHA.
- [ ] Compose it into `ci.yml` beside `typecheck` and the test matrix, with no
      path filter.
- [ ] Confirm it is reachable from a fork run with a read-only token.

### T-04 - Require it

**Agent:** github-engineer

- [ ] Add the check name to `.github/rulesets/main.json`.
- [ ] Confirm `@luam/pipeline` passes: the name resolves to a job that reports,
      no permission budget is exceeded, no action is unpinned.
- [ ] Update the live `main` ruleset from the file, so the committed JSON and
      what GitHub enforces stay the same text.
- [ ] Confirm a green pull request stays green and a deliberate violation turns
      it red.

### T-05 - Document it

**Agent:** github-engineer

- [ ] Add the command to `CONTRIBUTING.md` so a contributor reproduces the check
      locally.
- [ ] State in `code-conventions.md` which rules the gate enforces and which
      remain a review matter.

## Acceptance Criteria

- [ ] A pull request violating a mechanical convention fails the gate, proven by
      a deliberate violation.
- [ ] A conforming pull request passes.
- [ ] The check reports on every pull request, with no path filter.
- [ ] A fork run satisfies it with a read-only token and no secret.
- [ ] `@luam/pipeline` passes, and the required-check names in the file match the
      jobs that report.
- [ ] The committed ruleset and the live ruleset are the same text.
- [ ] `CONTRIBUTING.md` names the command that reproduces it locally.
- [ ] `code-conventions.md` states the gate's coverage and its limits.

## Out of Scope

- Changing any convention.
- Broader static analysis than the conventions the project has written down.
- Auto-fixing in CI. The gate reports; the developer fixes.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A required check that a fork cannot satisfy blocks every outside contribution | High | T-03 confirms fork reachability; `@luam/pipeline` asserts it |
| A path-filtered check is held pending and blocks unrelated pull requests | High | No path filter, which is the rule milestone 36 established for exactly this reason |
| A linter's opinions force a reformatting commit across the workspace | Medium | T-01 recommends the script; if a linter is chosen, T-02 separates the fix commit from the gate commit |
| The ruleset file and the live ruleset drift | Medium | T-04 updates the live one from the file, as 36.08 did |
