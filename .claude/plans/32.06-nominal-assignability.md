# 32.06 - Check assignability against interfaces and classes

## Objective

Make a value checked against an `interface` or a `class` produce the same
diagnostics a `type` alias already produces, so a declared return type, a typed
local and a typed parameter mean the same thing whichever way the type was
declared.

## Scope

- **In:** The nominal branch of `isAssignable`, the expansion of a `named` type
  to the members the declaration registry already holds, and the three positions
  that expansion reaches — return values, variable initialisers, and call
  arguments.
- **In:** The `AssignabilityOptions` shape, which today carries no way to reach a
  declaration.
- **Out:** Member *access* on a nominal value. `memberOf` already resolves it and
  already reports `check-unknown-member`; nothing here changes that path.
- **Out:** Narrowing, discriminated unions and flow analysis over nominal types.
  They consume `isAssignable` and inherit whatever it decides.
- **Out:** Generic variance beyond the invariant argument comparison
  `isNamedAssignable` performs today.

## Context

Assignability against a nominal type is a no-op. `packages/compiler/src/checker/types.ts`
closes the nominal branch with an unconditional escape hatch:

```ts
if (source.kind === 'named' && target.kind === 'named') {
    return isNamedAssignable(source, target, options);
}

if (source.kind === 'named' || target.kind === 'named') {
    return true;
}
```

`isNamedAssignable` is no stricter: it opens with
`source.name !== target.name || sourceArguments.length === 0` and returns `true`,
so two unrelated nominal types are mutually assignable unless both carry matching
generic arity.

A `type` alias escapes this because `resolveNamedAnnotation` in
`packages/compiler/src/checker/context.ts` resolves an alias through
`substituteType(alias.type, substitutions)` and yields a structural `record`. An
`interface` or a `class` has no alias entry, falls through to
`resolveClassAnnotation`, and yields a `named`. The declaration is checked; every
use of it is not.

Compiling the following against the current checker produces the diagnostic in
the first two cases and nothing in the third:

```luam
function example (): string
    return 1;
end

type ReturnFunction = { name: string }
function example (): ReturnFunction
    return 'wrong';
end

interface ReturnFunction {
    name: string;
}
function example (): ReturnFunction
    return 'wrong';
end
```

The same silence covers `local value: ReturnFunction = 'wrong'` and passing
`'wrong'` to a parameter annotated `ReturnFunction`, and it covers a `class` in
place of the interface. Returning `{ other = 1 }` where the interface requires
`name: string` is silent too.

This is the mirror of [32.01](32.01-method-call-checking.md). That task found
method calls checked on a nominal receiver and unchecked on a structural one;
this one finds assignability checked on a structural type and unchecked on a
nominal one. The two do not overlap in code — 32.01 changed member resolution in
`expressions.ts`, this changes `isAssignable` in `types.ts` — but 32.01 should
land first, because its tests pin the nominal method-call behaviour that must
stay unchanged here.

### The constraint that shapes the work

`isAssignable` is a pure function over `Type`. `AssignabilityOptions` is
`{ allowNil: boolean }` and nothing more. Expanding a `named` type to its members
requires the declaration registry, and the registry is reachable only from
`CheckContext`. There are 24 call sites across `packages/compiler/src` plus
`packages/lsp/src/features/argument-expectation.ts`, so how the registry reaches
`isAssignable` is the first design decision, not an implementation detail.

## Design

### Three kinds of `named`, three behaviours

A `named` type reaching `isAssignable` is one of three things, and they must not
be treated alike.

| Origin | Behaviour |
|---|---|
| `interface` in the registry | Structural. Expand to its members, including `extends` parents, and compare as a record. |
| `class` in the registry | Nominal. Assignable only from itself or a subclass, or from a type that satisfies its declared `implements` contract. |
| Not in the registry | Permissive. Return `true`, exactly as today. |

The third row is what keeps this change safe. MTA element types, ambient
declarations and any name the checker never resolved all arrive as `named` with
no registry entry, and `noteUnknownType` already records them for a separate
diagnostic. They must keep passing, or every resource that touches the MTA
surface stops compiling.

Interfaces are structural because that is what an interface means in the
languages Luam is inspired by, and because `collectInterfaceContract` already
produces exactly the member list a structural comparison needs. Classes stay
nominal because a class carries identity that its member list does not: two
classes with identical members are not interchangeable, `superClass` defines a
subtype relation the member list cannot express, and `implements` is the
declared, checked bridge between a class and an interface. Making classes
structural would also silently widen `check-unimplemented-interface`, which
`class-contracts.ts` reports today on the strength of that declaration.

### Expanding a nominal type

`DeclarationRegistry` already exposes the two primitives:

- `collectInterfaceContract(name)` — an interface's members including
  `superInterfaces`.
- `collectMembers(name)` — a class's members including its `superClass` chain.

Both walk their parent chains. Neither should be re-implemented, and no second
member table should be introduced.

Recursion is the hazard. `interface Node { next: Node }` expands to a member
whose type is the interface being expanded. The comparison must carry a visited
set keyed by the pair of type names under comparison and return `true` on a
repeat, which is the standard co-inductive answer and matches how
`interfaceExtends` and `lookupClassMember` already guard themselves with
`visited`.

### Reaching the registry

Two options, to be decided in T-01 and recorded in the plan before T-02 starts:

1. Add an optional resolver to `AssignabilityOptions` —
   `resolveNamed?: (name: string) => Type | null` — populated by `CheckContext`
   and absent everywhere else. Call sites that omit it get today's permissive
   behaviour, which means the LSP's `argument-expectation.ts` degrades rather
   than breaks.
2. Set a module-level resolver when a check begins. Cheaper to write and wrong
   for a language server holding several documents.

Option 1 is the recommendation. Option 2 is recorded only so the rejection is on
the record.

**Decided:** option 1. `AssignabilityOptions` gained
`resolveNominal?: (name: string) => NominalShape | null` and
`visited?: ReadonlySet<string>`, both optional. `CheckContext.assignability()`
populates the resolver from `DeclarationRegistry`; the four call sites that pass
options without one — `class-contracts.ts`, `classes.ts`, `generic-class.ts` —
and every site that passes none keep today's permissive behaviour, which is
correct for all of them: they compare members that are already resolved.
`packages/lsp/src/features/argument-expectation.ts` passes no options and
degrades to the permissive answer, which is the pre-milestone behaviour rather
than a wrong one.

### Diagnostics

No new code. The existing ones already carry the right meaning and the right
wording:

- `check-type-mismatch` — the value does not satisfy the nominal type. Emitted
  through `expectAssignable`, so `Return value expects "ReturnFunction" but
  received "string".` follows automatically from `typeToString`.
- `check-unimplemented-interface` — unchanged, still reported from
  `class-contracts.ts` on the declaration.

A record that is missing a member, or carries one at the wrong type, should say
which member. `typeToString` on a `named` prints only the name, so the message
would otherwise be `expects "ReturnFunction" but received "{ other: number }"`
and leave the reader to diff two shapes by eye. Whether that needs a second
message form is a T-03 decision, not a new diagnostic code.

## Steps

### T-01 - Decide and record how the registry reaches assignability

**Agent:** architecture-engineer

- [ ] Choose between the resolver-in-options and module-level-resolver designs,
      and record the choice and the rejected alternative in this plan.
- [ ] Confirm every one of the 24 `isAssignable` call sites either supplies a
      resolver or is correct without one, naming the ones that are not.
- [ ] Confirm `packages/lsp/src/features/argument-expectation.ts` behaves
      sensibly with no resolver, since the LSP builds its own context.

### T-02 - Measure the blast radius before changing behaviour

**Agent:** architecture-engineer

- [ ] Run the compiler suite against a probe build that rejects only the
      clearest case — a `named` against a primitive, a literal, a `function`, a
      `thread` or a `userdata` — and record every failure.
- [ ] Baseline already taken: **4 failing tests of 1217, in 3 files of 57.**
      `tests/catalog-coverage.test.ts` (one MTA API declared to return a
      `boolean` where the catalog produces `Ban`),
      `tests/event-calls.test.ts` (latent trigger form selection), and two in
      `tests/generic-classes.test.ts` (a parent pinned to a concrete argument).
- [ ] Extend the probe to full structural interface expansion and re-measure,
      since the figure above covers only the primitive case.
- [ ] Decide, on the second measurement, between fixing the fallout outright and
      a staged rollout. Fix outright if the count stays in this range; the four
      failures above read as genuine type errors the escape hatch was hiding, not
      as false positives.
- [ ] Do not introduce a strictness flag. A second checking mode is a permanent
      cost paid to avoid a one-time fix, and nothing in the measurement so far
      justifies it.

### T-03 - Expand interfaces structurally

**Agent:** architecture-engineer

**Files:** `packages/compiler/src/checker/types.ts`,
`packages/compiler/src/checker/context.ts`

- [ ] Replace the unconditional escape hatch with the three-way split, keeping
      the unresolved-name case returning `true`.
- [ ] Expand a registry interface through `collectInterfaceContract` and compare
      it as a record, with a visited set guarding recursive members.
- [ ] Keep `isNamedAssignable` for the interface-to-interface case, but make a
      name mismatch fall through to structural comparison instead of returning
      `true`.
- [ ] Decide whether a mismatched record needs a message naming the offending

### T-04 - Keep classes nominal

**Agent:** architecture-engineer

**Files:** `packages/compiler/src/checker/types.ts`

- [ ] A class is assignable to a class only through the `superClass` chain.
- [ ] A class is assignable to an interface when its declared `interfaces` list
      names that interface, directly or through `interfaceExtends`.
- [ ] An interface is not assignable to a class.
- [ ] Confirm `class-contracts.ts` reports exactly what it reports today.

## Acceptance Criteria

- [ ] `function example(): ReturnFunction return 'wrong' end`, with
      `ReturnFunction` declared as an `interface`, reports `check-type-mismatch`
      with the same wording the `type` alias form reports today.
- [ ] The same holds for a local initialiser and a call argument.
- [ ] A record literal satisfying the interface reports nothing.
- [ ] A `named` type with no registry entry reports nothing, in every position.
- [ ] A subclass assigned to its parent reports nothing; two unrelated classes
      report `check-type-mismatch`.
- [ ] A recursive interface compiles without hanging.
- [ ] The compiler suite passes, with every changed expectation individually
      justified in the T-05 record.
- [ ] `docs/en/language/types.md` and `docs/pt-br/language/types.md` state the
      interface-structural, class-nominal rule.

## Out of Scope

- Structural comparison of classes. Recorded as decided against, not deferred.
- A strictness flag or a second checking mode.
- Generic variance. `isNamedAssignable` keeps comparing type arguments
  invariantly.
- The `check-unknown-member` path, owned by `memberOf`.
- Method-call checking on a structural receiver, which is
  [32.01](32.01-method-call-checking.md).

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The full structural expansion surfaces far more than the 4 failures the primitive probe found | High | T-02 re-measures before T-03 changes behaviour; the decision to fix outright is conditional on that second number |
| The generated MTA catalog carries wrong annotations the escape hatch was hiding | Medium | T-05 attributes each one; a catalog error routes to the generator, and the checker change is not blocked on it |
| A recursive interface makes expansion loop | Medium | Visited set keyed on the compared pair, matching `interfaceExtends` and `lookupClassMember` |
| The LSP builds a context without a resolver and silently loses diagnostics the CLI reports | Medium | T-01 names `argument-expectation.ts` explicitly; absent resolver degrades to today's behaviour rather than to a wrong answer |
| Threading a resolver through 24 call sites churns unrelated code | Low | Optional field on `AssignabilityOptions`; call sites that do not care are untouched |
