# 38.03 - Report global collisions and missing library requirements

## Objective

Make the two failure modes a flat global namespace produces loud at compile time
instead of mysterious at run time: two libraries claiming one name, and a library
whose declared requirement the consumer never listed.

## Scope

- **In:** Collision reporting across libraries and between a library and the
  project, the missing-requirement diagnostic, and the wording that makes both
  actionable.
- **Out:** Resolving either one. ADR-038 decided that last-write-wins is the
  failure mode this model has to own and that the answer is a diagnostic, not a
  namespace, an alias or a rename.
- **Out:** Walking the requirement graph. A requirement is reported, never
  installed and never followed.

## Context

Every top-level name a library declares becomes a global in the consuming
resource. Lua 5.1 has one flat namespace per side, so two libraries that both
declare `List` produce a resource where one silently wins, and which one depends
on script order. ADR-038 names this explicitly: collisions are reported, not
resolved.

The mechanism already exists for the project's own files.
`validateContributions` in `packages/compiler/src/project/module-graph.ts` walks
every module's contributions, keys them by `<side>:<name>`, and reports a
conflict against the first owner it recorded. It already handles the
side-sensitivity a `shared` contribution needs, through `occupiedSides`.

So this task is mostly about what the diagnostic says, not about how the
collision is found. A message that names two paths inside `node_modules` is a
message the developer cannot act on. It has to name both packages, the name they
both claim, and the side.

The requirement half has no existing mechanism. `requires` is read by
[38.01](38.01-libraries-manifest-domain.md) and never walked; this task compares
the declared requirements of the resolved set against the resolved set itself and
reports what is absent.

## Design

### Three collision shapes, one diagnostic each

| Shape | Reported against |
|---|---|
| Two libraries claim one name on one side | Both packages, the name, the side. |
| A library and a project file claim one name | The package and the project file. |
| A library claims a name the MTA catalog defines | Decided in T-01. |

The third row is the open one. A library declaring `getPlayerName` shadows the
MTA API for the whole resource, which is either a legitimate wrapper or a
disaster, and the checker cannot tell which. Decide in T-01 whether that is an
error, a warning, or permitted in silence, and record the reasoning. Prefer a
warning: it is loud enough to be seen and quiet enough not to block a library
that shadows deliberately.

The second row deserves a note on direction. The project is the thing being
built; a library is what it pulled in. When they collide, the message should read
as the library intruding on the project rather than the reverse, whichever module
the walk happened to record first. That means `validateContributions` cannot
simply report against "the first owner" once library modules are in the list —
T-02 fixes the ordering so the message is stable and reads correctly.

### The requirement diagnostic

A library's `requires` names packages the consumer must also list. The check is a
set difference, and the message has to name three things: which library declared
the requirement, which package is missing, and that the fix is a `libraries`
entry plus an install.

There is no transitive walk. A missing package that itself declares requirements
produces one diagnostic now and possibly another after it is added, which is the
model working as designed: the developer resolves the graph, one honest step at a
time, with the compiler naming each one.

### Codes

| Code | Severity | When |
|---|---|---|
| `project-library-collision` | error | Two libraries, or a library and a project file, claim one name on one side. |
| `project-library-shadows-api` | warning or error, per T-01 | A library claims a name the MTA catalog defines for that side. |
| `config-library-requirement-missing` | error | A resolved library declares a requirement the manifest does not list. |

The first is a `project-` code because it is found across modules, matching the
existing `project-` family. The third is `config-` because the repair is a
manifest edit, matching the codes [38.01](38.01-libraries-manifest-domain.md)
adds.

## Steps

### T-01 - Decide the API-shadowing rule

**Agent:** architecture-engineer

- [ ] Decide whether a library claiming an MTA catalog name is an error, a
      warning, or silent, and record the reasoning and the rejected alternatives.
- [ ] Confirm the decision does not break a library that deliberately wraps an
      MTA function, which is a legitimate and probably common shape.
- [ ] Confirm whether the same rule should apply to a project file, and if it
      differs, say why.

### T-02 - Extend collision detection to libraries

**Agent:** architecture-engineer

**Files:** `packages/compiler/src/project/module-graph.ts`

- [ ] Include library modules in `validateContributions` without duplicating the
      walk.
- [ ] Order the walk so a library-versus-project collision reads as the library
      intruding, regardless of list order.
- [ ] Report `project-library-collision` naming both packages — or the package and
      the project file — the claimed name, and the side.
- [ ] Confirm a `shared` library colliding with a `server` project file is
      reported on the side they actually share, reusing `occupiedSides`.

### T-03 - Report missing requirements

**Agent:** architecture-engineer

- [ ] Compare each resolved library's `requires` against the resolved set.
- [ ] Report `config-library-requirement-missing` naming the declaring library,
      the missing package, and both repairs — the `libraries` entry and the
      install command.
- [ ] Confirm nothing is walked, fetched, or added implicitly.
- [ ] Confirm a requirement satisfied by a package listed later in `libraries`
      is not reported, since the list is an order, not a dependency chain.

### T-04 - Confirm the messages are actionable

**Agent:** architecture-engineer

- [ ] Read each message as a developer who did not write either library, and
      confirm it names what to change.
- [ ] Confirm no message prints a path inside `node_modules` without the package
      name that explains it.

## Acceptance Criteria

- [ ] Two libraries declaring one name on one side report
      `project-library-collision` naming both packages and the side.
- [ ] A library and a project file declaring one name report the same code, with
      the message reading as the library intruding.
- [ ] Two libraries declaring one name on sides that never meet report nothing.
- [ ] A library declaring an MTA catalog name behaves as T-01 decided, with a
      test either way.
- [ ] A library whose `requires` names an unlisted package reports
      `config-library-requirement-missing` naming both repairs.
- [ ] A satisfied requirement reports nothing, whatever the order of the
      `libraries` list.
- [ ] Nothing in this task walks a graph or touches the network.
- [ ] A project with no libraries reports exactly what it reports today.

## Out of Scope

- Namespacing, aliasing, or renaming to resolve a collision.
- Transitive resolution.
- Version conflicts, which the model prevents by having no resolver.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A collision message names two `node_modules` paths and cannot be acted on | High | T-04 reads every message from the developer's position |
| A library wrapping an MTA function becomes unusable | High | T-01 decides the rule against that exact case before it is written |
| The collision message blames the project for a library's name | Medium | T-02 fixes the walk order so the direction is stable |
| A requirement diagnostic reads as something the compiler should have installed | Medium | The message names the install command as the developer's step, matching `config-library-missing` |
