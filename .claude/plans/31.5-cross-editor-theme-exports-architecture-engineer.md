# 31.5 - Export the theme to the other editors

## Objective

Emit the same role table as a Zed theme, a Neovim colour scheme, and a
TextMate-family `.tmTheme`, so a Luam user gets the same reading of their code
outside VS Code without a second set of colour decisions existing anywhere.

## Scope

- **In:** Three exporters in `packages/theme`, their committed output under
  `packages/theme/dist-themes/`, and install instructions for each.
- **Out:** JetBrains. Its colour scheme format is `.icls`, its highlighting comes
  from a language plugin rather than from a grammar, and the community IDEs do
  not map LSP semantic tokens to a colour scheme without one. Shipping an `.icls`
  that colours nothing Luam-specific would be a worse promise than shipping
  nothing. Record the reason in 31.7 and revisit if a Luam plugin is ever built.
- **Out:** Publishing to any registry. The files are produced and documented; a
  release decision is separate.

## Why It Is Cheap

Every exporter reads `resolve()` and writes a different file format. The
decisions were made in 31.1, the mapping surfaces in 31.4. What is left is
serialisation plus each editor's naming, which is why this is one task and not a
milestone.

## Steps

### T-01 - Zed

**Agent:** architecture-engineer

- [ ] Emit a Zed theme family JSON with both appearances, mapping roles to Zed's
      syntax keys and its `players` and UI colours from the chrome group.
- [ ] Zed drives Luam highlighting entirely from the LSP, so the export is only
      as good as 31.3's tokens. Verify the four Set 1 callables render apart in
      Zed specifically; if they do not, the gap is a semantic-token gap and
      belongs back in 31.3, not a fudge here.
- [ ] Document the Zed language-server registration a user needs, since the
      extension only covers VS Code.

### T-02 - Neovim

**Agent:** architecture-engineer

- [ ] Emit a Lua colour scheme setting the standard highlight groups from the
      chrome and ink roles, then the `@lsp.type.*` and `@lsp.mod.*` groups from
      the semantic map, including the custom modifiers.
- [ ] There is no Tree-sitter grammar for Luam, so the file's highlighting comes
      from the LSP alone. State that in the file header rather than letting a
      user discover it as a missing colour.
- [ ] Keep the output a single file with no plugin-manager assumptions.

### T-03 - TextMate family

**Agent:** architecture-engineer

- [ ] Emit a `.tmTheme` plist from the TextMate map for Sublime Text, TextMate,
      and anything else consuming the format.
- [ ] Ship the `.tmLanguage.json` grammars alongside it, since the format has no
      semantic-token equivalent and the grammar is all these editors have. Note
      plainly that Set 1 and Set 3 are partially collapsed there — that is the
      format's limit, not a defect to hide.

### T-04 - One place to build them

**Agent:** architecture-engineer

- [ ] Extend `scripts/build-theme.ts` to write every target in one run, and add a
      package script that fails if any committed output is stale.
- [ ] Keep the outputs deterministic — stable ordering, no timestamps — so a diff
      of a colour change is readable across all four targets at once.

## Acceptance Criteria

- [ ] Zed, Neovim, and `.tmTheme` outputs are generated, committed, and load in
      their editor without error.
- [ ] Every target is produced from `resolve()`; no colour literal appears in an
      exporter.
- [ ] Regenerating produces no diff for any target.
- [ ] The Zed and Neovim outputs colour the custom modifiers, proving the
      semantic path works outside VS Code.
- [ ] The JetBrains exclusion is recorded with its reason, not left as silence.
