# 39.01 - Add luam format with a check mode

## Objective

Make the formatter reachable without an editor, so a contributor on any setup can
format a project and a pipeline can assert that a branch is already formatted.

## Scope

- **In:** A `luam format` command that rewrites files in place, a `--check` mode
  that writes nothing and reports what differs, the file selection rules, and the
  exit codes.
- **Out:** New formatting rules. The style is fixed, recorded in
  `docs/*/reference/formatting.md`, and this command renders it — it does not
  extend it.
- **Out:** Formatting `.luam.manifest`. Decide in T-01 whether the manifest is in
  scope; it is a Luam file parsed like any other, so the answer is probably yes,
  but it is a decision rather than an assumption.

## Context

Milestone 32 built the formatter and deliberately excluded a CLI:

> A `luam format` CLI command. The editor is the surface here; what CI enforces
> is a later question.

This is that later question. The formatter is idempotent, preserves comments,
compiles to byte-identical Lua across the corpus, and yields no edits for a file
that fails to parse. It is exposed as two pure functions in
`packages/compiler/src/format/format.ts`:

- `formatSource(source: string): string | null`
- `formatRange(source: string, startLine: number, endLine: number): RangeEdit | null`

`null` means the file did not parse. Both are already consumed by
`packages/lsp/src/features/formatting.ts`. A CLI command is a file walk, a call
to the first function, and a write — the engine is done.

Two things make it worth doing rather than leaving to the editor. A contributor
without the extension has no way to satisfy a style the project asks for. And
milestone 36 deferred automated enforcement of `code-conventions.md` because "the
workspace has no linter or formatter" available to a pipeline; `--check` is the
half of that which already exists.

## Design

### Two modes, three exit codes

| Invocation | Effect | Exit |
|---|---|---|
| `luam format` | Rewrites every selected file that differs. | `0` |
| `luam format --check` | Writes nothing. Lists files that differ. | `0` if none differ, `1` if any do |
| Either, with an unparseable file | Reports it and does not touch it. | `1` |

`1` is the CLI's existing meaning — the command reported diagnostics — and
`--check` finding differences is exactly that. `2` stays reserved for an invalid
command line or configuration.

### What gets formatted

The manifest's `sources` patterns, the same set `luam check` compiles, plus
`.d.luam` declaration files. Not `node_modules`, not generated output, not the
`outDir`. A path argument narrows the selection to one file or directory; with no
argument, the whole project.

Library sources from [38.01](38.01-libraries-manifest-domain.md) are never
formatted. They belong to another package, and rewriting a file inside
`node_modules` is wrong however it is spelled.

### A file that does not parse

`formatSource` returns `null` and the command reports the file and moves on. It
does not run the checker and does not report type errors — that is `luam check`,
and a formatter that also type-checks blurs two commands whose exit codes mean
different things. Decide in T-01 whether an unparseable file makes the whole run
exit `1` or whether it is a warning; prefer `1`, since a file the formatter
cannot read is a file the command failed to format.

### Idempotence as a runtime assertion

The formatter is idempotent by construction and by test. The command should not
re-verify that per file at runtime, which would double the work on every
invocation for a property the suite already pins. T-03 records that decision
rather than leaving it to look like an omission.

      anything does and `0` when nothing does.

- [x] The command and the LSP agree byte for byte across the corpus.

- [x] Passing `--check` to another command exits `2`.

- Configuring the existing ones, which is

## Record

### T-01 - The selection and failure rules

- **`.luam.manifest` is not formatted.** It is configuration written in the
  manifest dialect, whose validity is decided by `manifest-analysis.ts` and not
  by the source parser `formatSource` calls. Running the source formatter over it
  would format a file against a grammar that is not the one it is judged by, for
  no reader's benefit. The same reasoning excludes `.luam.formatter` when
  [39.05](39.05-formatter-configuration.md) adds it. Selection is by extension —
  `isSourcePath` — so both files fall out naturally rather than by a special case.
- **An unparseable file is a warning, and does not fail the run.** The plan
  preferred `1`; the repository decided otherwise. `docs/snippets/errors/` holds
  files that deliberately do not parse — `optional-position/src/shared/shapes.luam`
  and `reserved-word/src/server/legacy.luam` — because they are the documentation
  of those parse errors. Failing on them would mean
  [39.04](39.04-conventions-gate.md) could never be green without a path
  exclusion list, which is the brittleness that milestone 36 ruled out for
  required checks. The formatter has nothing to say about a file it cannot read;
  `luam check` is the command that explains why. The file is reported as
  `format-source-unparseable` and left untouched, and `--check` still exits `1`
  for anything that merely differs.
- **Library sources and generated output are excluded.** `listProjectFiles`
  already skips `EXCLUDED_DIRECTORIES` — `.git`, `.luam`, `node_modules` — so a
  library resolved into `node_modules` is unreachable by construction rather than
  by a filter that could be forgotten. The project selection additionally excludes
  `config.outDir`.
- **A path argument is supported, and replaces the manifest selection rather than
  intersecting it.** `luam format [paths...]` formats the named files and
  directories and loads no manifest, so the formatter is usable on a directory
  that is not a project — which is what makes one `luam format --check .` at the
  repository root possible for 39.04, where the corpus is spread across 40-odd
  small projects and a dozen loose fixtures. A path outside the project root, a
  path that does not exist, and a file that is not `.luam` are each reported as
  `format-path-unreadable`.

### T-03 - Idempotence is not re-asserted at runtime

`formatSource` is idempotent by construction and pinned by
`packages/compiler/tests/format-corpus.test.ts`, which re-formats every corpus
file and asserts the second pass is a fixed point. The command formats once and
writes; it does not format twice to compare. Doing so would double the work of
every invocation to re-derive a property the suite already owns.

### T-04 - How the two surfaces are held together

Both surfaces call the same exported `formatSource`, and each half is pinned
where it lives:

- `packages/lsp/tests/formatting.test.ts` asserts, over `docs/snippets` and the
  compiler fixtures, that `formatting()` produces exactly `formatSource(text)` —
  one edit carrying that text, or no edit when the text is already formatted or
  does not parse.
- `packages/cli/tests/format-command.test.ts` asserts that the command writes
  exactly `formatSource(source)`, and that `--check` over the same corpus reports
  nothing and exits `0`.

The repository's corpus is already a fixed point, so `--check` passes on a clean
checkout. Two of its files do not parse and are warned about, per T-01.

### Selection, in one place

`packages/cli/src/format/format-selection.ts` holds both rules:

| Invocation | Selected |
|---|---|
| `luam format` | Every `.luam` file under the project that the `sources` resolver matches, plus every `.d.luam` file, minus `outDir` and the excluded directories. |
| `luam format <path>...` | Every `.luam` file at or below each path, minus the excluded directories. No manifest is loaded. |
