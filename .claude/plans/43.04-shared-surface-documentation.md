# 43.04 - Record what a shared file may use

> File: `.claude/plans/43.04-shared-surface-documentation.md`

## Objective

Write down the new rule for a shared file, and why the compiler stopped deciding
what runs on which side inside one.

## Scope

- **In:** ADR-044, the Environments section of the language design, both locales
  of the public manual, and the changelog.
- **Out:** Any promise of narrowing, of a side global, or of splitting a shared
  file per side.

## Steps

- [ ] Write `.claude/docs/adr/044-merged-surface-in-shared-files.md`: a shared file
      sees the shared surface plus both sides, an unguarded side-restricted use is
      a warning rather than an error, the author owns the runtime branch, and
      ADR-023 stands — the environment is still a property of the file and nothing
      is split.
- [ ] Record the rejected alternatives and why: control-flow narrowing and a
      compiler-provided `isClient` both fail on a branch that tests a stored field,
      and silence would strip checking from every file that falls back to `shared`.
- [ ] Update the Environments section of `language-design.md`: the shared rule
      changes from "shared APIs only" to "shared APIs, plus both sides under a
      warning", with imports unchanged.
- [ ] Document the pattern in `docs/en` and `docs/pt-br` with the reported network
      class as the worked example, including the runtime branch it relies on and
      what happens if the branch is wrong.
- [ ] Add the changelog entry.

## Acceptance Criteria

- [ ] ADR-044 is linked from ADR-023 and from the language design.
- [ ] Both locales carry the same example and stay in parity.
- [ ] The manual states plainly that the warning is the only thing standing
      between a shared file and a nil call on the wrong side.
