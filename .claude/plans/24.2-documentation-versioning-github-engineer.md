# 24.2 - Keep documentation versioning synchronized with releases

> File: `.claude/plans/24.2-documentation-versioning-github-engineer.md`

## Objective

Make stale documentation versions impossible to publish by deriving every
current-version display from one committed source and requiring each release to
contain matching en-US and pt-BR changelog entries.

## Scope

- **In:** The documentation banner, installation and extension examples,
  documentation changelogs, repository changelog release sections, package
  version parity, release preparation, documentation CI, and release workflow
  validation.
- **Out:** Inferring release notes from commits without review, translating CLI
  output, maintaining documentation for every historical patch as a separate
  site, or changing the project's semantic-versioning policy.

## Root Cause

The plan was written against `0.7.0`. By the time it ran, the committed version
was `0.15.6`, which is the release it was retargeted to.

- `docs/.vitepress/config.ts` already reads the current banner version from
  `packages/cli/package.json`, which is `0.15.6` in the working tree.
- `docs/en/changelog.md` and `docs/pt-br/changelog.md` still contain a manually
  written `0.1.1` release heading. Changes since then accumulated under
  `Unreleased` and were never rolled into versioned sections.
- `CHANGELOG.md` keeps every change since the first release under `Unreleased`,
  grouped by milestone, below a header claiming that nothing is published. Thirty
  releases have shipped.
- Installation and VS Code examples in the manual hard-code `0.1.1`, creating
  several independent values to remember during release.
- `.github/workflows/release.yml` stamps package versions only in the temporary
  runner checkout. It can package a tag whose committed package files and
  documentation were not prepared for that version.
- Documentation CI verifies locale shape, snippets, captured output, and the
  VitePress build, but not version consistency or changelog release coverage.

## Version Contract

`packages/cli/package.json` is the committed source of truth for the Luam product
version. All published packages must carry that same version. Documentation may
read it at build time but must not duplicate it in prose or checked-in generated
Markdown except in immutable historical changelog headings.

For a tag `vX.Y.Z`:

1. The tag, CLI package, VS Code package, and all released workspace packages
   equal `X.Y.Z` in the tagged commit.
2. Both documentation changelogs contain exactly one release heading for
   `X.Y.Z`; `Unreleased` remains at the top and is empty or contains only work
   added after release preparation.
3. The repository `CHANGELOG.md` contains an `X.Y.Z` section with reviewed
   product changes. GitHub release notes may supplement it with commit links but
never replace it.
4. Version-specific install commands are rendered from the source-of-truth
   version. Historical release headings remain literal because they describe a
   past release.

## Obsolete Content Contract

Add a documentation linter for identifiers and forms removed from current Luam,
starting with `luam.json`, `--config`, superseded syntax, removed diagnostics,
and stale current-version literals. Each rule records the replacement, removal
version, allowed historical paths, and optional exact-line exemptions. Current
guides, recipes, snippets, landing pages, and reference pages fail validation;
historical changelog sections and migration `before` examples are allowed only
when their context explicitly identifies the old version. Apply the same check
to maintained examples such as `examples/json/luam.json` so documentation does
not link readers to obsolete project shapes.

## Release Preparation

Add one explicit, local release-preparation command, for example
`pnpm release:prepare 0.15.7`. It must be deterministic and safe to review in a
pull request. The command:

- validates strict SemVer and refuses a lower or already released version;
- updates every released workspace package to the same version and keeps the
  lockfile consistent;
- creates matching `X.Y.Z - YYYY-MM-DD` sections in `CHANGELOG.md`,
  `docs/en/changelog.md`, and `docs/pt-br/changelog.md` from their current
  `Unreleased` content;
- restores an empty `Unreleased` section in all three files;
- fails rather than fabricating an empty release or translating prose;
- prints the files changed and the verification command, but does not commit,
  tag, push, or create a GitHub release.

The author reviews the English and Portuguese entries in the release pull
request. Automation controls structure and version parity, not editorial
content.

## Outcome

- The tooling lives in `tools/release`, a new private workspace package, so it is
  covered by `pnpm -r typecheck` and `pnpm -r test` without joining the product
  packages under `packages/`.
- `CHANGELOG.md` was not folded into one release section. Each `###` group was
  mapped to the release commit that introduced it, so the file now carries 19
  dated release sections from `0.2.0` to `0.15.6`. Milestones 1 to 6 predate the
  first published release and sit under `0.2.0`. No prose changed except the
  header.
- The manual changelogs split the same way: their accumulated `Unreleased`
  content moved under `0.6.0`, `0.7.0`, `0.8.0`, `0.15.4`, `0.15.5`, and
  `0.15.6`, matching the releases that shipped each entry, and both locales end
  with identical heading lists.
- Version rendering uses a markdown-it rule in `docs/.vitepress/version-token.ts`
  rather than a Vue component, because the `.vsix` example lives inside a fenced
  code block where a component would not render.
- The lockfile needs no release step: every workspace dependency is declared as
  `workspace:*`.

## Acceptance Criteria

- [x] The current documentation banner and version-specific command examples are
  derived from `packages/cli/package.json`; no current-version literal needs a
  manual search-and-replace.
- [x] `CHANGELOG.md`, `docs/en/changelog.md`, and `docs/pt-br/changelog.md` have a
  reviewed `0.15.6` section and retain `Unreleased` for later work.
- [x] A documentation build fails when locale changelog release headings differ,
  the current release heading is absent, released package versions differ, or a
  supplied tag differs from the committed version.
- [x] `release:prepare` updates versions and changelog structure without creating
  prose, commits, tags, pushes, or releases, and its diff is deterministic.
- [x] The release workflow packages only a version already committed and reviewed
  and cannot silently correct stale package or documentation versions in CI.
- [x] Documentation CI runs for every file that can change the product version,
  rendered version, changelog contract, or release behavior.
- [x] Historical version literals are allowed only in historical changelog text,
  migration instructions that intentionally name that version, and validator
  fixtures with an explicit allowlist.
- [x] Current documentation and maintained examples contain no unmarked removed
  project file, removed CLI option, removed diagnostic, or other catalogued
  obsolete form; migration and historical uses identify their applicable version
  and replacement.
- [x] A dry run for a future `0.15.7` demonstrates that stale current examples or
  missing locale release notes fail before tagging.
