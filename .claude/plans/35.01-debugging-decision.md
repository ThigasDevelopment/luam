# 35.01 - Decide whether Luam ships a debugger

## Objective

Turn an aside inside a limitations entry into a recorded decision: either Luam
reaffirms that it ships no debugger and labels that boundary, or it scopes one.

## Scope

- **In:** An ADR deciding the question, and whatever
  [limitations](../../docs/en/reference/limitations.md) needs to say afterwards.
- **Out:** Implementing a debugger. If the ADR decides to build one, the
  implementation is its own milestone with its own plans.
- **Out:** Revisiting `luam dev`. Reading the local server log is the shipped
  answer and is not in question here.

## Context

This is not a forgotten gap. `limitations.md` already says it, in the closing
line of the development-logs section: evaluating an expression on a running
server "is a debugger, and it needs its own protocol and its own security
decision."

That sentence is doing a lot of work for something written as an aside. It is the
only place the product addresses debugging, it appears at the end of an entry
about something else, and it carries none of the four labels the limitations page
uses to tell a reader what will change from what will not — it is neither
**Planned**, **Design boundary**, **Upstream constraint** nor **Platform
constraint**. A developer reading it cannot tell whether a debugger is coming.

The surrounding decisions point one way. The `transport` manifest field that
configured a server connection was *removed*, and `ensure` writing files plus
`dev --start-server` driving a server the CLI owns is what replaced it.
`.claude/CLAUDE.md` states the CLI never opens a connection to an MTA server. A
debugger is a connection to a running server by definition, so shipping one
reverses a decision the product has already made twice.

The security question is the substantive one and is why this needs an ADR rather
than a doc edit. A debug protocol that evaluates expressions on a running server
is remote code execution against a live game server, and any design has to answer
who may attach, over what, and what happens when the port is exposed.

## Steps

### T-01 - State the case both ways

**Agent:** documentation-engineer

- [x] Write the case for reaffirming: the removed `transport` field, the
      CLI-never-connects rule, the security surface, and what `luam dev` and
      `luam trace` already give a developer.
- [x] Write the case for building: what a developer cannot do today that a
      breakpoint would give them, and how far the existing source-position
      mapping from milestone 18 already goes toward it.
- [x] Check what MTA itself offers, and whether the ecosystem has a debugging
      convention Luam would be interoperating with rather than inventing against.

### T-02 - Decide and record

**Agent:** documentation-engineer

- [x] Write the ADR in Nygard format with the decision and its consequences.
- [x] If reaffirmed: give `limitations.md` its own labelled section for
      debugging, rather than a trailing sentence inside the logs entry, and
      mirror it in `pt-br`.
- [x] If reversed: scope the milestone — protocol, authentication, what may be
      evaluated, and how a position maps back to `.luam` — and state that
      `.claude/CLAUDE.md`'s CLI-never-connects rule has to change with it.
- [x] Either way, cross-reference [33.01](33.01-luam-test-command.md), since a
      test runner and a debugger both want to execute project code and the two
      decisions constrain each other.

## Outcome

The decision is [ADR-039](../docs/adr/039-no-debugger.md): **Luam ships no
debugger**, and the boundary is recorded rather than left as a gap.

Both cases are in the ADR. The case for building is stated honestly — the live
half is genuinely missing, milestone 18's position mapping is most of a
debugger's hardest problem and already exists, and both TypeScript and Luau have
a debugger story. It loses on two independent grounds, either fatal alone. The
CLI never opens a connection to an MTA server, a rule the product has now
decided three times — removing `transport`, shelving
[24.12](24.12-remote-development-bridge.md), and this. And MTA publishes no debug
protocol and no way to suspend one resource: a Lua debug hook that stops on a
line stops the thread the whole server runs on, so a breakpoint freezes the game
for every connected player. There is no ecosystem convention to interoperate
with; Luam would be inventing one and asking server operators to load it.

The security model is not deferred, because the decision is to have no channel.
Evaluating expressions inside a live server is remote code execution against a
machine with players on it, an exposed port is a takeover rather than a leaked
stack frame, and no token scheme changes that. Refusing the channel *is* the
model.

The relationship to 33.01 is stated in the ADR: a test runner and a debugger both
want to execute project code, and [ADR-037](../docs/adr/037-test-execution-host.md)
already answered where that happens — a process the CLI starts, a discovered Lua
5.1 interpreter, MTA stubbed, never the server. A debugger over that same host is
recorded as the only future shape that would break no invariant, and as the place
a future attempt starts.

`limitations.md` gained "Luam ships no debugger" as a section of its own, labelled
**Design boundary**, in `en` and `pt-br`, with the development-logs aside now
pointing at it instead of carrying the decision. The section is registered in
`docs/scripts/limitations-contract.ts`, so its label and its recorded decision are
enforced by `pnpm docs:limitations`.
