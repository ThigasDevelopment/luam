# 46.01 - Share one distribution rule for a value list

> File: `.claude/plans/46.01-value-list-distribution.md`

## Objective

Give the checker and the editor a single implementation of the rule that turns a
list of value expressions into one type per name, so a multi-return call cannot
mean one thing to `luam check` and another to the language server.

## Reproduction

```luam
function triple(): (number, string, boolean)
    return 1, "a", true
end

local a, b, c = triple()
local only = triple()
local x, y = 1, triple()
```

The inlay hints the server answers today:

| Position | Label | Should read |
|---|---|---|
| `a` | `: (number, string, boolean)` | `: number` |
| `b` | none | `: string` |
| `c` | none | `: boolean` |
| `only` | `: (number, string, boolean)` | `: number` |
| `x` | `: number` | `: number` |
| `y` | `: (number, string, boolean)` | `: number` |

Hovering `b` answers `local b`, with no type at all.

The same happens against the catalog, which is where it was reported:
`getVehicleComponentPosition` is declared `tupleOf([NUMBER, NUMBER, NUMBER])` in
`packages/mta-types/src/generated/api/mta-vehicle-client.ts`, so
`local cX, cY, cZ = getVehicleComponentPosition(...)` renders the whole tuple on
`cX` and nothing on the other two.

## Context

The checker is right. `checkValueList` in
`packages/compiler/src/checker/expressions.ts` already implements Lua's adjust
rules: the value in final position expands through `valuesOf`, every earlier one
narrows through `firstValueOf`. Both helpers live in
`packages/compiler/src/checker/types.ts` and both are exported.

What is wrong is that two places in the language server pair declarator `n` with
`statement.values[n]` and read that expression's type whole —
`localHints` in `packages/lsp/src/features/inlay-hint-kinds.ts` and `collectLocal`
in `packages/lsp/src/symbols/statement-collector.ts`. Neither can be fixed by a
local patch without writing the adjust rules a third and fourth time, which is how
the two surfaces drifted apart in the first place.

## Options Considered

| Option | Single source of truth | Cost | Decision |
|---|---|---|---|
| Extract the rule from `checkValueList` into a pure function both packages import | Yes | Low — the extracted body is four lines already written | Accept |
| A helper private to the LSP package | No — the rule then exists twice | Low | Reject |
| Have the LSP re-run the checker over the statement | Yes, but by recomputation | High — a hint request must not type-check | Reject |

## Scope

- **In:** A pure `distributeValueTypes` in the compiler, `checkValueList` rewritten
  over it, and an LSP-side helper that pairs each declarator with its distributed
  type and with the expression it came from.
- **Out:** Every consumer of those helpers. 46.02 and 46.03 change the two call
  sites; this task changes no rendered output on its own.
- **Out:** `generic-for` variables, assignment targets, and any change to the
  emitted Lua.

## Steps

- [x] Add `packages/compiler/src/checker/value-distribution.ts` exporting
      `distributeValueTypes(types: readonly Type[]): Type[]` — the final entry
      expands through `valuesOf`, every earlier one narrows through
      `firstValueOf`, an empty list yields an empty list.
- [x] Rewrite `checkValueList` over it, keeping the checking order it has today so
      contextual typing by `expected[index]` is unaffected.
- [x] Add an LSP helper that walks a value list using only `analysis.types` and
      returns, per index, the distributed type and the expression that produced it,
      with the final expression repeated across the elements it expanded into.
- [x] Return nothing past the last index the value list can account for, so a name
      with no value keeps answering as it does today rather than gaining a hint.
- [x] Where the final expression has no recorded type, stop distributing at it: an
      unknown arity must produce no answer rather than a wrong one.

## Acceptance Criteria

- [x] `distributeValueTypes` has unit coverage for the empty list, a single
      non-tuple, a single tuple, a tuple in non-final position and a tuple followed
      by another value.
- [x] `pnpm --filter @luam/compiler test` passes with no fixture changed —
      `checkValueList` behaves exactly as before.
- [x] The LSP helper reads no expression the checker did not record, and answers
      without re-running the checker.
- [x] `pnpm typecheck` and `pnpm conventions` pass.
