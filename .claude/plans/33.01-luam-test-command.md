# 33.01 - Add a luam test command for user resources

## Objective

Give a developer a way to test the resource they wrote. Luam has 154 test files
of its own and ships no way for a user to test a single line of their gamemode.

## Scope

- **In:** A `luam test` command, the decision about what executes the tests, and
  the assertion surface a test file is written against.
- **Out:** Any coupling to `build`. A build never runs project code, and adding a
  test step inside one would break that.
- **Out:** Testing against a live MTA server. That is an integration surface with
  its own protocol and its own security decision, and it overlaps
  [35.01](35.01-debugging-decision.md).

## Context

`packages/cli/src/commands/` holds `build`, `check`, `ensure`, `dev`, `server`,
`config`, `trace`, `setup`, `doctor` and `init`. There is no `test`. A developer
writing a gamemode in Luam today verifies it by starting a server and playing.

The constraint that shapes this whole plan is the one the product has held since
milestone 1: **the compiler emits Lua text and never executes it, and a build
never runs project code.** A test runner is, by definition, an execution surface.
It therefore has to be a separate command that a person invokes, never a step
inside `build` or `check`, and the boundary has to be visible in the design
rather than assumed.

The open question is what executes the Lua. The realistic options, which T-01
exists to decide between:

- A bundled Lua 5.1 interpreter, which makes `luam test` self-contained and adds
  a native dependency to a package that currently declares none.
- The MTA server's own Lua, driven headlessly, which tests against the real
  runtime and requires a server installation to run any test.
- A Lua interpreter the developer already has, discovered on `PATH`, which keeps
  the package dependency-free and makes the command's availability depend on the
  machine.

None of these is obviously right, and the choice determines what MTA API surface
a test can touch. It deserves an ADR before any code.

## Steps

### T-01 - Decide the execution model

**Agent:** architecture-engineer

- [x] Write an ADR weighing the three options above against: the no-dependencies
      property of the published CLI, whether a test can call MTA APIs, and what a
      developer must install before the first test runs.
- [x] Decide how MTA APIs are handled in whatever host is chosen — stubbed,
      recorded, or unavailable — and say so plainly, because it bounds what can
      be tested.
- [x] Record the boundary explicitly: `luam test` is a command a person runs,
      never a step inside `build`, `check` or `ensure`.

### T-02 - Define the test file surface

**Agent:** architecture-engineer

- [x] Decide how a test file is recognized and where it lives, and confirm it is
      excluded from the resource a build assembles — test code must never ship.
- [x] Define the assertion surface, and type it so the checker and the editor
      understand a test file the way they understand any other module.
- [x] Decide what a test's environment is. `server`, `client` and `shared` are
      resolved per file, and a test has to resolve to something.

### T-03 - Implement the command

**Agent:** architecture-engineer

- [x] Register `test` through the CLI command registry from milestone 19.
- [x] Compile the test files and their subjects, run them, and report per-test
      results in the CLI's existing output voice.
- [x] Exit non-zero on a failing test, so CI can gate on it.
- [x] Report a failure with the position in the `.luam` source, not in the
      generated Lua.

### T-04 - Document it

**Agent:** documentation-engineer

- [x] Add `luam test` to [cli.md](../../docs/en/tooling/cli.md) and mirror it in
      `pt-br`.
- [x] Add a recipe showing a first test, and reference it from
      [ci-and-deployment](../../docs/en/tooling/ci-and-deployment.md).

## Acceptance Criteria

- [x] An ADR records the execution model, what a test may call, and why the
      rejected options were rejected.
- [x] `luam test` runs the project's tests and exits non-zero when one fails.
- [x] A failing assertion reports a `path:line:column` position in the `.luam`
      source.
- [x] `luam build` output is byte-identical whether or not test files exist, and
      no test file appears in the assembled resource or in `meta.xml`.
- [x] `build`, `check` and `ensure` execute no project code, unchanged.
- [x] The published CLI's dependency count is unchanged, or the ADR records why
      it had to grow.
- [x] The command is documented in both language trees and `pnpm docs:verify`
      passes.

## Outcome

The execution model is [ADR-037](../docs/adr/037-test-execution-host.md): a Lua 5.1
interpreter discovered on `PATH`, MTA functions replaced by recording stubs, and
`luam test` as a command a person runs rather than a step inside any build.

Not verified on this machine: the harness has never been executed by a real Lua
5.1 interpreter, because none is installed here. Everything around it is covered —
discovery, build exclusion, compilation of test files, the result protocol,
position mapping and the editor surface — and the harness Lua is checked by the
existing `parsesAsLua51` helper, which is a no-op without an interpreter.
