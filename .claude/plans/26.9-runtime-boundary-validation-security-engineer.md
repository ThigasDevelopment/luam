# 26.9 - Generate opt-in runtime boundary validators

## Objective

Generate runtime checks only at explicitly marked untrusted boundaries while preserving erased annotations everywhere else.

## Options Considered

| Option | Safety | Runtime cost | Decision |
|---|---|---|---|
| Validate every annotated value | High | Unbounded and breaking | Reject |
| Provide only manual predicates | Depends on users | Low | Keep supported |
| Generate validators for marked boundaries | High where requested | Localized | Accept |

## Scope

- **In:** Boundary syntax/API, reifiable type subset, validator IR, deduplication, event/export integration, diagnostics, runtime helper, size limits, and security documentation.
- **Out:** Mandatory runtime typing, reflection for all types, validation of functions/userdata internals, and trusting client-side validation.

## Steps

### T-01 - Define the trust-boundary contract

**Agent:** security-engineer

- [ ] Compare decorators, declaration modifiers, and `validate<T>(value)` for explicitness and composability.
- [ ] Define supported primitives, literals, arrays, records, unions, optionals, enums, and nominal class checks.
- [ ] Reject non-reifiable types with positioned diagnostics rather than silently weakening checks.

### T-02 - Generate validators

**Agent:** architecture-engineer

- [ ] Lower requested types to a cycle-safe validator IR and deduplicate structurally equal validators.
- [ ] Emit Lua 5.1 validators on demand with depth, collection-size, string-length, and error-detail limits.
- [ ] Preserve zero validator output for programs that do not opt in.

### T-03 - Integrate security boundaries

**Agent:** security-engineer

- [ ] Validate server-side event payloads regardless of client behavior.
- [ ] Define fail-closed behavior for exported and HTTP-facing functions and prevent diagnostics or logs from exposing sensitive values.

### T-04 - Verify attacks and compatibility

**Agent:** test-engineer

- [ ] Cover malformed payloads, deep/cyclic tables, oversized arrays and strings, union ambiguity, recursive types, and validator reuse.
- [ ] Assert that ordinary annotations still erase exactly as before.

## Acceptance Criteria

- [ ] Unmarked programs emit no validator code and retain current behavior.
- [ ] Marked unsupported types fail before emit with an actionable diagnostic.
- [ ] Server-side validation rejects malformed and resource-exhausting payloads within configured limits.
- [ ] Generated failures reveal paths and expected types but never raw secrets or complete attacker payloads.
