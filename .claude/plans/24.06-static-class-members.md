# 24.06 - Add static members to user classes

## Objective

Add typed static fields and methods with an explicit separation between class values and instances.

## Delivered

Statics are inherited and share one slot, which is what the definition chain the
class helper already builds does with no extra generated code. They live in the
same class table as everything else, so no helper and no second lookup chain
appear; the separation between the class value and an instance is a checker
contract, recorded in
[ADR-028](../docs/adr/028-static-class-members.md) together with the receiver
rules and what the runtime does not guard.

A read or a call lowers to `getClass('Name').member`, the only form that both
reads and assigns through the definition table. The readable build stays on the
authored lines: `static` is recorded as an erasure, like an annotation.

Out of scope and untouched, as planned: abstract members, visibility, static
initialization blocks, and instance access from a static method.

## Scope

- **In:** `static` syntax, AST, class-value types, lookup, inheritance, initialization, emission, completion, hover, definition, rename, and tests.
- **Out:** Abstract members, private/protected visibility, static initialization blocks, and implicit instance access from static methods.

## Steps

### T-01 - Specify the class-value model

**Agent:** architecture-engineer

- [ ] Compare own-only statics, inherited statics, and copied statics; select semantics consistent with MTA native class values where practical.
- [ ] Define duplicate names across static/instance spaces, `self` in static methods, overrides, field initialization order, and constructor access.

### T-02 - Extend syntax and checking

**Agent:** architecture-engineer

- [ ] Add `static` to class member parsing without reserving it outside that context.
- [ ] Store separate static and instance member maps in class declarations and fingerprints.
- [ ] Resolve `Class.member` and reject static access through instances and instance access through class values.

### T-03 - Emit and expose editor features

**Agent:** architecture-engineer

- [ ] Emit static methods and ordered static field initialization on the runtime class table.
- [ ] Align LSP completion, hover, definition, references, and rename with the two member spaces.

### T-04 - Verify behavior

**Agent:** test-engineer

- [ ] Cover inherited lookup, override compatibility, initialization order, invalid receiver kinds, environment visibility, and source maps.
- [ ] Compare user-class behavior with native OOP completion where contracts overlap.

## Acceptance Criteria

- [ ] Static and instance members never leak into each other's receiver completion.
- [ ] Static field initialization executes once per class in deterministic order.
- [ ] Invalid overrides and receiver access fail before emit.
- [ ] Generated code remains Lua 5.1-compatible and requires no new helper when the class helper already suffices.
