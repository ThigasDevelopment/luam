# 16.1 — Decorator syntax, AST, and ADR-009

> File: `.claude/plans/16.1-decorator-syntax-architecture-engineer.md`
> This task adds the grammar and nothing else. `@Getter` parses here and means
> nothing until 16.2. Splitting it that way keeps the syntax decision — a new
> sigil in a Lua-shaped language — reviewable on its own.

## Objective

Give Luam a decorator syntax: `@Name` written above a class declaration or above
a class member, parsed into the AST and attached to the declaration it precedes.

## Scope

- **In:** `@` in the lexer, a `Decorator` node, decorator lists on
  `ClassDeclaration`, `ClassFieldDeclaration`, and `ClassMethodDeclaration`,
  parser recovery for a misplaced decorator, and ADR-009 recording the design.
- **Out:** What any decorator *does* (16.2), editor support (16.3), decorators on
  functions, locals, parameters, interfaces, or enums, decorator arguments, and
  user-defined decorators. All four are named in the ADR as deliberate
  non-goals with room to grow into.

## Design

A decorator is `@` followed by an identifier, written on its own line above its
target:

```lua
@Getter
class Player {
    name: string

    @Getter
    @Setter
    health: number
}
```

Decorators bind to the *next* declaration. A run of them applies to one target,
and a target with no decorator carries an empty list, so every downstream
consumer reads the same shape.

`@` becomes a token; decorator names do not become keywords. `Getter` stays an
ordinary identifier everywhere else, which is the same contextual rule that lets
`class`, `enum`, and `export` coexist with user code
([ADR-007](../docs/adr/007-build-directives.md)).

## Steps

- [ ] Add `'@'` to `SYMBOLS` and to `PUNCTUATION` in `lexer/token.ts`. It is not
      an operator — it never takes operands — so `symbolKind` must classify it as
      punctuation and `stream.check('punctuation', '@')` must be the way the
      parser tests for it. Before this change `@` is `lex-unexpected-character`;
      after it, a stray `@` is a parser diagnostic with a better message.
- [ ] Add to `parser/declaration-nodes.ts`:
      `Decorator { kind: 'decorator'; name: string }` and a
      `decorators: Decorator[]` field on `ClassDeclaration`,
      `ClassFieldDeclaration`, and `ClassMethodDeclaration`. The list is always
      present and empty by default — never `null`.
- [ ] Add `parseDecorators(stream): Decorator[]` to `parser/declarations.ts`.
      It consumes `@ identifier` pairs while the stream is on `@`, and records
      the position of the `@` so a diagnostic underlines the decorator, not the
      field.
- [ ] Reject an argument list with a dedicated diagnostic. `@Getter(...)` parses
      the parenthesised run and reports `parse-decorator-arguments`
      ("Decorators do not take arguments."), instead of failing on an
      unexpected `(`. This is where a future argument form would land.
- [ ] Teach `isDeclarationStart` to look past a decorator run. It scans forward
      over `@ identifier` pairs and then applies the existing class-header
      lookahead, so `@Getter\nclass Player {` is recognised as a declaration
      start while `@Getter` alone is not.
- [ ] Pass the parsed decorators into `parseClassDeclaration` and
      `parseClassMember`. A member with decorators keeps the member's own
      position; only the decorator nodes carry the `@` positions.
- [ ] Report a decorator that precedes something that is not a class or a class
      member as `parse-unexpected-decorator`, and recover. Inside a class body
      that means `recoverInBlock` skips to the next member; at statement level it
      means the statement is skipped and parsing continues. A half-typed
      decorator must never end the parse — that is what keeps the editor alive
      mid-keystroke.

## Acceptance Criteria

- [ ] `@Getter` lexes as `punctuation '@'` followed by `identifier 'Getter'`,
      with the positions of both.
- [ ] A class with decorators above the declaration and above members parses,
      and every member carries the decorators written above it in source order.
- [ ] `local at = 1 @ 2` reports `parse-unexpected-decorator`, not a lexer error,
      and parsing continues past it.
- [ ] `@Getter(true)` reports `parse-decorator-arguments` and the class it
      precedes still parses.
- [ ] A decorator above a `local`, a `function`, an `interface`, or an `enum` is
      `parse-unexpected-decorator`, and the declaration after it still parses.
- [ ] `local Getter = 1` and a method named `Getter` still compile. Decorator
      names are not keywords.
- [ ] The emitted Lua is byte identical to today for every existing fixture. A
      decorator that no pass consumes yet changes nothing about the output.
- [ ] [ADR-009](../docs/adr/009-decorators.md) is written and accepted: why a
      sigil rather than another comment directive, why binding is positional,
      why arguments and user-defined decorators are out, and what a decorator is
      allowed to do (rewrite the class it annotates, nothing else).
- [ ] `pnpm typecheck`, `pnpm build`, and `pnpm test` pass.
