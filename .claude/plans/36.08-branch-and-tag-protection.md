# 36.08 - Protect the permanent branches and the release tags

## Objective

Make the rules the project already follows unbreakable by moving them from
convention into rules GitHub enforces on the server, so a mistake, a stale
machine, or an outside contributor cannot rewrite `main`.

## Problem

Neither permanent branch is protected. `GET /branches/main/protection` and the
same call for `develop` both answer `404 Branch not protected`, and the
repository has no rulesets. Today `main` accepts a direct push, a force-push
that rewrites published history, and its own deletion.

Three consequences follow:

- **History is not safe from tooling.** The working copy lives in a
  OneDrive-synchronised directory shared by two machines. Files have already
  been overwritten by that synchronisation during ordinary work. Nothing but a
  server-side rule stops a stale clone from force-pushing over `main`.
- **A broken commit can be released.** `release.yml` triggers on a `v*` tag.
  Nothing requires CI to have passed on the commit being tagged.
- **Tags are a second, unguarded door.** A tag can be deleted and recreated
  pointing at a different commit, and the release workflow will run on it.

## Decisions

Two decisions are settled and the task implements them rather than reopening
them:

- **Pull requests are required on `main`, with zero required approvals.** The
  project has one maintainer, and GitHub does not count a self-approval, so any
  non-zero requirement would make `main` unmergeable without an administrator
  bypass that would hollow out every other rule. The continuous integration
  checks are the gate; the review requirement is raised to one only when a
  second maintainer exists.
- **Rulesets, not classic branch protection.** Classic protection cannot cover
  tags, and the release path is tag-triggered. One mechanism covering branches
  and tags is preferable to two.

## Scope

- **In:** Rulesets for `main`, `develop` and `v*` tags; the required-check set;
  the bypass policy; and the documentation of what a contributor and a
  maintainer each experience.
- **Out:** Raising the approval requirement above zero, adding a merge queue,
  and signed-commit enforcement. Each is a separate decision with its own cost,
  recorded below as deliberately deferred.

## Steps

### T-01 - Harden history immediately

**Agent:** github-engineer

This step has no dependency on the rest of the milestone and should land before
it. It carries the whole force-push benefit at no workflow cost.

- [ ] Create a ruleset for `main` and `develop` that blocks force-pushes and
      blocks branch deletion, with no other rule enabled.
- [ ] Verify by attempting a force-push to `main` from a scratch clone and
      confirming the server refuses it.
- [ ] Confirm the ordinary `develop` workflow is unaffected.

### T-02 - Gate `main` on pull requests and checks

**Agent:** github-engineer

- [ ] Require a pull request to merge into `main`, with zero required
      approvals.
- [ ] Require the check set named by [36.01](36.01-pipeline-contract.md) and
      narrowed by [36.03](36.03-merge-gate-and-signal.md). Advisory jobs are
      never required; a required check that can fail for a reason the change did
      not cause would block the branch.
- [ ] Confirm every required check name matches a job name exactly, and record
      that renaming a job means updating the ruleset in the same change.
- [x] Decide and record whether the maintainer bypasses the rules. Default to
      no bypass, so the rules mean what they say.
- [x] Reconcile with `git-rules.md`, which forbids feature branches: state how
      `develop` is promoted to `main` under a pull request requirement.

### T-03 - Protect the release tags

**Agent:** github-engineer

- [ ] Create a tag ruleset for `v*` that blocks deletion and blocks updating a
      tag to a different commit.
- [ ] Confirm `release.yml` still runs on a newly pushed tag.
- [ ] Confirm a tag cannot be moved after the fact.

### T-04 - Document the effect

**Agent:** github-engineer

- [x] Record the ruleset configuration as the source of truth, so it can be
      rebuilt after an accidental change.
- [x] Describe in `CONTRIBUTING.md` what a contributor sees: which checks must
      pass, that no human approval is required today, and what a red required
      check means.

## Acceptance Criteria

- [ ] A force-push to `main` or `develop` is refused by the server, proven by
      attempting one.
- [ ] Neither permanent branch can be deleted.
- [ ] A merge into `main` requires a pull request whose required checks passed.
- [ ] Zero approvals are required, and the single maintainer can merge without
      an administrator bypass.
- [ ] No advisory job appears in the required-check set.
- [ ] Every required check name resolves to a job that actually reports.
- [ ] A `v*` tag cannot be deleted or moved to another commit, and `release.yml`
      still runs on a new tag.
- [x] The bypass policy is recorded, with its reasoning.
- [x] `CONTRIBUTING.md` states what the protection means for a contributor.

## Deliberately deferred

- **Requiring one approval.** It becomes correct the moment a second maintainer
  exists, and it is wrong before that, because GitHub does not count a
  self-approval.
- **A merge queue.** It earns its cost when concurrent pull requests contend,
  which one maintainer does not produce.
- **Requiring signed commits.** A real supply-chain improvement, and a separate
  decision with key-management consequences on two machines.
- **Requiring the branch to be up to date before merging.** It serialises merges
  behind a full CI run and buys little at the current rate of change.
