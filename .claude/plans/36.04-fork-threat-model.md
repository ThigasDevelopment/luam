# 36.04 - Threat-model contributions from forks

## Objective

Decide what a pull request from an untrusted fork is allowed to make the
pipeline do, before any workflow is written to run one. A community pipeline
executes a stranger's code on the project's runners; the boundary has to be
designed, not discovered.

## Problem

The repository has never accepted an outside contribution, and nothing in the
pipeline is written for one. `ci.yml` triggers on `pull_request`, which for a
fork means a read-only `GITHUB_TOKEN` and no secrets — safe by default, and
also silently unable to run anything that needs a token. No workflow states
which of its steps fall into that gap.

The dangerous repair is `pull_request_target`, which runs the workflow from the
base branch with a writable token and access to secrets, in a context where
checking out the pull request head hands an attacker both. That trade has to be
refused explicitly and in writing, or someone will reach for it later.

## Scope

- **In:** The trust boundary for fork pull requests, the token and secret
  policy, the `pull_request_target` position, the cache-poisoning surface, the
  first-time contributor gate, and an ADR recording the model.
- **Out:** Implementing the pipeline. [36.05](36.05-fork-pull-request-pipeline.md)
  builds against this model.

## Steps

### T-01 - Model the threat

**Agent:** security-engineer

- [x] Enumerate what a fork pull request can influence: workflow files on the
      head, dependency manifests, lifecycle scripts run by `pnpm install`, test
      fixtures, and generated output compared by `git diff --exit-code`.
- [x] Identify each asset the pipeline holds: `GITHUB_TOKEN` scopes, the npm
      publish identity, the Pages deployment token, and the pnpm store cache.
- [x] For each asset, state whether a fork run may reach it and by what path.

### T-02 - Decide the policy

**Agent:** security-engineer

- [x] Rule on `pull_request_target`: permitted, forbidden, or permitted only for
      jobs that never check out the head. Record the reasoning either way.
- [x] Decide the secret policy for fork runs. The expected answer is that no
      job reachable from a fork reads a secret, which makes the answer testable.
- [x] Decide the cache policy, given that a fork run writing a shared cache key
      is a poisoning path into later trusted runs.
- [x] Decide whether first-time contributors require manual approval before any
      workflow runs, and who approves.

### T-03 - Record the decision

**Agent:** security-engineer

- [x] Write an ADR for the untrusted-contribution boundary, claiming the next
      free number from [the ADR index](../docs/adr/README.md).
- [x] State the invariants the pipeline must preserve, in a form
      [36.07](36.07-pipeline-verification.md) can assert.

## Acceptance Criteria

- [x] Every pipeline asset is listed with a reachability verdict for a fork run.
- [x] The `pull_request_target` decision is recorded with its reasoning.
- [x] No job reachable from a fork pull request reads a secret, or every
      exception is named and justified individually.
- [x] The cache policy prevents a fork run from writing a key a trusted run
      later reads.
- [x] The first-time contributor approval rule is stated, with the approver.
- [x] An ADR records the model with a status, and its invariants are written as
      assertions rather than intentions.
- [x] The project invariant is restated and preserved: the compiler packages
      make no network calls, and a build with no network still succeeds.
