# 39.02 - Emit diagnostics in a machine-readable form

## Objective

Let a program consume Luam diagnostics without parsing prose, so a pipeline, a
pre-commit hook or an editor that does not speak LSP can act on a build without
guessing at the human output.

## Scope

- **In:** A `--json` option on the commands that report diagnostics, the schema
  it emits, and the guarantee that the human output is unchanged when it is not
  passed.
- **Out:** Changing any diagnostic message, code or severity.
- **Out:** A second output format. One machine format, decided once.
- **Out:** Streaming during a watch. Decide in T-01 whether `dev` and `ensure`
  support it; a rebuild loop emitting a document per rebuild is a different
  shape from a single-shot command.

## Context

The CLI reports diagnostics as prose. That is deliberate — `.claude/CLAUDE.md`
requires one wording everywhere, and the diagnostics carry hints written for a
reader. The consequence is that everything else has to parse it.

There is no `--json`. Today, wiring Luam into GitHub Actions annotations, a
`lint-staged` hook, or any editor without the extension means matching
`path:line:column severity code: message` with a regular expression, against
output whose exact shape the project reserves the right to improve. The reporter
lives in `packages/cli/src/reporting`, with `cli-diagnostic.ts`,
`diagnostic-layout.ts`, `diagnostic-excerpt.ts` and `diagnostic-reporter.ts`
between the compiler's `Diagnostic` and the terminal, so the structured value
exists internally and is discarded at the last step.

This is cheap and it unlocks integrations the project does not have to write or
maintain.

## Design

### One option, on the commands that diagnose

`--json` on `build`, `check`, and `test`. Decide `dev` and `ensure` in T-01.

When passed:

- The document goes to stdout. Nothing else does.
- Progress, phase timings, colour and the summary line go to stderr or are
  suppressed, per T-01, so stdout is a single parseable document.
- Exit codes are unchanged. A consumer reads the document; a script reads the
  code; neither has to do the other's job.

### The schema

Emitted as one JSON document, not as newline-delimited records. A build is a
single result, and a document a consumer can `JSON.parse` in one call is simpler
than a stream for every case this serves.

The fields, fixed in T-01 and versioned:

| Field | Meaning |
|---|---|
| `version` | The schema version. Present from the first release so a consumer can branch. |
| `luam` | The CLI version that produced it. |
| `success` | Whether the command succeeded. |
| `diagnostics[]` | Each with `path`, `line`, `column`, `severity`, `code`, `message`, and the position's end when the compiler has one. |
| `summary` | Counts by severity, and the duration. |

`path` is relative to the project directory, matching what the human output
prints, so the two can be reconciled by eye.

The message is the same string the human output shows. A structured consumer that
wants to render its own wording has the code; one that wants Luam's wording has
the message. Splitting the message into a headline and a hint is tempting and is
deferred to T-01, which should record the decision either way, because adding the
split later is a schema change and a consumer break.

### Stability

The schema is a public interface the moment it ships. `version` exists from the
first release for that reason. T-04 records what a consumer may rely on — field
presence, code values — and what it may not — message wording, diagnostic order
beyond the sort the human output already applies.

## Record

### T-01 - The schema and the scope

**The field set, version 1.** One document, `JSON.parse`-able in one call:

```
{ version, luam, command, success, diagnostics[], summary }
```

Each diagnostic carries `path`, `line`, `column`, `endLine`, `endColumn`,
`severity`, `code`, `message`. **Every key is always present**, `null` where the
value does not exist — a configuration diagnostic has no location, and a compiler
diagnostic that reports a point rather than a span has no end. A consumer that
reads `diagnostic.line` never has to check whether the key is there, only whether
it is null. `summary` is `{ errors, warnings, files, durationMs }`.

**The message is not split into a headline and a hint.** It is exactly the string
the human output shows. Splitting later would break every consumer reading
`message`; adding a separate `hint` field later is additive and allowed by the
version policy below. Not splitting is therefore the reversible choice, and it is
the one taken.

**`--json` is owned by `check` and `build`. `test`, `dev` and `ensure` do not
have it.**

- `test` reports test runs — names, assertions, per-environment results — whose
  machine shape is a different document from a diagnostics list. Emitting only
  its compile diagnostics under `--json` would be a machine-readable half-report,
  which is worse than none. A test-report schema is its own decision.
- `dev` and `ensure` are rebuild loops. A document per rebuild is a stream, which
  the plan set out of scope, and this schema describes a single result.
- For the same reason `--json` with `--watch` on `check` exits `2` rather than
  emitting the first run's document and then contradicting itself.

**Progress output is suppressed, not redirected.** With `--json`, the command
runs against a silent logger and a silent reporter, and the only thing written is
the document, on stdout. Routing the human report to stderr instead would restate
every diagnostic in a second wording, which is the thing this option exists to
avoid. A manifest that fails to load is reported before the command runs and
exits `2` with no document; the exit code distinguishes that case.

### T-02 - How it is wired

- `@cli/reporting/json-report.ts` holds the schema, `REPORT_SCHEMA_VERSION`, and
  `buildReport`, which reads the structured `BuildOutcome` the pipeline already
  carries. No diagnostic is re-derived from text.
- `runCheckCommand` and `runBuildCommand` gained an optional `onOutcome` callback.
  Neither changed what it reports or what it returns.
- `@cli/commands/json-command.ts` builds the silenced context, captures the
  outcome, and writes the document to the real logger after the command returns —
  so `success` is the command's actual exit code rather than a guess made before
  it finished.
- `--json` is a shared option (`jsonOption`), registered on `build` and `check`
  only, so the registry's existing ownership rule makes it `2` everywhere else.

### T-03 - The human output did not move

`tests/json-report.test.ts` runs `check` twice without the flag and asserts the
two transcripts are equal once durations are masked, and that no document leaks
into them. Every existing reporter test passes unchanged. `--no-color` and
`NO_COLOR` are untouched: they select the capability, and `--json` replaces the
reporter entirely rather than styling it.

### T-04 - The contract

Recorded in both manual trees under "Machine-readable output", as a table of what
is stable and what is not.

- **Stable:** every field's presence and type; `code` values and their meaning;
  `version`; exit-code equivalence with the run without the flag.
- **Not stable:** the wording of `message` — match on `code`; the order of
  `diagnostics` beyond the sort the human output already applies; `durationMs`,
  which is a measurement.
- **Version policy:** a field may be added without a bump, and a consumer must
  ignore fields it does not know. A field may not be removed, nor change type or
  meaning, without raising `version`.
