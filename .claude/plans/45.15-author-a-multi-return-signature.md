# 45.15 - Author a multi-return signature

> File: `.claude/plans/45.15-author-a-multi-return-signature.md`

## Objective

Let a project function declare that it returns more than one value, so the rule
30.01 already implements for the MTA catalog applies to the code a resource
writes.

## Reproduction

There is no syntax to try. 30.01 states it plainly: "A tuple has no source
syntax: it is produced by the API catalog from the upstream `LuaMultiReturn`
declarations, never annotated by hand."

The ported resource has two functions that need one:

```luam
query = function (str: string, ...)
    local result, rows, lastId = dbPoll(qh, -1)
    return result, rows, lastId
end

function getPositionFromElementOffset(element: Element, offX: number, offY: number, offZ: number)
    return x, y, z
end
```

Both are left unannotated, so every caller destructures three values out of an
inferred type that describes one. The MySQL adapter's `query` is called from four
places and each of them reads `result, rows, lastId` unchecked.

## Context

Multiple returns are not a corner of Lua, and a compiler that types 97 catalog
functions with tuples while refusing to type the resource's own wrappers around
them has the checking exactly where the author does not need it. The distribution
rules, the narrowing rules and the printing already exist; only the annotation is
missing.

## Options Considered

| Option | Reads like the language | Cost | Decision |
|---|---|---|---|
| Parenthesised return list: `function f(): (number, number, number)` | Yes — it is how the checker already prints one | Low | Accept |
| A `tuple<...>` type constructor | No — a second spelling for a printed form | Medium | Reject |
| Infer the tuple from the `return` statement | Partly — but a function with two return statements of different arity has no answer | Medium | Reject as the primary mechanism; revisit as a follow-up |

## Scope

- **In:** A parenthesised return-type list on a function declaration, a function
  expression, a class method and a `fun` type; checking each `return` statement
  against it; and the existing distribution rules at the call site.
- **Out:** Inference of a tuple from the body. A tuple in any position other than
  a return type — it is not a value type and must not become one. Any change to
  the emitted Lua.

## Steps

- [ ] Parse `(T1, T2, T3)` as a return type wherever a return type is accepted,
      producing the tuple descriptor 30.01 already defines, and keep a single
      parenthesised type meaning what it means today so `(fun(string): void)?`
      does not change.
- [ ] Check every `return` in the body against the tuple element by element,
      reporting the element that fails by position, and report an arity mismatch
      as its own diagnostic.
- [ ] Reject a tuple in a parameter type, a variable annotation, an alias body and
      a field type, with a message that says a tuple is a return shape.
- [ ] Confirm the call site needs no work: a call to an annotated function must
      distribute exactly as a catalog call does, including the narrow-to-first
      rule anywhere but final position.
- [ ] Print an authored tuple the same way a catalog tuple prints, so hover and
      diagnostics do not show two notations.
- [ ] Handle a variadic tail if and only if the descriptor already supports one;
      otherwise state the boundary in the docs rather than inventing syntax.

## Acceptance Criteria

- [ ] Both functions from the reproduction can be annotated, and a caller writing
      `local result, rows, lastId = adapter:query(sql)` types all three names.
- [ ] A `return` with the wrong arity, and one with a wrong element type, each
      report their own diagnostic naming the position.
- [ ] A tuple written in a parameter or a variable annotation reports.
- [ ] `local x = f()` where `f` returns a tuple narrows to the first element,
      matching the catalog rule.
- [ ] Hover prints an authored tuple identically to a catalog tuple.
- [ ] The emitted Lua is the function as written.
