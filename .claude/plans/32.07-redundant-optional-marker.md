# 32.07 - Report the redundant optional marker on a name that already carries one

## Objective

Make `name?: Type?` a diagnostic. The language puts the optional marker on the
name, the parser already says so when the marker is only on the type, and it
says nothing when both carry one — the single spelling the rule was written to
forbid slips through silently.

## Scope

- **In:** `parseNamedAnnotation` in
  `packages/compiler/src/parser/type-annotation.ts`, the diagnostic it reports,
  the AST node it returns, and the quick fix that repairs it.
- **In:** The diagnostics and editors reference pages, in both `en` and `pt-br`.
- **Out:** The optional suffix inside a type expression. `fun(): string?`,
  `string?[]` and a `?` on a union member are type syntax, not a named
  declaration, and keep parsing exactly as they do.
- **Out:** Any change to what `name?: Type` and `name: Type?` do today. The
  first stays silent, the second keeps reporting `parse-optional-position` with
  the same message and the same quick fix.

## Context

`parseNamedAnnotation` reads an optional `?` after the name, then parses the
annotation, which may itself end in `?`:

```ts
const optional = stream.check('operator', '?') ? stream.next() : null;
const annotation = parseOptionalAnnotation(stream);

if (optional === null && annotation?.kind === 'type-optional') {
    stream.report('parse-optional-position', `Write optional ${label} as "name?: Type", not "name: Type?".`, annotation.position);
}
```

`packages/compiler/src/parser/type-annotation.ts:267`

The guard is conditioned on `optional === null`, so it only fires when the name
has no marker. Parsing the three spellings confirms the hole:

| Source | Diagnostics |
|---|---|
| `local titulo: string? = nil` | `parse-optional-position` |
| `local titulo?: string = nil` | none — the canonical form |
| `local titulo?: string? = nil` | **none** |

The third also returns a `type-optional` wrapped in a `type-optional`, because
`parseOptionalAnnotation` already wrapped `string` and line 285 wraps the result
again.

The nesting is not a type bug: `createOptional` in
`packages/compiler/src/checker/types.ts:229` returns the element unchanged when
it is already optional, so the checker resolves `((string?)?)` and `string?` to
the same type. The damage is in the two places that read the annotation shape
rather than the resolved type:

- **The parser stays quiet.** A file written in a form the reference forbids
  compiles with no diagnostic, so the rule holds only for people who happen to
  write the marker in one of the two places instead of both.
- **The editor echoes the forbidden form back.** `namedAnnotationText` in
  `packages/lsp/src/symbols/signature-text.ts:65` peels one `type-optional` for
  the name and renders the rest, so hover and signature help print
  `titulo?: string?` — the exact spelling `parse-optional-position` exists to
  remove.

The same path serves fields, locals and parameters, so the hole is present in
all three.

## Steps

### T-01 - Decide the diagnostic and record it

**Agent:** architecture-engineer

- [ ] Choose between reusing `parse-optional-position` and adding a
      `parse-redundant-optional` code. The reused code keeps the reference table
      short; a new code lets the message and the fix name the actual mistake,
      which is a duplicate marker rather than a misplaced one.
- [ ] Whichever is chosen, keep the existing `name: Type?` message and quick fix
      title unchanged — a developer who already learned that wording should not
      have to relearn it.
- [ ] Record the decision in the plan before writing code, so the docs and the
      quick fix in T-03 and T-04 follow one answer.

**Decided:** a new code, `parse-redundant-optional`. The existing message —
`Write optional locals as "name?: Type", not "name: Type?".` — describes a
marker in the wrong place, which is not what `name?: Type?` is. The new message
names the actual mistake, `The marker on the name already allows "nil". Remove
the "?" after the type.`, and its quick fix deletes rather than moves. The
misplaced case keeps its code, its message and its fix title unchanged.

### T-02 - Report and normalise in the parser

**Agent:** architecture-engineer

- [ ] Report the diagnostic when the name carries a marker and the annotation is
      already `type-optional`, positioned on the redundant `?` on the type so the
      editor underlines the character to delete.
- [ ] Return a single `type-optional` node instead of a nested pair, so the AST
      shape of `name?: Type?` matches the shape of `name?: Type`.
- [ ] Leave `parse-invalid-optional` alone — a `?` with no annotation after it is
      still the thrown error it is today.
- [ ] Confirm the erasure path is unaffected: `eraseFrom(checkpoint)` must still
      strip the marker and the annotation from the emitted Lua for every spelling.

### T-03 - Offer the quick fix

**Agent:** architecture-engineer

- [ ] Add the repair to `FIXES` in
      `packages/lsp/src/features/quick-fixes.ts:120` — deleting the redundant `?`
      when the name already has one, rather than moving it.
- [ ] Keep `moveOptionalMarker` bound to the misplaced-marker case, and make sure
      neither fix can fire on the other's diagnostic.
- [ ] Verify the fixed source compiles, per the milestone 32 acceptance rule that
      every fixable diagnostic offers a fix whose result compiles.

### T-04 - Update the reference

### T-05 - Cover the three spellings

**Agent:** test-engineer

- [ ] Assert the AST for `name?: Type?` carries exactly one `type-optional`.
- [ ] Assert hover and signature help render `titulo?: string`, never

- [ ] Assert the quick fix output for both optional diagnostics parses clean.

## Acceptance Criteria

- [ ] `local titulo?: string? = nil` reports a diagnostic positioned on the `?`
      that follows the type.
- [ ] The same spelling reports in a class field, an interface field, an object
      type key and a parameter.
- [ ] `name: Type?` still reports `parse-optional-position` with an unchanged
      message, and `name?: Type` still reports nothing.
- [ ] The annotation for `name?: Type?` is a single `type-optional`, and the type
      the checker resolves is unchanged.
- [ ] Hover and signature help never print a `?` on both the name and the type.
- [ ] A quick fix is offered, its edit deletes the redundant marker, and the
      result parses with no diagnostic.
- [ ] `docs/en` and `docs/pt-br` agree with each other and with the shipped
      codes, and the fixable-diagnostic count in the roadmap matches `FIXES`.
- [ ] Every existing parser, checker and LSP test passes untouched.
