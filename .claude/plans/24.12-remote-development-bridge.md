# 24.12 - Add an authenticated remote development bridge

## Why this is not planned

The bridge serves a developer whose MTA server is somewhere they cannot read from
disk. That is not how this project is developed: the server runs in the
developer's own terminal, and `luam dev --start-server` already starts it, waits
for readiness, and follows `server.log` from the filesystem with structured
records and source positions.

Building it also needs the CLI to open a connection to an MTA server. The
product has moved away from that twice. [CLAUDE.md](../CLAUDE.md) forbids the
call in as many words, and `transport` — the manifest domain that configured a
server connection — was removed, with `ensure` syncs files, `dev --start-server`
restarts the server it owns recorded as what replaces it. This plan would have to
bring that surface back. Accepting it is a product decision about the network
invariant, not an implementation detail, and it is not worth making for a
workflow nobody here has.

The plan below stays as written. If the server ever moves off the developer's
machine, amend the invariant first, then follow it.

## Objective

Stream structured logs from a remote MTA development server through an authenticated, development-only bridge, with runtime inspection considered only as a separately gated phase.

## Options Considered

| Option | Deployment fit | Security | Decision |
|---|---|---|---|
| Read a remote log over a shared filesystem | Environment-specific | Depends on mount | Keep as external workaround |
| Poll logs through an HTTP resource endpoint | Fits existing MTA HTTP | Can be bounded and authenticated | Accept for logs |
| Open an arbitrary eval socket | Flexible | Remote code execution surface | Reject from initial release |

## Scope

- **In:** Threat model, bridge protocol, authentication, structured log cursoring, reconnect, redaction, rate and size limits, CLI transport, development-only assembly, tests, and documentation.
- **Out:** Production telemetry, background analytics, arbitrary expression evaluation, pausing execution, breakpoints, and a full DAP implementation.

## Steps

### T-01 - Record the remote trust model

**Agent:** security-engineer

- [ ] Define client, CLI, MTA resource, network, token, replay, log-content, and denial-of-service threats.
- [ ] Compare pull and push protocols and require TLS for non-loopback communication.
- [ ] Specify development-only enablement and automatic exclusion from production builds.

### T-02 - Define the bridge protocol

**Agent:** architecture-engineer

- [ ] Version request and response envelopes with resource, environment, level, source position, sequence cursor, and bounded message text.
- [ ] Support reconnect and deduplication without unbounded server retention.
- [ ] Keep the local log follower as the default path.

### T-03 - Implement secure transport

**Agent:** security-engineer

- [ ] Load credentials only from environment-backed configuration and redact them from diagnostics, logs, traces, and generated maps.
- [ ] Authenticate every request, resist replay where practical, rate-limit endpoints, and validate all fields server-side.

**Agent:** cli-engineer

- [ ] Add remote bridge selection under `development.logs` and integrate cancellation, retry, formatting, and offline fallback behavior.

### T-04 - Verify adversarial behavior

**Agent:** test-engineer

- [ ] Cover invalid credentials, replay, oversized records, cursor gaps, reconnects, duplicate responses, redaction, cancellation, and production output exclusion.
- [ ] Use a mock transport; tests perform no real network calls.

## Acceptance Criteria

- [ ] Remote logs require explicit development configuration and authenticated requests.
- [ ] Credentials and sensitive configured values never appear in output or generated artifacts.
- [ ] Disconnects resume from a bounded cursor without duplicate terminal records.
- [ ] `luam build` and normal runtime helpers contain no bridge code.
- [ ] Expression evaluation remains unavailable until a separate DAP and security ADR is accepted.
