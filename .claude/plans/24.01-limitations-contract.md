# 24.01 - Classify and align Luam limitation contracts

## Objective

Make every published limitation accurately describe current behavior and distinguish temporary implementation gaps from deliberate product and platform boundaries.

## Context

The reference page describes ten limitations, but the README still says that no narrowing exists and parts of the editor guidance predate workspace scanning and declaration-triggered rechecks. The planning template also names `.claude/plans/` while the repository stores project memory under `.claude/`.

## Decision

Use four labels: planned, design boundary, upstream constraint, and platform constraint. Keep erased annotations, opaque `config.lua`, and one environment per file as default contracts; future opt-in features must not silently change those defaults.

## Scope

- **In:** EN/PT-BR limitation pages, README summary, editor guidance, architecture decisions, plan-path guidance, version statements, and links to milestone 24.
- **Out:** Compiler, runtime, CLI, or LSP behavior changes.

## Steps

### T-01 - Record product boundaries

**Agent:** architecture-engineer

- [ ] Compare keeping each boundary, making it opt-in, and removing it against correctness, Lua 5.1 compatibility, MTA semantics, security, and developer experience.
- [ ] Record ADRs for erased-by-default types, opaque native Lua configuration, and file-level environments.
- [ ] State that block-level environments cannot preserve arbitrary locals, closures, control flow, or effects across MTA scripts.

### T-02 - Align public guidance

**Agent:** documentation-engineer

- [ ] Correct the README narrowing and LSP summaries.
- [ ] Give each limitation a classification, workaround, owning plan, and version.
- [ ] Keep EN and PT-BR structurally and semantically equivalent.
- [ ] Correct the plan-location references or formally migrate project memory in a separate change.

### T-03 - Prevent drift

**Agent:** test-engineer

- [ ] Extend documentation verification to check locale parity and limitation-plan links.
- [ ] Add assertions for claims that can be derived from fixtures or package metadata.

## Acceptance Criteria

- [ ] No active page claims that identifier narrowing or workspace scanning is absent.
- [ ] All ten limitations have one classification and one explicit product decision.
- [ ] File-level environments remain the supported model and no roadmap item promises semantics the MTA cannot execute.
- [ ] `pnpm docs:verify` passes.
