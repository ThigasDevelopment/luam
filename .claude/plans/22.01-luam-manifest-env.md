# 22.01 - Replace `luam.json` with `.luam.manifest` environment modules

## Objective

Replace the JSON-only project configuration with a discoverable `.luam.manifest`
module. The manifest may export a static configuration object or a function that
receives a small, explicit environment context. It must produce the same validated
`LuamConfig` consumed by the CLI, without treating `luam.json` as a fallback.

## Context

Today the CLI resolves only `luam.json`, parses it with `JSON.parse`, then validates
the resulting object. The LSP independently reads the same JSON file to discover the
`oop` setting. The template, `init`, VS Code activation, tests, examples, snippets,
and EN/PT-BR documentation also expose that filename.

The new contract should work like modern tool manifests: it is discovered from the
workspace root, supports environment-sensitive values without duplicating JSON files,
and keeps configuration validation separate from evaluation. A project manifest is
trusted project code, but it must not run in the editor process.

## Proposed Contract

The canonical file is exactly `.luam.manifest` in the project root. Its content is an
ESM module evaluated by the CLI through the project-local Node runtime:

```js
export default ({ mode, env }) => ({
    name: 'luam-demo',
    outDir: mode === 'development' ? 'build-dev' : 'build',
    transport: env.LUAM_MTA_PASSWORD
        ? { kind: 'http', resource: 'luam-sync', username: 'luam', passwordEnv: 'LUAM_MTA_PASSWORD' }
        : { kind: 'none' },
})
```

The default export may instead be a plain object. The function receives only:

| Value | Meaning |
| --- | --- |
| `mode` | `development` for `dev` and `ensure`; `production` for `build`; otherwise the command name, such as `check` or `trace`. |
| `env` | Read-only copy of the process environment, exposed so manifests can select values by explicit variable name. |
| `root` | Absolute project root, for deterministic path composition when necessary. |

The manifest must export exactly one default value. The loader rejects an unsupported
extension, an import/evaluation failure, a non-object function result, or an async
result with new `config-*` diagnostics. Configuration validation remains the sole
authority for defaults, unknown fields, path safety, helper names, and transport
credentials.

## Decisions Required Before Implementation

| Decision | Recommended choice | Rationale |
| --- | --- | --- |
| Manifest syntax | ESM default export | Fits the workspace's ESM packages and supports static and dynamic configuration without inventing a DSL. |
| Execution boundary | Isolated child process for CLI evaluation | Project code must not execute inside the long-lived CLI watcher or VS Code/LSP process. Serialize only the resulting JSON object. |
| LSP behavior | Never execute the manifest | Read an optional generated settings snapshot or use defaults until the language server receives validated settings from the extension. Prevents arbitrary workspace code execution in the editor. |
| Legacy support | Breaking change, no `luam.json` fallback | The requested rename is unambiguous, avoids two sources of truth, and makes missing-manifest diagnostics actionable. |
| Explicit manifests | `--manifest <path>` replaces `--config <path>` | The name describes the artifact and accepts an alternate `.luam.manifest` file for deployment profiles. |

Before coding, record these decisions in an ADR. If the repository must support users
who cannot run ESM project modules, reconsider the first two choices rather than
adding an undocumented second syntax.

## Scope

- **In:** Default discovery, explicit manifest selection, isolated module evaluation,
  validation hand-off, CLI/LSP integration, scaffolding, VS Code discovery, tests,
  documentation, examples, snippets, and migration guidance.
- **Out:** Loading TypeScript manifests, searching parent directories, merging multiple
  manifests, watch-mode hot reload semantics beyond the existing configuration reload,
  and retaining `luam.json` compatibility.

## Risks And Mitigations

| Risk | Mitigation |
| --- | --- |
| Executing a project manifest can access the developer machine. | Use a short-lived child process, document the trust boundary, never execute it in LSP/extension, and expose only its serialized result to the parent process. |
| ESM resolution varies by project package settings. | Define and test the dedicated evaluator protocol for `.luam.manifest`; do not rely on Node auto-detecting an extensionless module. |
| Environment access accidentally leaks passwords in diagnostics or logs. | Never serialize context back to the parent, redact evaluator failures, and retain `passwordEnv` validation as the only credential resolution path. |
| CLI and LSP disagree on OOP. | Establish one validated settings channel in T-04 before removing the JSON reader. |
| A breaking rename strands existing projects. | Provide an explicit migration guide and a precise missing-manifest diagnostic; do not retain dual discovery indefinitely. |
