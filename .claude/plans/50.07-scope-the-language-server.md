# 50.07 - Scope the language server to the nearest manifest

## Objective

Make the language server analyse each resource against its own manifest, so that
opening a directory of resources — the layout this milestone blesses — is
correct rather than merely tolerated.

## What is actually broken

[WorkspaceIndex](../../packages/lsp/src/workspace/workspace-index.ts) is
single-project by construction. It picks one manifest for everything:

```ts
private manifest(): DocumentAnalysis | null {
    return this.all().find((analysis) => analysis.manifest !== null) ?? null;
}
```

`settings`, `env`, `project` and `libraries` are one value each, derived from
whichever manifest that `find` reached first — which depends on scan order, so
the answer is not even stable. Three consequences, all reachable today by opening
a folder that holds two resources:

- **Declarations leak.** `ambientFor` merges the surface of every other analysed
  file, filtered only by environment and test-ness. `resource-a` sees
  `resource-b`'s globals, gets completion for them, and reports no error when it
  calls one.
- **Compiler options are borrowed.** `resource-b` is checked under
  `resource-a`'s `strict`, `oop` and `noImplicitGlobals`.
- **Every file's side is wrong.** `run` resolves the environment with
  `this.settings.resolver.side(relative)`, where `relative` is relative to the
  *workspace* roots. With the parent folder open, `resource-a/src/server/main.luam`
  is tested against `src/server/**/*.luam` and matches nothing, so a server file
  is analysed as shared.

The third is the one a developer notices first, and it has nothing to do with
`.luam.server` — it is what "open the resources folder" does today.

## Scope

- **In:** Per-project scoping inside `WorkspaceIndex`, keyed on the nearest
  manifest above each file.
- **Out:** Reading `.luam.server` in the language server. The scoping rule is the
  nearest `.luam.manifest`, so a plain folder of resources with no workspace file
  is fixed by this task too. The server file's own editor support is 50.08.

## The rule

A file belongs to the project rooted at the nearest ancestor directory holding an
analysed `.luam.manifest`. A file with no manifest above it keeps
`DEFAULT_PROJECT_SETTINGS`, which is what a lone `.luam` file gets today and must
keep getting.

## Steps

- [ ] Introduce a project key — the directory of the owning manifest, or the
      empty string for none — and a resolver from a file path to that key, using
      the longest matching ancestor so a nested project wins over an outer one.
- [ ] Replace the single `settings`, `env`, `project`, `libraries` and `key`
      fields with maps from project key to those values. `applySettings` becomes
      per project and returns which project changed.
- [ ] Make `relative` project-relative. `run` computes it against the owning
      project's root rather than against `this.roots`, so `sources` patterns match
      what they were written to match. This is the fix for the misclassified side
      and should be verified with a real two-resource fixture.
- [ ] Filter `ambientFor` to the same project. Cross-project visibility is not a
      feature to preserve; a resource's surface is its own files, exactly as the
      compiler treats it.
- [ ] Scope `rerunOthers` and `rerunDependents` to the affected project. Saving a
      manifest in one resource must not re-analyse the whole directory — the cost
      of that is what makes a large workspace unusable.
- [ ] Load the environment and the library index per project.
      `loadProjectDeclarations` and `loadLibraries` already take a root; give each
      one its own instead of a merged root list.
- [ ] Keep the memory shape honest: one map keyed by project, cleared when the
      last file of a project is removed, so closing a resource does not leak its
      settings for the life of the session.

## Acceptance Criteria

- [ ] With `resource-a` and `resource-b` open under one folder, a global declared
      in `resource-a` is not offered in completion in `resource-b` and calling it
      there reports an unresolved reference.
- [ ] `compiler = { strict = true }` in one manifest does not check the other
      resource's files.
- [ ] `resource-a/src/server/main.luam` is analysed as a server file when the
      opened folder is the parent of `resource-a`.
- [ ] A `.luam` file with no manifest above it still analyses under the default
      settings.
- [ ] A nested project — a manifest inside a directory that also has one above it
      — is scoped to the nearer manifest.
- [ ] Saving one manifest re-analyses only that project's files.
- [ ] Opening a single resource directory behaves exactly as it does today; every
      existing LSP test passes unchanged.
- [ ] `pnpm -r test`, `pnpm typecheck` and `pnpm conventions` pass.
