# 16.01 - Stream MTA development logs to the Luam terminal

> File: `.claude/plans/16.01-mta-development-logs.md`

## Objective

Give `luam dev` one terminal stream for server and client resource logs without
changing the normal build or deployment runtime.

## Scope

- **In:** Server-log tailing, a development-only client relay helper, structured
  log records, CLI formatting, configuration, tests, and documentation.
- **Out:** Runtime value decorations in VS Code, arbitrary expression evaluation,
  engine logs that cannot be attributed to the resource, remote log collection,
  and changes to `luam build` or `luam ensure`.

## Options Considered

| Option | Correctness | Maintainability | Developer experience | Decision |
|---|---|---|---|---|
| Parse the server console process output | Depends on how the server was launched and cannot see a separately started server | Couples Luam to process ownership | Inconsistent across local setups | Reject |
| Send resource events directly to a local HTTP receiver | Can carry structured records but adds a network listener and outbound resource HTTP | Conflicts with the project network boundary | Requires ports, tokens, and client reachability | Reject |
| Relay client logs through MTA events and tail the server log | Uses MTA's existing client-to-server channel and the configured server path | Keeps the CLI as a local reader with no new network path | One terminal stream for both environments | Accept |

## Behavior Contract

`luam dev` requires `serverPath` and runs the existing build, sync, restart, and
watch workflow with development log capture enabled. It writes the generated
development helper only to the synchronized server resource. `luam build` and
`luam ensure` remain byte-for-byte and behaviorally unchanged.

The server log watcher reads appended lines only. It classifies native server
records for the active resource where the MTA log format exposes a resource name.
The generated client helper wraps the resource's `outputDebugString`, calls the
original function, and relays the same record to its paired server helper through
an MTA event. The server helper writes a delimited record through
`outputDebugString`; the watcher recognizes and renders it.

The first release does not claim to capture MTA engine messages or logs emitted by
other resources. A client message is visible only while the generated helpers are
loaded and the client can trigger the resource event.

## Steps

- [x] Add `dev` to the CLI argument parser, usage text, dispatch, and command
      tests. Require `serverPath`; reuse the ensure runner's successful build,
      server write, restart, and watch semantics instead of duplicating them.
- [x] Add a server-log follower under `packages/cli/src/logging/` that resolves
      the MTA log location from `serverPath`, starts at EOF, handles file
      rotation or truncation, and stops with the command abort signal. Keep log
      parsing isolated from command orchestration.
- [x] Define a small internal log record shape with `timestamp`, `environment`,
      `level`, `message`, `resource`, and optional source location. Parse known
      MTA server lines conservatively; render unknown lines as plain server
      output rather than guessing fields.
- [x] Add a development-only runtime helper pair. The client helper preserves
      `outputDebugString` behavior and relays records with `triggerServerEvent`.
      The server helper validates event argument types, rate-limits client input,
      and emits an unambiguous structured marker for the CLI log follower.
- [x] Extend the runtime helper catalog and resource assembly with an explicit
      development-only helper selection path. Load the server helper before
      server scripts and the client helper before client scripts; neither helper
      may be selected by normal compilation or by the `helpers` configuration.
- [x] Add a log formatter to the CLI reporter that renders stable lines such as
      `[14:22:07][client][warn] Missing vehicle model`. Respect existing TTY,
      `--no-color`, and `NO_COLOR` behavior, and clear transient progress before
      writing a log line.
- [x] Add an opt-in `development.logs` configuration section for default log
      capture and client relay limits. Validate its fields, preserve a disabled
      default, and let `luam dev` enable capture without requiring the section.
- [x] Document prerequisites, server-log limitations, client relay behavior,
      commands, configuration, and the distinction between development logs and
      future runtime value observations.
- [x] Update the code graph for every new CLI logging module, runtime helper,
      test file, and this plan. Run `pnpm --filter @luam/cli typecheck`,
      `pnpm --filter @luam/cli test`, `pnpm --filter @luam/runtime test`, and
      `pnpm typecheck`.

## Acceptance Criteria

- [x] `luam dev --no-watch` without `serverPath` reports a command diagnostic,
      writes no resource, and starts no log watcher.
- [x] With `serverPath`, `luam dev` prints appended server records for the active
      resource without printing prior log history or duplicating a line after a
      rebuild.
- [x] A client `outputDebugString` call remains visible in the MTA client debug
      console and produces one corresponding `[client]` record in the Luam
      terminal.
- [x] An invalid, oversized, or rate-limited client event does not crash the
      server helper, write arbitrary content, or flood the terminal.
- [x] Log formatting emits no ANSI escape sequences when output is piped, when
      `NO_COLOR` is set, or when `--no-color` is passed.
- [x] `luam build` and `luam ensure` generate no development helper files and
      retain their existing resource output and restart behavior.
- [x] Unit tests cover parsing, truncation and rotation, record formatting,
      helper selection, configuration validation, command cancellation, and
      client relay record validation.
