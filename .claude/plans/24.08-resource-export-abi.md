# 24.08 - Define and verify a typed resource export ABI

## Objective

Generate stable export contracts and type-check statically identifiable calls between declared resource dependencies.

## Options Considered

| Option | Portability | Precision | Decision |
|---|---|---|---|
| Parse dependency source projects directly | Low | High | Reject |
| Publish declaration files manually | High | Depends on authors | Support as fallback |
| Generate a versioned ABI artifact | High | High | Accept |

## Scope

- **In:** ABI schema, signature serialization, dependency discovery, side and HTTP metadata, static `call` checking, dynamic fallback, compatibility diagnostics, cache integration, and documentation.
- **Out:** Downloading dependencies, package management, runtime RPC replacement, and rejection of dynamic calls that cannot be proven.

## Steps

### T-01 - Record the ABI contract

**Agent:** architecture-engineer

- [x] Compare JSON, `.d.luam`, and generated Lua metadata for determinism, readability, and schema evolution.
- [x] Version the selected artifact and define resource identity, export name, side, HTTP flag, parameters, returns, and optional documentation.
- [x] Define compatibility rules and behavior for missing, stale, or unsupported ABI versions.

### T-02 - Emit provider contracts

**Agent:** architecture-engineer

- [x] Preserve checked export signatures in manifest contributions.
- [x] Emit the ABI only after successful checking and keep it outside the runnable resource unless explicitly required.
- [x] Detect duplicate and environment-invalid exports before artifact generation.

### T-03 - Resolve consumer calls

**Agent:** architecture-engineer

- [x] Resolve ABI files only for manifest `dependencies` through explicit project-relative configuration or workspace convention.
- [x] Type-check literal resource and export names, arguments, returns, and environment.
- [x] Keep dynamic names conservative and configurable without claiming verification.

### T-04 - Secure and test the boundary

**Agent:** security-engineer

- [x] Treat ABI files as untrusted input with size, depth, schema, path, and version limits.

**Agent:** test-engineer

- [x] Cover provider changes, stale consumers, missing contracts, dynamic calls, side mismatches, HTTP exports, cycles, and deterministic artifacts.

## Acceptance Criteria

- [x] A literal call to a declared dependency receives exact argument and return checking.
- [x] A changed provider signature invalidates only consumers that resolved that export.
- [x] Dynamic resource or export names remain compilable but are visibly unverified.
- [x] Invalid ABI input cannot escape project roots, exhaust unbounded resources, or produce partial output.
