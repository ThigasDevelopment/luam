# 30.6 - Automate refresh proposals without trusting the wiki

## Objective

Make the catalog track the wiki on a schedule, while treating the wiki as what
it is: a source anyone on the internet can edit.

## Root Cause

Even with a live source, a manual refresh only happens when someone remembers.
But the obvious automation — regenerate and merge — would let any wiki edit
reach the type catalog unreviewed. The refresh has to be automatic and the
adoption has to be manual.

## Scope

- **In:** A scheduled workflow, a structured PR summary, and the safeguards that
  make an unreviewed wiki edit unable to change shipped behaviour.
- **Out:** Auto-merge, in any form and behind any condition. Also out: fetching
  during a build, which stays forbidden.

## Steps

### T-01 - Schedule the refresh

**Agent:** github-engineer

- [ ] Run weekly and on manual dispatch: fetch the snapshot, regenerate, then
      typecheck and test.
- [ ] Fetch incrementally by `revid`, so an unchanged wiki costs one list request
      and produces no diff.
- [ ] Pin every action to a commit SHA and grant the workflow the minimum
      permissions that let it open a PR.

### T-02 - Make the PR reviewable

**Agent:** github-engineer

- [ ] Summarise the diff in four sections: functions added, existing signatures
      changed, environments changed, and functions that disappeared from the
      wiki.
- [ ] Order the summary by blast radius. A changed signature can break code that
      compiles today; an added function cannot.
- [ ] Link each entry to the wiki page revision it came from, so a reviewer can
      check the claim without leaving the PR.

### T-03 - Guard against a bad edit

**Agent:** github-engineer

- [ ] Fail the run when the parse rate falls below the bar 30.3 set, rather than
      emitting a catalog degraded by a template change or a vandalised page.
- [ ] Never delete a declaration because it vanished from the wiki. Report it
      and leave the catalog alone. A blanked page must not remove a function
      from users' type information.
- [ ] Fail the run when the diff exceeds a sanity threshold, since a mass change
      is far more likely to be breakage upstream than a real MTA release.
- [ ] Keep `catalog-overrides.ts` applied after the parse, so a hand-written
      correction cannot be undone by an automated refresh.

### T-04 - Keep the boundary intact

**Agent:** github-engineer

- [ ] Confirm the fetch runs only in this workflow and the `fetch-wiki` script,
      never from the compiler, the CLI build path, or a test.
- [ ] Assert in CI that a build with no network still succeeds.

## Acceptance Criteria

- [ ] The workflow opens a PR and never merges one, under any condition.
- [ ] A simulated bad edit — a blanked page, a removed function, a broken
      template — produces a report or a failed run, never a catalog deletion.
- [ ] A parse-rate regression fails the run.
- [ ] An unchanged wiki produces no PR.
- [ ] Compiler packages make no network call, and an offline build succeeds.
- [ ] Actions are SHA-pinned and permissions are minimal.
