# 29.07 - Document the theme and its contract

## Objective

Record why the theme looks the way it does, teach the one rule that makes it
readable, and tell a user of each editor how to install it — in both languages
the documentation ships.

## Scope

- **In:** An ADR for the contract, a theme page in `docs/en` and `docs/pt-br`,
  the editors page update, the `packages/theme` README, the extension README,
  and the roadmap and code-graph entries.
- **Out:** Marketing copy and screenshots of every editor. One dark and one light
  sample of the same file is enough to show the system; more images age faster
  than the theme changes.

## Steps

### T-01 - Write ADR-020

**Agent:** documentation-engineer

- [ ] Context: the extension shipped a grammar and no theme, so Luam was read
      through themes designed for other languages, and the elements Luam adds to
      Lua — the erased type layer, environments, decorators, the MTA surface —
      were painted as if they were ordinary identifiers.
- [ ] Options considered, with the reason each was rejected or chosen: no theme
      and better scopes only, rejected because no scope split separates a native
      from a user function; a maximalist theme with a hue per element, rejected
      as unreadable and unmaintainable at seventy roles; a minimal palette with
      globally unique styles, rejected as arithmetically impossible under four
      hues; and the confusion-set contract that was chosen.
- [ ] Decision: four syntax hues, three axes, distinctness scoped to confusion
      sets, cyan for the erased layer and violet for what emits, one generator
      and one role table for every editor.
- [ ] Consequences, honestly: a new language element must be added to the role
      table and placed in a confusion set before it can be coloured, which is
      friction by design; the TextMate targets are partially collapsed because
      the format has no semantic tokens; JetBrains is unserved until a plugin
      exists; and semantic highlighting adds per-keystroke work in the LSP, whose
      measured cost 31.3 records.

### T-02 - Write the theme page

**Agent:** documentation-engineer

- [ ] Lead with the rule a reader can use immediately: cyan is compile-time and
      disappears from the Lua; violet is what runs. Everything else is detail.
- [ ] Show one annotated sample — the same file in both modes — with the elements
      labelled. The sample is generated from the 31.6 fixture so it cannot drift
      from what the theme does.
- [ ] Explain the environment tint and why the directive line breaks the rule.
- [ ] List the elements and their colours as a table, generated from the role
      table rather than transcribed.

### T-03 - Update the editors page

**Agent:** documentation-engineer

- [ ] Install instructions per editor: VS Code picks it from the theme picker;
      Zed, Neovim, and the TextMate family install the exported file, and each
      needs the language server configured, which the page already covers.
- [ ] State plainly what each editor gets. VS Code and Zed and Neovim get the
      full reading; the TextMate family gets the grammar layer only.
- [ ] Record the JetBrains position with its reason, so the question is answered
      rather than reopened.

### T-04 - Write the package READMEs

**Agent:** documentation-engineer

- [ ] `packages/theme/README.md`: what the package is, why the role table is the
      only place a colour lives, how to add a role, and the instruction that
      generated files are never hand-edited.
- [ ] `packages/vscode/README.md`: the themes are included and how to select
      them, plus the semantic highlighting setting.

### T-05 - Mirror into pt-br

**Agent:** documentation-engineer

- [ ] Translate the theme page and the editors changes, keeping the English
      source authoritative and the structure identical.
- [ ] Update `docs/translation-allowlist.json` for any term the theme introduces
      that must stay in English — the scope names, the role ids, and the
      semantic token names are identifiers, not prose.

### T-06 - Update the project records

**Agent:** documentation-engineer

- [ ] Add the Milestone 29 section to `roadmap.md` and keep every task status in
      step with its plan file.
- [ ] Add `packages/theme` to the package layout in `architecture.md`, with one
      line on its boundary: data and pure functions, depended on by nothing in
      the compile path.
- [ ] Add and update the code-graph nodes every task in the milestone names.
