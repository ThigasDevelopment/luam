# 24.1 - Turn the manual into an interactive product experience

> File: `.claude/plans/24.1-documentation-experience-documentation-engineer.md`

## Objective

Make the Luam manual demonstrate the complete development loop before asking a
reader to install anything: understand the value on the landing page, compile
real Luam in a browser playground, follow progressive examples, and inspect
authentic CLI, MTA, and VS Code evidence.

## Scope

- **In:** The en-US and pt-BR landing pages, an offline static playground,
  example and recipe information architecture, realistic MTA use cases,
  reproducible CLI and MTA logs, author-provided VS Code screenshots,
  responsive and accessible presentation, documentation validation, and usage
  measurement that does not collect source code.
- **Out:** Executing generated Lua in the browser, embedding an MTA server,
  adding an API or application backend, authentication, cloud persistence,
  collaborative editing, replacing the VS Code extension, translating product
  output, or turning the reference manual into a tutorial-only site.

## Baseline

- VitePress already publishes equivalent `/en/` and `/pt-br/` trees with local
  search, a locale picker, a custom theme, and mobile and dark-mode support.
- Locale home pages currently use the standard VitePress hero, four feature
  cards, one short source sample, and a routing table. They describe Luam but do
  not show the source-to-diagnostic-to-Lua loop.
- Eleven paired recipes already include shared source snippets. `docs:snippets`
  checks each project, while `docs:outputs` captures actual CLI check, build,
  output-tree, manifest, and expected-error output.
- MTA runtime output and development-loop timing shown in recipes are currently
  hand-authored examples. The site has no provenance convention for runtime
  evidence and no editor screenshots.
- The compiler exposes a source-level `compile` function, but no browser bundle
  or worker boundary exists. Browser compatibility and bundle size must be
  measured before the playground becomes a landing-page dependency.

## Product Narrative

The primary journey is `write -> understand diagnostics -> inspect emitted Lua
-> run in MTA`. Every prominent page should reinforce one part of that journey.

| Audience | First proof | Next action |
| --- | --- | --- |
| Lua/MTA developer | Familiar Lua blocks plus useful types | Edit and compile the hero example |
| TypeScript/Luau developer | Types, classes, completion, and early diagnostics | Open the language tour |
| Resource maintainer | Generated `meta.xml`, environment checks, and readable Lua 5.1 | Follow a real use case |
| Tooling evaluator | Same checker in the browser, CLI, and editor | Install the CLI and extension |

The first screen must answer what Luam is, why it is safer than plain Lua for an
MTA resource, what it emits, and what the reader can try without installation.

## Playground Decision

| Option | Correctness | Operations | UX | Decision |
| --- | --- | --- | --- | --- |
| Bundle the compiler for a browser Web Worker | Runs the real parser, checker, and emitter without blocking the page | Static GitHub Pages artifact; no service | Immediate and works offline after load | Accept, subject to a bundle budget spike |
| Call a hosted compilation API | Can run the CLI implementation | Adds backend, abuse controls, cost, and a network dependency | Supports project builds but can fail remotely | Reject |
| Display precomputed transformations | No untrusted execution | Smallest artifact | Looks interactive but does not validate edits | Reject |

The first playground compiles one virtual `.luam` file. It lets the reader choose
`shared`, `server`, or `client`, toggle OOP when supported by the example, and
inspect either emitted Lua or sorted diagnostics. It does not assemble a resource
or run Lua. A Web Worker owns compilation, receives plain serializable messages,
and is terminated and recreated after a time budget. Input length and queued
requests are bounded; stale responses are ignored. User source never leaves the
browser and is never sent to analytics.

If the browser bundle cannot stay below 500 kB compressed without maintaining a
second compiler implementation, ship the playground on a dedicated route and
lazy-load it from the landing page. Record the measured result and final loading
strategy in this plan before implementation continues.

## Content Model

Use one canonical, verified project for each example and render its files in both
locales. A recipe follows this order:

1. Outcome: show what appears in MTA before explaining implementation details.
2. Prerequisites and estimated completion time.
3. Small file tree with the active environment made explicit.
4. Complete verified source, split into numbered conceptual steps only when the
   full file would hide the teaching point.
5. `luam check` and `luam build` commands with captured output.
6. Authentic MTA or `luam dev` output, when the example has runtime behavior.
7. One intentional failure with the exact diagnostic and a correction.
8. Explanation of generated Lua or `meta.xml` only where the transformation is
   relevant to the lesson.
9. A next step linking to a slightly more capable example and the canonical
   reference pages.

Use callouts sparingly for environment, security, and limitations. Keep API
names, diagnostics, commands, paths, source, and output in English in both
locales. Translate only explanatory prose and navigation.

## Real Use Cases

Build three end-to-end projects from ordinary MTA work rather than isolated
syntax features:

| Use case | Product proof | Required evidence |
| --- | --- | --- |
| Moderation command | Typed command arguments, ACL-safe server validation, player feedback | Successful command, rejected input, server log, and generated manifest |
| Vehicle interaction | Shared model, server-authoritative event, client UI feedback, environment checking | Client and server `luam dev` records plus one wrong-environment diagnostic |
| Persistent session boundary | Typed serialization shape, defensive external data validation, reconnect behavior without claiming a database framework | Sanitized lifecycle logs and an explicit mock/storage-boundary note |

Each use case must run on the documented MTA version, contain no private
framework dependency, and live under the existing verified snippet source. Use
the smallest scenario that demonstrates the real boundary. Do not present a
database, framework, or API as part of Luam.

## Evidence Policy

- Store machine-generated compiler captures under `docs/snippets/output/` and
  continue regenerating them with `pnpm docs:capture`.
- Store reviewed runtime sessions under `docs/evidence/<case>/` with a short
  metadata file containing Luam version or commit, MTA version, OS, capture date,
  exact command, source project, and redactions applied.
- Preserve authentic ordering and wording. Replace only usernames, absolute home
  paths, IP addresses, hostnames, and secrets with explicit tokens such as
  `<USER>` or `<SERVER_IP>`; never invent timestamps, timings, or runtime lines.
- Label manually captured MTA output as a recorded session. Keep generated CLI
  captures visually distinct from terminal transcripts that depend on an MTA
  installation.
- Reject evidence containing passwords, environment values, access tokens,
  private server addresses, player serials, or unrelated chat and console data.

## Screenshot Set

The author supplies screenshots from their own VS Code session after opening the
canonical use-case workspace. Capture only images that prove a feature:

| Asset | Visible proof | Placement |
| --- | --- | --- |
| `editing-and-completion` | `.luam` syntax, a short real file, and MTA-aware completion | Landing page and editor guide |
| `diagnostic-and-hover` | One useful diagnostic, source range, and typed hover | Landing proof section and troubleshooting |
| `ensure-and-logs` | Editor beside the integrated terminal running `luam dev` with matching server/client records | Daily development and real use case |

Use a clean profile, repository theme, 1440-1920 px source capture, 2x density
when available, and lossless PNG for legible code. Crop to the relevant editor
area but retain enough UI to establish that it is VS Code. Hide notifications,
accounts, unrelated tabs, absolute paths, server addresses, player data, and
tokens before capture. Store source images under
`docs/public/images/editor/`; provide meaningful localized captions and alt text,
explicit dimensions to prevent layout shift, and a click-to-view full image.
Screenshots supplement text and never contain the only explanation or command.

## Additional Workstreams

### Migration Guide

Add paired `/en/guide/migration` and `/pt-br/guide/migration` pages organized by
released version. Start with the path from `0.1.x` to `0.7.0`, including every
breaking syntax, configuration, CLI, output-layout, and editor change that needs
an author action. Each entry shows `before`, `after`, impact, and a link to the
canonical reference and product changelog. The guide must not duplicate ordinary
release notes or imply that a source rewrite is needed when compatibility holds.

### Language Comparison

Add a concise comparison of Luam, Lua 5.1, Luau, and TypeScript to the landing
page with a fuller paired guide page. Compare only decisions a developer needs to
choose or learn the language: block syntax, type erasure, target runtime,
comments, classes, nullability, module and environment model, MTA catalog, and
generated output. Cite authoritative language documentation and avoid subjective
performance or popularity claims.

### Generated Output Explorer

Extend the playground with an inspectable `Luam -> Lua 5.1` view. Link authored
source ranges to generated lines where source mappings exist; classify erased
types, lowered syntax, runtime helper requirements, and manifest contributions
without inventing a textual diff when no exact mapping exists. The explorer must
use compiler results, never a second transformation model, and explain that the
single-file playground does not assemble a complete resource.

### Example Downloads

Generate deterministic ZIP archives from the same canonical projects under
`docs/snippets/` that CI checks. Each recipe and real use case gets a download
action carrying the current source, manifest, and safe sample assets, but never
captured output, local environment files, build artifacts, credentials, or MTA
server data. Archive generation must normalize paths and timestamps, reject path
traversal, and produce a checksum manifest so published downloads are auditable.

### MTA API Explorer

Generate a searchable static API explorer from `@luam/mta-types`, not copied
Markdown. Support server, client, and shared filters; procedural and OOP names;
signatures, parameter and return documentation; element inheritance; and links
to the upstream MTA Wiki. Display the pinned catalog source/version and mark
missing upstream prose rather than filling it with guessed descriptions. Keep
the generated data lazy-loaded so reference pages and the landing page remain
small.

### Diagnostic Catalog

Turn the diagnostic reference into a generated catalog backed by the compiler's
diagnostic definitions and verified failing fixtures. Each entry includes the
stable code, phase, severity, exact message shape, minimal failure, corrected
source, and version introduced when known. Add stable anchors suitable for links
from CLI and editor diagnostics, but treat automatic editor links as separate
product work unless the current diagnostic contract already exposes a URL.

### Documentation Integrity

Expand validation beyond locale parity and compilation. Check internal and
external links, orphan pages, navigation coverage, missing assets, image alt text
and dimensions, duplicate anchors, unused snippets, missing snippet references,
unsupported terminology differences between locales, and generated artifacts
that drift from their source. External checks should cache results, retry
conservatively, and distinguish a remote outage from a broken local link so
third-party availability does not make every pull request flaky.

### How Luam Works

Add a paired, user-facing architecture page with one accessible diagram covering
source discovery, environment resolution, parsing, checking, emission, resource
assembly, CLI, LSP, and browser playground reuse. Explain practical consequences
such as no output on error and matching diagnostics across tools. Link to the
internal architecture document for contributors instead of exposing package
internals or turning the page into maintainer documentation.

### Page Feedback

Add a privacy-preserving `Was this page helpful?` control and a report link
pre-filled with the documentation URL, locale, rendered Luam version, and page
title. Prefer a GitHub issue URL requiring explicit user submission; do not send
playground source, referrers, free-form text, identifiers, or telemetry in the
background. If anonymous voting requires a backend or third-party analytics,
defer voting and ship only the explicit issue flow.

## Delivery Order

1. Audit and content contract.
2. Compiler browser spike and playground contract tests.
3. Landing page and three playground presets.
4. Recipe restructuring and real use-case projects.
5. Runtime evidence and author-owned VS Code screenshots.
6. Migration, comparison, downloads, and user-facing architecture.
7. Generated API and diagnostic explorers plus integrity validation.
8. Accessibility, feedback, responsive checks, usability test, and release validation.

The landing page may ship before all use cases, but it must not link to placeholder
content. The playground may ship only after parity, worker-failure, and input-bound
tests pass. Screenshot slots remain absent until reviewed real images exist.

## Acceptance Criteria

- [ ] A first-time visitor can state that Luam checks typed `.luam` and emits an
  MTA-ready Lua 5.1 resource after viewing the first desktop or mobile screen.
- [ ] The landing page exposes one primary installation action and one immediate
  no-install playground action without hiding locale, theme, or navigation.
- [ ] Playground presets and arbitrary bounded edits use the real compiler in a
  worker, match Node compiler results, never execute output, make no source-data
  requests, and recover visibly from timeout or worker failure.
- [ ] The playground is lazy-loaded, its compressed size is documented, and it
  does not regress non-playground documentation pages or local search.
- [ ] en-US and pt-BR have equivalent landing, playground, learning-path, and use
  case routes; product source and output remain unchanged between locales.
- [ ] Every recipe states an outcome before code, renders verified canonical
  source, shows expected output or behavior, includes one useful failure where
  relevant, and links to one next step.
- [ ] Three real use cases pass `luam check` and `luam build`, avoid private
  framework assumptions, and include reviewed evidence from an actual MTA run.
- [ ] Every runtime transcript has provenance metadata and explicit redactions;
  automated validation rejects missing metadata, forbidden sensitive patterns,
  stale references, and unapproved redaction forms.
- [ ] Three author-provided VS Code screenshots are sharp at normal and 200% zoom,
  contain no sensitive information, have localized captions and useful alt text,
  declare dimensions, and are never the sole source of information.
- [ ] Paired migration pages provide a complete reviewed `0.1.x -> 0.7.0` action
  path, and the language comparison accurately distinguishes Luam from Lua 5.1,
  Luau, and TypeScript with authoritative references.
- [ ] The output explorer derives emitted Lua, mappings, helpers, and
  contributions from the real compiler and clearly distinguishes erased,
  transformed, and unsupported project-level output.
- [ ] Every applicable recipe and use case offers a deterministic archive built
  from its verified canonical source; archives contain no output, secret, local
  configuration, unsafe path, or untracked file.
- [ ] The API explorer is generated from the pinned MTA catalog, supports
  environment and procedural/OOP filters, provides stable URLs, and adds no
  handwritten duplicate API inventory.
- [ ] Every documented diagnostic has a stable anchor and compiler-backed failing
  fixture; its corrected example passes the current compiler.
- [ ] Documentation integrity checks report broken links, orphan pages, missing
  navigation, inaccessible or missing images, duplicate anchors, snippet drift,
  and generated-data drift before deployment.
- [ ] The user-facing architecture page explains why CLI, editor, and playground
  results agree, and its pipeline diagram has an equivalent textual explanation.
- [ ] Page feedback requires an explicit user action and sends only page URL,
  locale, rendered version, and title; no playground source or background
  telemetry leaves the browser.
- [ ] The landing page and playground work at 360, 768, and 1440 px, in light and
  dark themes, with keyboard-only navigation, visible focus, reduced motion, and
  no horizontal page overflow.
- [ ] At least four of five usability participants complete all five tasks without
  intervention; repeated hesitation is resolved or recorded as follow-up work.
- [ ] `pnpm docs:verify`, browser/Node playground parity tests, evidence validation,
  and the production VitePress build pass in CI.
