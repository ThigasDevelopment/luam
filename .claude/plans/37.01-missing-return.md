# 37.01 - Report a function that can end without returning

## Objective

Make a declared return type mean what it says, so a function annotated
`: string` cannot fall off the end of its body and hand the caller `nil`.

## Scope

- **In:** The end-of-body check in `checkFunctionBody`, the new diagnostic, and
  the rules that decide which declared return types tolerate falling through.
- **In:** Every construct that reaches `checkFunctionBody` — a function
  declaration, a function expression, a class method, a constructor.
- **Out:** Unreachable-statement reporting. Lua 5.1 already makes a statement
  after `return` a syntax error, so there is nothing to report.
- **Out:** Inference. A function with no return annotation infers its type from
  the returns it has; nothing here changes that path.
- **Out:** Exhaustiveness over a union discriminant. Deciding that a chain of
  `if`s covers every member is a separate analysis and a separate task.

## Context

The checker reports `check-return-mismatch` on a `return` whose value does not
match the annotation. It reports nothing about a path that has no `return` at
all. Compiled against the current CLI, this passes with zero diagnostics:

```luam
function pick(flag: boolean): string
    if flag then
        return 'yes'
    end
end
```

`pick(false)` is `nil`, the annotation said `string`, and every caller was told
otherwise. The same silence covers a method, a constructor and a function
expression, and it survives `warningsAsErrors` because nothing is emitted to
promote.

### The analysis already exists

This is not a new pass. `FlowState` in `packages/compiler/src/checker/flow.ts`
already carries a reachability flag beside its narrowing facts, and
`context.markUnreachable()` clears it. `packages/compiler/src/checker/statements.ts`
calls it on `return-statement`, `break-statement` and `continue-statement`.
`joinFlows` filters unreachable states out of a join and returns an unreachable
state when every branch exited, which is what makes an `if` whose branches all
return hand the rest of the block to nobody.

So after `checkStatements(context, body)` inside `checkFunctionBody`, the answer
is already sitting in `context.flowState.reachable`: true means control can
reach the closing `end`.

The insertion point is between two existing lines in
`packages/compiler/src/checker/statements.ts` — the call to `checkStatements`
and the `context.popReturnType()` that follows it.

## Design

### When falling through is legal

A body that can reach its end is only a defect when the annotation promised a
value. The rule, in the order the check should apply it:

| Declared return type | Falling through |
|---|---|
| Absent | Legal. The type is inferred from the returns present. |
| `void` | Legal. That is what `void` means. |
| `any` | Legal. `checkReturn` already returns early on `any`; this must match. |
| `nil` | Legal. The value produced by falling through is exactly `nil`. |
| Optional, or a union containing `nil` | Legal. `nil` is a member. |
| Anything else | `check-missing-return`. |

The optional row carries the fix: a developer told that `pick(): string` is
wrong changes it to `pick(): string?` and the annotation becomes true. That is
the repair the message should name, which also makes this diagnostic a candidate
for a quick fix once T-04 confirms it has exactly one correct repair.

A tuple return type falls through to the last row. A function declaring two
return values that ends without returning gives the caller two nils.

### Severity

Error, not warning. It is the same class of defect as `check-return-mismatch`,
which is an error, and reporting the two at different severities would say the
mismatch matters more when a return is written than when it is forgotten.

The risk is the blast radius: existing code, the documented examples, the
snippet projects and `examples/` may all contain functions this rejects. T-02
measures that before T-03 changes behaviour, and the measurement decides whether
this lands as an error outright or as a warning promoted in a later release.
Record the decision here; do not add a strictness flag for it. A second checking
mode is a permanent cost paid to avoid a one-time fix.

### The message

`check-missing-return` reads:

> This function declares "string" but can end without returning a value. Add a
> return on every path, or declare "string?".

Reported at the function's own position rather than at the closing `end`, so the
editor underlines the signature that made the promise.

## Record

### T-01 - What the reachable flag answers

- `context.flowState.reachable` after `checkStatements` is false for a body whose
  every path returns, including an `if`/`elseif`/`else` chain that returns in
  every branch. `joinFlows` already returns an unreachable state when no branch
  survives, so no new analysis was needed.
- `while true do ... end` gave the **wrong** answer. `checkLoopBody` restores the
  entry flow after the body, so an infinite loop left the state reachable and
  would have been reported. Fixed in `control-flow.ts`: `checkWhile` marks the
  state unreachable when the condition is a truthy literal and the body has no
  `break` that belongs to it.
- `repeat ... until false` had the same defect and is reconciled with the same
  rule, mirrored on a falsy literal condition. A `break` in either form makes the
  loop exit again, and `hasBreak` deliberately does not descend into a nested
  loop or a function body, because a `break` there belongs to the inner loop.
- `error(...)` as the last statement is **not** treated as an exit. A call
  statement never marks the flow unreachable, so a body ending in `error(...)`
  under a concrete annotation is reported. Recorded as a known false positive,
  not fixed here: treating a call as a terminator needs a never-returning type
  the system does not have. The repair available today is widening the
  annotation.

### T-02 - Blast radius: zero

Measured with the diagnostic live, before deciding severity:

| Corpus | Hits |
|---|---|
| `packages/compiler` suite (1263 tests) | 0 |
| Every `.luam` file tracked by git (85 files) | 0 |
| `docs/snippets` (12 projects) | 0 |
| Documented examples (242, 26 erroring on purpose) | 0 |
| Captured outputs (63) | 0 |
| `packages/lsp` suite (456 tests) | 0 |
| `packages/cli` suite (370 tests) | 0 |

**Decision: it lands as an error**, as designed. Nothing in the repository is
rejected, so the argument for staging it as a warning has no case to answer. It
sits at the same severity as `check-return-mismatch`, which is the point.

### T-03 - Where it lives

- `packages/compiler/src/checker/statements.ts` — `toleratesFallthrough` holds
  the table, `reportMissingReturn` holds the message, and the check sits between
  `checkStatements` and `popReturnType` inside `checkFunctionBody`.
- The declared type is read with `context.currentReturnType()`, which is the
  same value `checkReturn` reads, so `any`, `void` and an alias resolving to an
  optional agree between the two by construction rather than by duplication.
- `unknown` was added to the tolerant set alongside `any`. It is the other type
  that carries no promise about a value.
- `checkFunctionBody` gained a trailing `position`. All four constructs pass
  their own: a function declaration, a function expression, a class method and a
  constructor (a constructor is a class method named `constructor`).

### T-04 - No quick fix

`check-missing-return` does **not** register a quick fix. Milestone 32's rule is
exactly one correct repair, and this diagnostic has two that are both ordinary:
add a return, or widen the annotation. Widening is the one a machine could
apply, and it is the one that silently changes the contract every caller was
compiled against — a plausible wrong edit that compiles, which the rule exists to
prevent. The message names the widening so the author can choose it; the editor
does not choose it for them.

A second reason is mechanical. Every fix in `quick-fixes.ts` anchors on the token
at the diagnostic offset, and this diagnostic is reported at the function's own
position so the editor underlines the signature. The annotation is an unbounded
distance away.

### T-05 - No fallout

T-02 found nothing to fix, so nothing was changed and no snapshot moved.

- [x] A body whose every branch returns reports nothing.
- [x] A `while true do` loop with no exit and no return reports nothing.
- [x] A class method, a constructor and a function expression are each reported
      on the same terms as a function declaration.
- [x] The compiler suite, `examples/`, `docs/snippets` and the documented
      examples all pass, with every change justified in the T-05 record.

## Out of Scope

- A strictness flag or a second checking mode.
- Exhaustiveness over a discriminated union.
- Treating `error(...)` as a terminator, which needs a never-returning type.
- Unreachable-code reporting, which Lua 5.1 makes a syntax error.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The check rejects a large amount of existing code | High | T-02 measures before T-03 changes behaviour; the error-versus-warning decision is conditional on that number |
| `error(...)` at the end of a body is reported as missing a return | Medium | Named in T-01 as a known false positive; the repair is an annotation change, and the alternative needs a type-system feature |
| A loop that never falls through is reported | Medium | T-01 pins `while true` and `repeat until false` before the diagnostic is written |
| The declared type resolves differently here than in `checkReturn` | Medium | T-03 reuses the same resolution path rather than reading the annotation again |
