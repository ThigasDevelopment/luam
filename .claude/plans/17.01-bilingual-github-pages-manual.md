# 17.01 - Publish a bilingual GitHub Pages manual

## Objective

Publish a modern, versioned Luam manual in en-US and pt-BR so developers can
install the toolchain, write resources, diagnose failures, and deploy to MTA
without relying on the repository README.

## Scope

- **In:** VitePress site, en-US and pt-BR content, language and CLI reference,
  recipes, example verification, accessibility, search, and GitHub Pages deploy.
- **Out:** Translating CLI, compiler, LSP, diagnostics, generated resources, or
  the VS Code extension; they remain English-only product surfaces.

## Decisions

- Use VitePress because the manual is static, Markdown-first, and needs no
  product backend or runtime service.
- Publish under `/luam/`, with `/en/` and `/pt-br/` as locale roots. The root
  page offers language selection and defaults to en-US when no preference exists.
- Treat en-US as the source locale. Code, API names, diagnostics, CLI commands,
  configuration keys, file paths, and source keywords are never translated.
- Keep a one-to-one page map between locales. A locale may omit a page only when
  it carries a visible "Translation in progress" marker and the CI allowlist names it.
- Keep `README.md` as the concise repository landing page and link detailed
  material to the manual rather than maintaining duplicated reference content.

## Information Architecture

Each locale contains the same sections and page identifiers:

| Section | Purpose |
| --- | --- |
| `guide/` | Install, quick start, project layout, daily development, troubleshooting. |
| `language/` | Lua foundations, types, declarations, classes, directives, and emitted Lua. |
| `mta/` | Server/client/shared environments, events, APIs, OOP, resources, and security boundaries. |
| `tooling/` | CLI commands, `luam.json`, environment files, VS Code, LSP, CI, and deployment. |
| `recipes/` | Complete, task-oriented resource examples with expected output. |
| `reference/` | Keywords, operators, directives, config fields, diagnostics, limitations, and compatibility. |

## Content Rules

- Every language feature page includes source Luam, emitted Lua when its
  transformation matters, expected behavior, and at least one common error.
- Recipes include prerequisites, file tree, complete source, commands, expected
  result, and cleanup or security notes where relevant.
- pt-BR translates prose and navigation only. At first use, it may explain a
  technical word, such as "resource (recurso MTA)", while retaining the original
  identifier thereafter.
- The reference does not imply that contextual words are globally reserved.
- Documentation states the Luam version it applies to and links to the relevant
  release or changelog entry.

## Acceptance Criteria

- [x] `pnpm docs:build` produces a static site with no broken internal links.
- [x] The deployed site provides equivalent en-US and pt-BR navigation at
  `/luam/en/` and `/luam/pt-br/`, plus a working locale selector.
- [x] Locale parity validation fails when a non-exempt page is missing or has no
  paired translation.
- [x] The keyword page correctly separates the 22 lexical keywords from
  contextual language terms and links each term to its grammar page.
- [x] A new user can create, check, build, and run a basic MTA resource by
  following either locale without unstated repository knowledge.
- [x] All documented recipes and snippets are checked automatically against the
  current compiler behavior.
- [x] Documentation deployment runs after successful validation and requires no
  deployment secret beyond GitHub's Pages token.
- [x] Pages are readable with keyboard navigation, narrow screens, and both light
  and dark color schemes.
