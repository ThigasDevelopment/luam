# 8.3 — Define signature normalization and overrides

> File: `.claude/plans/8.3-signature-normalization-architecture-engineer.md`

## Objective

Decide how ambiguous upstream declarations become Luam types, so a full import
never turns a valid resource into a wall of false diagnostics.

## Scope

- **In:** Environment resolution for functions that exist on both sides,
  multi-return handling, `any` fallbacks, deprecated functions, name collisions,
  the override module, and the `outputChatBox` decision.
- **Out:** Tuple types in the checker and the import run itself.

## Steps

- [x] Declare a function that exists on the server and the client as `shared`,
      and record the exceptions the project wants to keep stricter.
- [x] Revisit `outputChatBox`: the Wiki declares it on both sides, while the
      milestone 3 catalog scopes it to the server. Decide which rule wins and
      record it.
- [x] Type a multi-return function as `any` until the checker models tuples, and
      list the functions this affects.
- [x] Decide what happens to deprecated and removed functions: excluded, or
      declared and reported as a warning.
- [x] Add an override module the generator never rewrites, for signatures the
      upstream source gets wrong or that the project wants tightened.
- [x] Keep the rule that an undeclared name stays `any` without a diagnostic, so
      a gap in the catalog never blocks a build.

## Acceptance Criteria

- [x] Every rule is written down and applied by the generator, not applied by
      hand per function.
- [x] An override wins over the generated declaration and survives a
      regeneration.
- [x] No name is declared in more than one catalog after normalization.
- [x] A function whose environment the source cannot resolve falls back to
      `shared`, the permissive side.
