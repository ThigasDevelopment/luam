# 32.02 - Add a document formatting provider to the LSP

## Objective

Give Luam a formatter, so format-on-save works in every editor the extension
supports and a project stops arguing about layout in review.

## Scope

- **In:** `documentFormattingProvider` and `documentRangeFormattingProvider`, the
  formatter itself, and the settings the extension contributes for it.
- **Out:** Code actions and quick fixes, which are [32.03](32.03-code-actions.md).
- **Out:** Inlay hints. They are not part of milestone 32 at all.
- **Out:** A `luam format` CLI command. The editor is the surface this plan
  delivers; a CLI entry point is a separate decision about what CI should
  enforce.

## Context

`packages/lsp/src/server/capabilities.ts` declares completion, signature help,
hover, definition, references, rename, document symbols, an execute-command
provider and — conditionally — semantic tokens. It declares no formatting
provider of either kind. There is no way to format a `.luam` file today, and
format-on-save is the first thing a developer arriving from TypeScript reaches
for and does not find.

The formatter has one hard constraint the rest of the LSP does not: it rewrites
the user's source. It must be total on every parseable file and must never be
partial, because a formatter that drops a construct it did not recognize
destroys work.

## Steps

### T-01 - Decide the style and write it down

**Agent:** architecture-engineer

- [ ] Derive the style from what the repository's own `.luam` fixtures and
      snippets already look like, so formatting the existing corpus is close to a
      no-op.
- [ ] Settle indentation, line width, blank-line rules between declarations,
      table and argument-list wrapping, and where the language's own constructs —
      `class`, `interface`, `enum`, decorators, type annotations — sit.
- [ ] Record the style as a reference page, so it is a documented contract rather
      than whatever the implementation happened to do.

### T-02 - Implement the formatter

**Agent:** architecture-engineer

- [ ] Format from the parsed AST plus the token stream, so comments and their
      attachment survive.
- [ ] Preserve every construct: a file the formatter cannot fully account for is
      returned unchanged rather than emitted partially.
- [ ] Make the formatter idempotent — formatting formatted output changes
      nothing.

### T-03 - Wire the providers

**Agent:** architecture-engineer

- [ ] Declare `documentFormattingProvider` and
      `documentRangeFormattingProvider` in `capabilitiesFor`.
- [ ] Return no edits, rather than an error, for a file with parse errors, so
      format-on-save never mangles a file mid-edit.
- [ ] Contribute the editor settings the extension needs for format-on-save, and
      document them in [editors](../../docs/en/tooling/editors.md).

## Acceptance Criteria

- [ ] Formatting is idempotent: running it twice produces the same bytes as
      running it once.
- [ ] Formatting every `.luam` file in `docs/snippets` and the compiler fixtures
      preserves their meaning — the compiled Lua is byte-identical before and
      after.
- [ ] Comments keep their position relative to the construct they document,
      including a trailing comment on the same line.
- [ ] A file that fails to parse returns no edits and reports no error.
- [ ] Range formatting formats the selection and touches nothing outside it.
- [ ] Format-on-save works in VS Code with the shipped extension, and the setting
      that enables it is documented.
