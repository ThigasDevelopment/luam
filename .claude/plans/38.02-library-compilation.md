# 38.02 - Compile library sources as part of the consuming project

## Objective

Make a library's types reach the checker by compiling its source, so a call into
a library is checked as precisely as the library is written and a library that
does not type-check fails the consumer's build instead of degrading silently.

## Scope

- **In:** Feeding resolved library files into the project compile, resolving
  their environment, checking them, and making their top-level names visible to
  project files on compatible sides.
- **In:** `.d.luam` files a library ships for the verbatim Lua it does not
  compile.
- **Out:** Collision and requirement reporting, which is
  [38.03](38.03-library-collisions.md).
- **Out:** Writing anything, which is [38.04](38.04-library-vendoring.md).
- **Out:** A serialized type artifact. ADR-038 rejected one: the source is on
  disk, so there is nothing to publish and nothing to drift.

## Context

A project compile today is a list of `ProjectFile`s handed to `compileProject` in
`packages/compiler/src/project/project.ts`, discovered from the manifest's
`sources` patterns. Library files are a second origin for the same list, and the
design question is how much of the pipeline can stay unaware of that.

The answer ADR-038 forces is: almost all of it. A library file is "an ordinary
file of that environment once resolved", so after resolution it should flow
through the same binder, the same checker and the same registry as a project
file. What has to differ is narrow and specific:

- Its environment comes from the library's own `luam` field, per side, and the
  consumer does not get to reassign it.
- Its patterns are package-root relative, never project-root relative.
- Its output path is `libs/<package>/<environment>/`, not `outputPath(sourcePath)`.
- A diagnostic reported inside it has to say which package it came from, or the
  developer sees an error in a file they did not write and cannot place.

That last point is the one most likely to be got wrong, and it is worth its own
step.

### Ordering

Compile order matters for the same reason it matters inside a project: a class
is a type everywhere but a value from its declaration, and a library's classes
must be registered before a project file that extends one. The emission order
ADR-038 fixes — libraries after the runtime helpers and before the project's own
sources — is the order the compile should use too, so what the checker saw and
what the resource loads agree.

## Design

### One list, two origins

`ProjectFile` gains an optional origin naming the package a file came from, absent
for a project file. Every consumer of the list that does not care is untouched;
the three that do — environment resolution, output path, diagnostic
attribution — read it.

This is preferred over a parallel list of library modules, because a second list
means every pass that walks modules has to be taught to walk two, and the passes
that forget are exactly where a library symbol goes missing.

### Environment

A library file's environment is decided by which side of the library's `luam`
field matched it, and a `#!` directive inside a library file is a conflict rather
than an override — the library declared its layout in one place, and a second
place that can disagree is a bug source with no benefit. Decide in T-01 whether
that conflict is an error or whether the directive simply loses, and record it.

Once resolved, the existing rules apply unchanged. A `server` library symbol used
from a client file is the environment error that already exists under
[ADR-023](../docs/adr/023-file-level-environments.md), with no new rule and no
new code.

### Visibility

`buildSymbolTable` in `packages/compiler/src/project/module-graph.ts` already
builds the cross-file symbol table that makes a class in one file visible to
another. A library module contributes to it on the same terms. Nothing about
visibility needs a new mechanism; what needs care is that a project file may see
a library symbol and a library file may not see a project symbol. A library that
depends on the consumer's globals is not a library, and the one-way rule should
be enforced rather than left to convention — record the decision in T-01.

### Diagnostics from inside a library

A diagnostic in a library file must carry the package name in the path the
reporter prints, so the developer reads `@luam/collections/src/list.luam:12`
rather than a path inside `node_modules` that means nothing to them. The CLI
reporter in `packages/cli/src/reporting` formats the path; T-04 decides the exact
form and applies it in one place rather than at every report site.

Severity is not softened. ADR-038 says a library that does not type-check fails
the consumer's build, and that is the whole point of compiling from source
rather than trusting a summary.

## Steps

### T-01 - Decide the three rules that differ

**Agent:** architecture-engineer

- [ ] Decide whether a `#!` directive inside a library file is an error or is
      ignored, and record the reasoning.
- [ ] Decide and enforce that visibility is one-way: a project file sees library
      symbols, a library file does not see project symbols.
- [ ] Confirm the compile order matches the emission order ADR-038 fixes —
      libraries in `libraries` order, their files in the order their `luam` field
      declares, all before the project's own sources.

### T-02 - Feed library files into the compile

**Agent:** architecture-engineer

**Files:** `packages/compiler/src/project/project.ts`,
`packages/compiler/src/project/module.ts`,
`packages/cli/src/build/source-discovery.ts`

- [ ] Add the optional package origin to `ProjectFile` and populate it during
      resolution.
- [ ] Append resolved library files to the compile list in the order T-01 fixed.
- [ ] Resolve each one's environment from the library's declaration.
- [ ] Confirm every pass that walks modules sees them without being changed, and
      name any that does not.

### T-03 - Declaration files

**Agent:** architecture-engineer

- [ ] Compile a library's `.d.luam` files through the existing declaration-file
      path, so a library that wraps verbatim Lua gets types without emitting.
- [ ] Confirm a declaration file from a library emits nothing, as a project
      declaration file already does.

### T-04 - Attribute diagnostics

**Agent:** architecture-engineer

**Files:** `packages/cli/src/reporting`

- [ ] Decide the printed form for a path inside a library and apply it in one
      place.
- [ ] Confirm a type error inside a library fails the consumer's build with a
      path the developer can act on.
- [ ] Confirm the LSP reports the same path form, so the editor and the CLI agree.

## Acceptance Criteria

- [ ] A project file calling a library function is checked against the signature
      the library's source declares.
- [ ] A library that does not type-check fails the consumer's build, with a
      diagnostic naming the package and the file.
- [ ] A `server` library symbol used from a client file reports the existing
      environment diagnostic, with no new code.
- [ ] A library `.d.luam` supplies types and emits nothing.
- [ ] A library class is registered before a project file that extends it.
- [ ] A library file cannot see a project global.
- [ ] A project with an empty `libraries` list compiles exactly as it does today,
      proven by an unchanged snapshot.

## Out of Scope

- Collision and requirement diagnostics.
- Output paths and `meta.xml`.
- Serialized types or a published summary.
- Transitive resolution.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A pass that walks modules is missed and a library symbol goes invisible | High | T-02 enumerates the passes rather than assuming the single-list change covers them |
| A diagnostic points inside `node_modules` and means nothing to the developer | High | T-04 owns the path form and applies it in one place |
| Compile order and emission order disagree, so the checker sees what the resource does not | High | T-01 fixes one order for both |
| A library file depends on a consumer global and works by accident | Medium | One-way visibility enforced in T-01, not left to convention |
| A `#!` directive inside a library silently overrides its declared layout | Medium | Decided in T-01 |
