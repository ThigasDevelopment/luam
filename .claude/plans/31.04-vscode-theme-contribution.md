# 31.04 - Generate and contribute the VS Code themes

## Objective

Turn the role table into `Luam Dark` and `Luam Light`, generated rather than
hand-written, and ship them from the existing extension so a user gets the
language and its theme from one install.

## Scope

- **In:** A generator in `packages/theme` that emits VS Code colour themes, the
  scope and semantic-token mapping, the two committed theme files, and the
  `contributes.themes` entry.
- **Out:** Other editors, which is 31.5, and any hand-editing of the generated
  files. A theme file edited by hand is a theme file that has drifted.

## Why Generated

Two themes times roughly seventy roles times two mapping surfaces is
two hundred and eighty values that must agree. Hand-maintained, the light theme
drifts from the dark one within two changes, and the semantic map drifts from
the TextMate map immediately. Generation makes the role table the only place a
colour decision exists, which is also what lets 31.6 assert against it.

## Steps

### T-01 - Map roles to TextMate scopes

**Agent:** architecture-engineer

- [ ] `src/targets/textmate.ts` maps each role to the scopes 31.2 produces. One
      role may claim several scopes; a scope may not be claimed twice.
- [ ] Include the `source.luam-manifest` scopes in the same map, so the manifest
      is themed by the same roles.
- [ ] Cover the common non-Luam scopes a user still meets in the same window —
      JSON, Markdown, Lua output, diff — at a deliberately plain level. A theme
      that only handles its own language is unusable as a daily driver, and the
      generated Lua sitting next to the source is the first thing a Luam user
      opens.

### T-02 - Map roles to semantic tokens

**Agent:** architecture-engineer

- [ ] `src/targets/semantic.ts` maps each `(type, modifiers)` combination from
      31.3's legend to a role, including the custom modifiers.
- [ ] Order matters: VS Code resolves the most specific selector, so
      `function.defaultLibrary.mtaNative` must be expressed as its own selector
      rather than relied on to inherit.
- [ ] Every custom modifier must change something visible. A modifier that
      resolves to the same style as its base is dead weight and must be removed
      from the legend in 31.3 instead of carried here.

### T-03 - Build the workbench colours

**Agent:** architecture-engineer

- [ ] Derive the chrome from the same ramps: editor, sidebar, activity bar,
      status bar, tabs, panel, terminal, peek view, and the git decorations.
- [ ] Terminal ANSI colours come from the same four hues plus red, so the CLI's
      own output — its progress renderer and diagnostic layout — lands inside the
      theme rather than beside it.
- [ ] Diagnostics use red, amber, cyan, and ink for error, warning, info, and
      hint, which is the only place red is allowed.

### T-04 - Emit and commit

**Agent:** architecture-engineer

- [ ] `scripts/build-theme.ts` writes `packages/vscode/themes/luam-dark.json`
      and `luam-light.json`, with stable key order and a header comment naming
      the generator and forbidding hand edits.
- [ ] Commit the output. The extension bundle must not require the generator to
      run, and a reviewer must be able to read the diff of a colour change.
- [ ] Wire the script into the extension's `bundle` step so a stale file fails
      the build rather than shipping.

### T-05 - Contribute the themes

**Agent:** architecture-engineer

- [ ] Add both to `contributes.themes` with `uiTheme` `vs-dark` and `vs`, and
      labels `Luam Dark` and `Luam Light`.
- [ ] Add `themes` to the extension `categories` and to `.vscodeignore`'s keep
      list, and confirm the packaged extension carries the files.
- [ ] Leave the theme unselected on install. An extension that changes a user's
      colours without being asked is a bad citizen; the README tells them how to
      pick it.

## Acceptance Criteria

- [ ] `Luam Dark` and `Luam Light` appear in the theme picker and apply cleanly.
- [ ] Regenerating produces no diff. The committed files are exactly what the
      generator writes.
- [ ] Every scope emitted by both grammars resolves to an explicit rule; nothing
      falls through to the editor default foreground.
- [ ] Every semantic token type and modifier combination from 31.3 resolves to an
      explicit rule.
- [ ] Opening a `.luam` file, a `.luam.manifest`, and a generated `.lua` side by
      side reads as one theme.
- [ ] The extension packages with the themes included and no increase in
      activation work.
